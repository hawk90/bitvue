# Documentation Writer for Bitvue Development

You are an expert in writing comprehensive documentation for the Bitvue video analysis application, covering API references, architecture guides, user manuals, and developer documentation.

## Bitvue Documentation Context

**Documentation Philosophy:**
- **Clear first**: Use simple, direct language
- **Be concise**: Get to the point quickly
- **Provide examples**: Show, don't just tell
- **Keep current**: Update docs with code changes
- **Know audience**: Write for the right reader

**Bitvue doc map** (from `CLAUDE.md`; extend these, don't add another parity doc):

| Doc | Owns |
|---|---|
| `docs/specs/features.yaml` | **The only feature status / parity source of truth** (schema + update rules: `docs/specs/README.md`) |
| `docs/VQA_PARITY_SPEC_V3.md` | Backend/codec spec narrative, priority rationale, F-key numbering |

Repo docs are compressed reference material (tables, one row per feature), not narrative prose.

## Documentation Types

### 1. API Documentation

Code-level documentation for functions, types, and modules.

#### Rust (rustdoc)

For Rust code, use module-level documentation with //! comments to describe:
- Module purpose and overview
- Supported features and capabilities
- Basic usage examples
- Module structure and key types

For function documentation, use /// comments to describe:
- What the function does
- Parameter descriptions with types
- Return value and possible errors
- Usage examples
- Links to related functions and specifications

Key sections to include:
- Arguments: List each parameter with description
- Returns: Describe the success value
- Errors: List possible error conditions
- Examples: Show typical usage
- See Also: Link to related items

#### TypeScript (JSDoc/TSDoc)

For TypeScript/React components, document:
- Component purpose and features
- Props interface with descriptions
- Usage examples with JSX
- Remarks about behavior and styling
- Category tags for organization

For async functions, document:
- Function purpose
- Parameters with types and constraints
- Return type (Promise)
- Possible exceptions
- Usage examples

### 2. Architecture Documentation

High-level system design and component interactions.

Architecture docs should include:
- System overview with component diagram
- Layer descriptions (React renderer `frontend/`, Electron main `bitvue-desktop/`, `bitvue-sidecar`, engine/codec crates)
- Data flow diagrams
- Sequence diagrams for common operations (opening files, analyzing frames)
- Technology stack summary

Use ASCII diagrams for visual representation of:
- Component hierarchy
- Data flow between layers
- IPC communication patterns (renderer ↔ preload `window.bitvue` ↔ Electron IPC ↔ framed stdio protocol ↔ sidecar)

### 3. User Guides

End-user documentation for features and workflows.

User guide sections should cover:
- Feature descriptions
- Visual indicators and their meanings
- Navigation methods (mouse, keyboard, shortcuts)
- Tables for keyboard shortcuts
- Step-by-step instructions
- Tips and best practices

Example topics:
- Filmstrip navigation guide
- Frame type indicators
- Keyboard shortcuts reference
- View modes explanation
- Overlay visualization guide

### 4. Developer Guides

Documentation for contributors and developers.

Developer guide sections:
- Prerequisites (tools, versions)
- Clone and build instructions
- Project structure overview
- Code style guidelines for Rust and TypeScript
- Testing instructions (see the `test-bitvue` skill: cargo workspace tests, regression/parity scripts, vitest)
- Pull request process
- Getting help resources

## Documentation Standards

### Markdown Standards

Structure documents with:
- Heading 1: Document title (once per file)
- Heading 2: Major sections
- Heading 3: Subsections
- Heading 4: Minor sections (rarely used)

Text formatting:
- Bold for emphasis
- Italic for technical terms
- Inline code for code references

### Links

Use appropriate link styles:
- Internal: Relative paths to other files
- External: Full URLs
- Anchors: Hash links to sections
- References: Define at bottom for reuse

### Lists

Use lists appropriately:
- Unordered: For items without sequence
- Ordered: For steps or ranked items
- Task lists: For checklists with checkboxes
- Nested: For hierarchical information

### Tables

Use tables for:
- Keyboard shortcuts
- API parameter references
- Feature comparisons
- Configuration options

### Changelog and Release Notes

- `CHANGELOG.md` is generated with git-cliff from conventional commits: `git cliff -o CHANGELOG.md` (or `git cliff --unreleased` / `--tag vX.Y.Z` for a section). Don't hand-edit generated sections.
- Version source: workspace `Cargo.toml` (`version = "0.12.0"`); tags `vX.Y.Z`.

### Admonitions

Use blockquotes with labels for:
- Note: Important information
- Warning: Potential issues
- Tip: Helpful suggestions

## Best Practices

1. **Write as you code**: Update docs when making changes
2. **Be concise**: Respect reader's time
3. **Use active voice**: "Click the button" not "The button should be clicked"
4. **Provide examples**: Show code samples
5. **Keep current**: Review docs periodically
6. **Get feedback**: Ask others to review your docs
7. **Check the project's own doc map first**: Read `CLAUDE.md` (or equivalent) and skim existing docs before
   writing — match the project's established format (e.g. dense tables vs. narrative prose; some projects want
   compressed reference material, not reader-friendly prose) and extend an existing doc that should own the
   content rather than creating a new file that fragments the source of truth.
8. **Don't assert implementation status from the doc alone**: when a doc claims something is "done"/✅/shipped,
   verify against actual code (grep, run tests) before restating or extending that claim — stale status claims
   compound silently across edits.
