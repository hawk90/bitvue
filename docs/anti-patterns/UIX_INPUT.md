# Anti-Pattern Catalog — UIX_INPUT: 조작과 키보드 UX

이 문서는 더 큰 안티패턴 카탈로그의 일부입니다(전체 목차는 별도 작성 중인 `docs/anti-patterns/INDEX.md` 참고). UI/UX+Tauri Phase 3 웨이브에 속하며, Phase 1(Rust/미디어 엔지니어링)·Phase 2(VQ-Probe 도메인)에 이어 마우스 없이도 생산적으로 작업해야 하는 파워유저 도구(비트스트림 분석기)의 조작·키보드 UX를 다룹니다. 이 파일은 1단계(일반 참조 카탈로그)이며, 2단계에서 Bitvue 저장소를 실제로 감사해 각 항목의 "Bitvue 판정"을 채웁니다. Bitvue에는 이미 문서화된 키보드 단축키 표(`docs/PARITY_CHECKLIST.md` Layer 4)가 있으므로, 2단계 감사 시 modifier key 일관성(UIX-INPUT-011)을 그 표와 교차 검증할 가치가 있습니다.

---

### UIX-INPUT-001: keyboard navigation 없음

**분류**: 키보드 내비게이션 · **심각도**: Critical · **탐지**: Interaction

**사용자 목표**:
마우스에서 손을 떼지 않고(혹은 아예 떼고) 패널·리스트·트리·타임라인을 순회하며 분석 흐름을 유지하고 싶다.

**증상**:
- 프레임 리스트, NALU/OBU 트리, 에러 로그 리스트 등에서 방향키를 눌러도 아무 반응이 없다.
- Tab 키로 포커스를 이동시켜도 시각적 포커스 링이 어디 있는지 보이지 않는다.
- 트리 노드를 펼치거나 접으려면 반드시 마우스로 화살표 아이콘을 클릭해야 한다.
- 리스트 항목 100개를 확인하려면 100번 클릭하거나 스크롤+클릭을 반복해야 한다.

**원인**:
리스트/트리/그리드 컴포넌트를 `<div onClick>` 나열로 구현하고 `tabIndex`, `role`, `aria-activedescendant`, `onKeyDown` 방향키 핸들러를 처음부터 설계에 포함하지 않았기 때문. 시각적 스타일만 리스트처럼 보이게 만들고 상호작용 모델은 구현하지 않은 경우가 흔하다.

**구현 냄새**:
- 리스트/트리 컴포넌트에 `onKeyDown` 핸들러가 아예 없음.
- `tabIndex`가 지정되지 않아 포커스 자체가 불가능한 클릭형 `<div>` 항목.
- 포커스 스타일(`:focus-visible`)이 CSS에서 명시적으로 제거되어 있음(`outline: none`만 있고 대체 스타일 없음).
- 커스텀 드롭다운/콤보박스가 네이티브 `<select>`/ARIA 패턴 대신 순수 마우스 이벤트로만 구현됨.

**영향**:
반복적인 프레임/블록/에러 탐색이 전부 클릭 기반이 되어 손목 피로와 처리량 저하를 유발한다. 접근성 요구사항(스크린리더, 키보드 전용 사용자)도 동시에 위반한다. 파워유저가 자연스럽게 기대하는 "화살표로 훑고 Enter로 확정" 흐름이 근본적으로 불가능해진다.

**권장**:
- 리스트/트리/그리드에 roving tabindex 또는 `aria-activedescendant` 패턴을 적용해 방향키 이동을 지원한다.
- 트리 노드는 좌/우 화살표로 접기/펼치기, 상/하 화살표로 형제/자식 이동을 지원한다(WAI-ARIA Tree View 패턴 참고).
- 포커스 상태를 항상 시각적으로 렌더링한다(`:focus-visible` 대체 스타일 필수).
- Home/End, PageUp/PageDown 등 대량 이동 키도 함께 지원한다.

**탐지**:
- 마우스를 물리적으로 뽑고 Tab/화살표/Enter만으로 프레임 100개를 순회해 목표 프레임에 도달할 수 있는지 시나리오 테스트.
- 접근성 린터(axe, eslint-plugin-jsx-a11y)로 `tabIndex` 누락, 클릭 전용 인터랙티브 요소를 스캔.

**Bitvue 판정**: 미정 — 2단계(저장소 감사)에서 채움

### UIX-INPUT-002: 같은 단축키가 포커스 패널마다 다른 의미

**분류**: 단축키 일관성 · **심각도**: High · **탐지**: Interaction

**사용자 목표**:
어느 패널에 포커스가 있든 같은 키는 같은 종류의 동작(예: Delete는 항상 "제거", Space는 항상 "재생/일시정지")을 수행할 것이라 믿고 손가락을 움직이고 싶다.

**증상**:
- 타임라인 패널에서 Space는 재생/정지인데, 트리 패널에서 Space는 노드 펼치기다.
- Delete 키가 프레임 패널에서는 "마커 삭제"지만 오버레이 패널에서는 "선택 해제"로 동작해 실수로 데이터를 지운다.
- 같은 세션 안에서 여러 번 오조작이 발생해 사용자가 결국 단축키 사용을 포기하고 마우스로만 조작하게 된다.

**원인**:
각 패널을 독립 팀/독립 시점에 개발하면서 전역 단축키 맵을 공유하지 않고 컴포넌트별로 로컬 `onKeyDown`을 임의로 붙였기 때문. 단축키를 설계 문서 없이 "그때그때 자연스러워 보이는 키"로 정했다.

**구현 냄새**:
- 단축키 정의가 중앙화된 테이블/레지스트리 없이 각 컴포넌트 파일 안에 `case 'Delete':`, `case ' ':` 형태로 흩어져 있음.
- 동일 키 코드에 대해 컴포넌트마다 다른 시맨틱 이름(`deleteMarker`, `clearSelection`)이 부여됨.
- 단축키 문서(치트시트)가 패널별로 따로 존재하거나 아예 없음.

**영향**:
숙련 사용자일수록 "몸에 밴 반사적 키 입력"에 의존하는데, 패널 전환 시 그 반사가 배신당해 데이터 손실(마커 삭제, 선택 해제)이나 의도치 않은 재생 상태 변경으로 이어진다. 신뢰가 무너지면 단축키 학습 자체를 포기한다.

**권장**:
- 단축키를 "동작 카테고리(재생 제어/편집/내비게이션/뷰)"로 분류한 중앙 레지스트리를 두고, 같은 카테고리의 키는 모든 패널에서 동일 시맨틱을 갖도록 강제한다.
- 패널 특화 동작이 꼭 필요하면 서로 다른 키를 배정하거나, 동일 키+다른 modifier 조합으로 명시적으로 구분한다.
- 파괴적 동작(삭제류)은 패널 불문 항상 확인 단계(짧은 undo 토스트 등)를 거치게 한다.

**탐지**:
- 전역 단축키 레지스트리를 키 코드 기준으로 그룹핑해 같은 키가 서로 다른 동작 카테고리에 매핑되는 항목을 정적으로 나열.
- 사용자 테스트: 패널 A에서 학습한 단축키를 패널 B에서 그대로 눌러보게 하고 오조작 빈도 측정.

**Bitvue 판정**: 미정 — 2단계(저장소 감사)에서 채움

### UIX-INPUT-003: 입력 필드 포커스 중 전역 단축키 실행

**분류**: 단축키 스코프 · **심각도**: Critical · **탐지**: Interaction

**사용자 목표**:
텍스트 입력창(프레임 번호, 검색어, 필터 표현식)에 값을 타이핑할 때는 그 문자가 오직 입력 필드로만 들어가길 원한다.

**증상**:
- 프레임 번호 입력창에 "120"을 입력하려는데 "1"이 눌리는 순간 전역 단축키(예: 레이어 1 토글)가 함께 발동한다.
- 검색창에 "f"를 입력했더니 필터 패널이 아니라 전체화면(fullscreen) 토글이 실행된다.
- Backspace로 텍스트를 지우려다 브라우저 뒤로가기(UIX-INPUT-015와 연관)나 "이전 프레임" 내비게이션이 함께 발동한다.

**원인**:
전역 키보드 이벤트 리스너를 `document`/`window` 레벨에 등록하면서 `event.target`이 입력 가능 요소(`input`, `textarea`, `contenteditable`)인지 검사하지 않았기 때문. 또는 React 이벤트 버블링 단계에서 로컬 핸들러가 `stopPropagation`을 호출하지 않아 전역 핸들러까지 이벤트가 도달한다.

**구현 냄새**:
- `document.addEventListener('keydown', handler)`에 target 화이트리스트/블랙리스트 검사가 없음.
- 입력 필드 컴포넌트가 `onKeyDown`에서 `e.stopPropagation()`을 호출하지 않음.
- 단축키 디스패처가 "현재 포커스가 텍스트 편집 가능한 요소인가"라는 개념 자체를 모델링하지 않음.

**영향**:
숫자/텍스트 입력이 도구 사용의 기본 동작인 분석기에서 이 결함은 즉시 체감되며, 사용자가 "이 앱은 타이핑 중 뭔가 랜덤하게 튄다"는 불신을 갖게 만든다. 특히 파괴적 단축키(삭제, 리셋)가 얽히면 데이터 손실로 이어진다.

**권장**:
- 전역 단축키 디스패처 최상단에서 `isEditableTarget(event.target)` 가드를 두고, 입력 가능 요소에 포커스가 있으면 명시적으로 허용된 키(Escape, Enter 등)만 통과시킨다.
- 입력 컴포넌트는 자신이 처리할 키에 대해 `stopPropagation`을 명시적으로 호출해 의도를 코드로 드러낸다.
- Escape 키로 입력 필드 포커스를 해제하고 전역 스코프로 복귀하는 표준 동작을 제공한다.

**탐지**:
- 모든 텍스트 입력 필드에 포커스를 두고 알파벳/숫자/Backspace/Delete를 눌러 전역 단축키가 함께 발동하는지 전수 테스트.
- 코드 스캔: `document.addEventListener('keydown'`, `window.addEventListener('keydown'` 호출부에서 target 검사 유무 확인.

**Bitvue 판정**: 미정 — 2단계(저장소 감사)에서 채움

### UIX-INPUT-004: 프레임 이동 단위가 고정

**분류**: 내비게이션 유연성 · **심각도**: Medium · **탐지**: Interaction

**사용자 목표**:
상황에 따라 프레임 단위(1프레임씩 정밀 이동), GOP 단위(구조 파악), 초 단위(대략적 탐색)로 이동 폭을 바꿔가며 탐색하고 싶다.

**증상**:
- 방향키가 항상 ±1 프레임만 이동시켜, 10,000프레임짜리 영상에서 특정 구간까지 가려면 방향키를 수천 번 눌러야 한다.
- Shift/Ctrl 같은 modifier로 이동 폭을 바꾸는 기능이 없어 큰 폭 이동은 오직 타임라인 드래그(마우스)로만 가능하다.
- I-frame/키프레임 단위로만 건너뛰고 싶어도 그런 옵션이 아예 없다.

**원인**:
프레임 이동 핸들러를 "가장 흔한 단일 유스케이스(정밀 이동)"만 상정하고 구현했고, modifier 조합이나 단위 전환 UI를 나중에 추가할 확장 포인트로 설계하지 않았다.

**구현 냄새**:
- 이동 로직이 `currentFrame + 1` / `currentFrame - 1`로 하드코딩되어 modifier 상태를 아예 읽지 않음.
- 이동 "단위"라는 개념이 상태로 존재하지 않고 코드 상수로 박혀 있음.
- GOP 경계, 키프레임 위치 같은 메타데이터가 이미 파싱되어 있음에도 내비게이션 로직과 연결되어 있지 않음.

**영향**:
긴 시퀀스에서 특정 결함 구간을 찾는 작업의 체감 속도가 프레임 총수에 비례해 느려진다. 결과적으로 사용자는 방향키 대신 타임라인 드래그(부정확)나 반복 클릭에 의존하게 되어 정밀도와 속도를 둘 다 잃는다.

**권장**:
- 기본 방향키 = 1프레임, Shift+방향키 = 1초(또는 GOP), Ctrl/Cmd+방향키 = 다음 키프레임/씬 경계처럼 계층적 이동 단위를 modifier로 구분한다.
- 이동 단위를 UI에 명시(현재 단위를 상태 표시줄에 표시)해 사용자가 지금 어떤 폭으로 이동 중인지 늘 알 수 있게 한다.
- 이미 파싱된 GOP/키프레임/씬 전환 메타데이터를 내비게이션 계층에 노출한다.

**탐지**:
- 10,000프레임 이상의 테스트 시퀀스에서 "500번째 결함 프레임까지 도달하는 데 필요한 키 입력 횟수"를 측정하는 시나리오 테스트.
- modifier 조합(Shift/Ctrl/Alt + 방향키) 전수 입력 후 이동 폭 로그 기록.

**Bitvue 판정**: 미정 — 2단계(저장소 감사)에서 채움

### UIX-INPUT-005: 이전·다음 오류 지점 이동 기능 없음

**분류**: 결함 중심 내비게이션 · **심각도**: High · **탐지**: Domain review

**사용자 목표**:
전체 시퀀스를 훑지 않고 "다음/이전 이상 지점(디코드 에러, QP 급변, 프레임 드롭, 신택스 위반)"으로 바로 점프하고 싶다.

**증상**:
- 에러 로그 패널에 목록은 있지만 그 항목을 클릭해도 타임라인/프레임 뷰가 해당 지점으로 이동하지 않는다.
- "다음 오류" 버튼이나 단축키가 없어서 사용자가 직접 스크럽바를 손으로 훑으며 이상 지점을 눈으로 찾아야 한다.
- 여러 종류의 이상(에러, 경고, 임계값 초과)이 섞여 있어도 종류별로 필터링해 건너뛸 방법이 없다.

**원인**:
에러/경고를 "로그에 나열해서 보여주면 끝"인 정적 리포트로만 취급하고, 그 데이터를 내비게이션 상태(현재 프레임 포인터)와 연결하는 계층을 설계하지 않았기 때문. 분석기의 핵심 가치가 "이상 지점을 빨리 찾는 것"임에도 로그 뷰와 플레이어 뷰가 별개의 기능으로 분리 개발되었다.

**구현 냄새**:
- 에러 리스트 컴포넌트와 프레임 뷰어 컴포넌트 사이에 공유 상태나 이벤트 연결이 없음(순수 표시용 리스트).
- 에러 데이터에 프레임 인덱스/타임스탬프는 있지만 그것을 "탐색 가능한 정렬된 인덱스"로 취급하는 유틸리티가 없음.
- "다음/이전" 개념이 프레임 단위 내비게이션에만 존재하고 이벤트 기반 내비게이션에는 존재하지 않음.

**영향**:
분석기의 존재 이유(문제 지점을 빠르게 특정)가 무색해진다. 수만 프레임 중 몇 개의 결함 프레임을 찾기 위해 사람이 눈으로 스크럽바를 훑어야 하므로, 자동 파싱/검증 로직이 만들어낸 가치가 UI 단에서 소실된다.

**권장**:
- 에러/경고/임계값 초과 이벤트를 프레임 인덱스 기준 정렬된 시퀀스로 취급하고, "다음 이슈"/"이전 이슈" 단축키(예: `]`/`[` 또는 F8/Shift+F8)를 제공한다.
- 이슈 종류별 필터(에러만/경고만/특정 신택스 위반만)를 내비게이션에 결합한다.
- 타임라인에 이슈 지점을 마커로 표시해 "다음 이슈로 점프"와 "시각적으로 어디 있는지 보기"를 함께 지원한다.

**탐지**:
- Domain review: 에러 로그 100건이 있는 테스트 시퀀스에서 첫 번째 오류부터 마지막 오류까지 키보드만으로 순회 가능한지 확인.
- 코드 스캔: 에러 리스트 데이터 구조와 현재 프레임 상태 간 연결(구독/콜백) 존재 여부.

**Bitvue 판정**: 미정 — 2단계(저장소 감사)에서 채움

### UIX-INPUT-006: selection history back/forward 없음

**분류**: 내비게이션 이력 · **심각도**: Medium · **탐지**: Interaction

**사용자 목표**:
프레임 A의 블록을 조사하다 참조 프레임 B로 점프한 뒤, 다시 A의 원래 위치로 "뒤로가기"로 정확히 복귀하고 싶다.

**증상**:
- 매크로블록/CU를 클릭해 참조 프레임으로 이동한 뒤 원래 있던 프레임·선택 상태로 돌아가려면 수동으로 프레임 번호와 블록 좌표를 기억해 다시 찾아야 한다.
- 여러 단계(A → B → C)로 깊이 파고든 뒤에는 원점으로 돌아가는 경로 자체를 잊어버린다.
- 브라우저 스타일의 Alt+←/→(또는 마우스 뒤로가기 버튼)를 눌러도 선택 이력이 아니라 페이지 자체가 이동하거나 아무 반응이 없다.

**원인**:
"현재 선택"만 단일 상태로 관리하고, 선택이 바뀔 때마다 스택에 push하는 이력 구조를 두지 않았기 때문. 참조 프레임 점프 같은 "탐색적 조사" 워크플로우를 설계 시점에 고려하지 않고 선택을 단순 값 대입으로만 다뤘다.

**구현 냄새**:
- 선택 상태가 `useState<Selection>` 단일 값으로만 관리되고 이력 스택이 없음.
- 참조 프레임 점프 로직이 `setSelection(newSelection)`으로 이전 값을 완전히 덮어씀.
- Undo/redo 인프라(있다면)가 선택 이동과 데이터 편집을 구분하지 않아 재사용이 안 됨(UIX-INPUT-014와 연관).

**영향**:
움직임 벡터를 따라 참조 프레임을 오가며 원인을 추적하는 것은 비트스트림 분석의 핵심 워크플로우인데, 그 경로를 되짚어올 수단이 없으면 사용자가 매번 종이에 좌표를 적어두는 식의 수작업으로 대체하게 된다.

**권장**:
- 선택 변경을 스택(back stack/forward stack)으로 관리하고 Alt+←/→ 또는 마우스 사이드 버튼에 바인딩한다.
- "참조 프레임으로 점프" 같은 명시적 내비게이션 액션은 항상 이력에 push하되, 단순 hover나 미리보기는 push하지 않도록 구분한다.
- 이력 항목에 "무엇에서 무엇으로 이동했는지"를 표시하는 간단한 브레드크럼/드롭다운을 제공하면 더 좋다.

**탐지**:
- 시나리오 테스트: 3단계 이상 참조 프레임을 따라간 뒤 Alt+←를 3번 눌러 정확히 원점(같은 프레임, 같은 블록 선택)으로 복귀하는지 확인.
- 코드 스캔: 선택 상태 관리 훅에 스택 자료구조 존재 여부.

**Bitvue 판정**: 미정 — 2단계(저장소 감사)에서 채움

### UIX-INPUT-007: zoom·pan·select 모드 전환이 불명확

**분류**: 모드 가시성 · **심각도**: High · **탐지**: Interaction

**사용자 목표**:
지금 마우스 드래그가 "화면을 이동(pan)"시키는지 "영역을 선택(select)"하는지 "확대(zoom)"하는지 드래그를 시작하기 전에 확실히 알고 싶다.

**증상**:
- 블록을 선택하려고 드래그했는데 화면이 pan되어 버리고, pan하려고 드래그했더니 의도치 않게 영역이 선택된다.
- 현재 모드가 툴바 아이콘의 미묘한 강조 색상 차이로만 표시되어 있어 화면을 오래 봐야 알아챈다.
- 모드 전환 단축키(예: `V`=select, `H`=pan, `Z`=zoom)가 존재하지만 그 사실 자체가 툴팁이나 문서 어디에도 드러나지 않는다.

**원인**:
드래그 제스처를 다루는 여러 도구(pan/zoom/select)가 같은 캔버스 위에서 같은 마우스 이벤트(mousedown+drag)를 소비하도록 설계되었는데, "현재 모드"라는 개념을 사용자에게 명확히 전달하는 UI(커서 모양, 상태 표시줄, 테두리 색)에 투자하지 않았다.

**구현 냄새**:
- 모드 상태가 내부 변수로만 존재하고 커서(`cursor: grab/crosshair/zoom-in`)에 반영되지 않음.
- 툴바 버튼의 활성 상태 표시가 `opacity: 0.8` 같은 미세한 차이뿐이고 텍스트 라벨이 없음.
- 모드 전환 시 애니메이션/피드백(토스트, 캔버스 테두리 색 변경)이 전혀 없어 전환 자체를 놓치기 쉬움.

**영향**:
정밀 조작이 핵심인 분석기에서 "의도한 제스처와 실제 결과가 다른" 경험이 반복되면 사용자가 도구를 신뢰하지 못하고 매번 실행 취소/재시도를 반복하게 되어 작업 속도가 크게 떨어진다.

**권장**:
- 모드별로 커서 모양을 명확히 다르게 하고(예: select=crosshair, pan=grab/grabbing, zoom=zoom-in), 상태 표시줄에도 현재 모드 이름을 텍스트로 표시한다.
- 모드 전환 단축키를 툴팁과 커맨드 팔레트/치트시트에 노출한다.
- Space 홀드로 임시 pan 모드 진입처럼, 업계 표준(이미지 편집 툴)의 관례를 따라 학습 비용을 낮춘다.

**탐지**:
- 사용자 테스트: 툴바를 보지 않고 커서 모양만으로 현재 모드를 맞힐 수 있는지 확인.
- Interaction: 모드 전환 후 첫 드래그 제스처의 오조작률(의도한 동작과 실제 동작 불일치 비율) 측정.

**Bitvue 판정**: 미정 — 2단계(저장소 감사)에서 채움

### UIX-INPUT-008: drag 시작 영역이 너무 작음

**분류**: 히트 타겟 · **심각도**: Medium · **탐지**: Interaction

**사용자 목표**:
패널 경계, 타임라인 핸들, 리사이즈 핸들을 마우스로 편하게 잡아 드래그하고 싶다.

**증상**:
- 패널 사이 리사이즈 경계선이 1~2px 폭이어서 정확히 그 픽셀에 커서를 올려야만 드래그가 시작된다.
- 타임라인의 in/out 마커 핸들이 너무 작아 확대된 4K 디스플레이에서도 클릭하기 어렵다.
- 여러 번 시도 끝에야 드래그가 시작되고, 그 사이 실수로 다른 요소(예: 프레임 선택)를 클릭해 상태가 바뀐다.

**원인**:
드래그 가능 요소의 "시각적 크기"와 "히트 영역(hit area)"을 동일하게 취급했기 때문. 시각적으로는 얇은 선이 예쁘지만, 클릭 판정 영역까지 그만큼 얇게 남겨두면 Fitts's Law 관점에서 조작 난이도가 급격히 올라간다.

**구현 냄새**:
- 리사이즈 핸들의 CSS `width`/`padding`이 시각적 두께(1~2px)와 동일하게 설정됨.
- `hitSlop`이나 투명 확장 영역(패딩된 pseudo-element, 확장된 클릭 레이어) 개념이 코드에 없음.
- 히트 영역이 마우스 전용으로만 설계되어 터치/트랙패드 사용성이 전혀 고려되지 않음.

**영향**:
반복적으로 사용하는 리사이즈/트리밍 조작에서 매번 "정확히 그 픽셀"을 맞춰야 하는 마찰이 누적되어 피로도가 커지고, 실수로 인접 요소를 잘못 클릭하는 2차 오조작까지 유발한다.

**권장**:
- 시각적 두께는 얇게 유지하되(1~2px 선), 실제 히트 영역은 최소 8~10px 폭의 투명 확장 레이어로 별도 구현한다.
- 커서가 히트 영역에 들어오면 즉시 리사이즈 커서(`col-resize` 등)로 바뀌게 하여 드래그 가능 영역을 미리 알린다.
- 핸들류 요소는 플랫폼 접근성 가이드라인의 최소 타겟 크기(예: 44×44px 권장, 최소 24×24px)를 참고해 여백을 확보한다.

**탐지**:
- Interaction: 리사이즈 경계/핸들에 커서를 올려 드래그가 시작되는 실제 픽셀 범위를 측정.
- 사용자 테스트: 특정 시야각/디스플레이 배율에서 드래그 시도 성공률 측정.

**Bitvue 판정**: 미정 — 2단계(저장소 감사)에서 채움

### UIX-INPUT-009: context menu만 존재하는 기능

**분류**: 발견 가능성 · **심각도**: High · **탐지**: Interaction

**사용자 목표**:
자주 쓰는 기능이라면 마우스 우클릭 메뉴를 열지 않고도(키보드 단축키나 툴바로) 접근할 수 있길 원한다.

**증상**:
- "이 블록으로 필터링", "참조 프레임 비교" 같은 핵심 기능이 오직 우클릭 컨텍스트 메뉴 안에만 존재한다.
- 같은 동작을 반복 수행하려면 매번 우클릭 → 메뉴 항목 찾기 → 클릭의 3단계를 거쳐야 한다.
- 해당 기능에 단축키가 아예 배정되어 있지 않아 익숙해져도 빨라질 방법이 없다.

**원인**:
새 기능을 추가할 때 "일단 우클릭 메뉴에 넣으면 어디든 노출된다"는 이유로 컨텍스트 메뉴를 1차 진입점이자 유일한 진입점으로 굳혀버렸기 때문. 툴바/단축키/커맨드 팔레트 같은 대체 진입점 설계를 후속 작업으로 미뤘다가 잊혀졌다.

**구현 냄새**:
- 기능 핸들러 함수가 컨텍스트 메뉴 컴포넌트 파일 안에서만 정의되고 다른 곳에서 import되지 않음.
- 단축키 레지스트리에 해당 액션의 항목이 없음.
- 툴바/메뉴바 어디에도 동일 기능으로 이어지는 버튼이 없음.

**영향**:
반복 작업의 속도가 "우클릭 → 메뉴 탐색"이라는 가장 느린 경로에 고정된다. 신규 사용자는 그 기능이 존재하는지조차 모를 수 있어(발견 가능성 저하) 기능이 있어도 안 쓰이는 결과로 이어진다.

**권장**:
- 컨텍스트 메뉴 항목은 항상 "이미 다른 곳(단축키, 툴바, 커맨드 팔레트)에도 존재하는 동작의 지름길"로 설계한다. 컨텍스트 메뉴를 유일한 진입점으로 두지 않는다.
- 자주 쓰이는 컨텍스트 메뉴 항목에는 단축키를 배정하고 메뉴 항목 옆에 그 단축키를 표시한다.
- 액션 핸들러를 메뉴 컴포넌트에서 분리해 여러 진입점(툴바, 단축키, 메뉴)이 동일 함수를 공유하도록 리팩터링한다.

**탐지**:
- 코드 스캔: 컨텍스트 메뉴 정의 파일에서만 참조되는 핸들러 함수(다른 곳에서 import되지 않는 함수) 목록화.
- 사용자 테스트: 우클릭을 금지한 상태로 전체 기능을 사용할 수 있는지 확인하는 시나리오.

### UIX-INPUT-010: hover에만 정보가 존재

**분류**: 정보 영속성 · **심각도**: Medium · **탐지**: Interaction

**사용자 목표**:
특정 블록/픽셀의 상세 정보(QP, MV, 참조 인덱스)를 확인한 뒤, 마우스를 다른 곳으로 옮기거나 스크린샷을 찍거나 동료에게 공유할 때도 그 정보가 유지되길 원한다.

**증상**:
- 블록에 마우스를 올려야만 툴팁으로 QP/MV 값이 뜨고, 마우스를 떼는 순간 정보가 사라진다.
- 여러 블록의 값을 비교하려면 마우스를 이 블록 저 블록으로 계속 오가야 하고 이전 값은 기억에 의존해야 한다.
- 스크린샷이나 화면 녹화로 값을 기록하려 하면 마우스 커서와 툴팁이 겹쳐 가려지거나, 캡처 순간 마우스가 움직여 정보가 사라진다.

**원인**:
"세부 정보 = hover 툴팁"이라는 가장 구현이 쉬운 패턴에 안주하고, 클릭으로 정보를 고정(pin)하거나 별도 인스펙터 패널에 영속적으로 표시하는 대안을 설계하지 않았기 때문.

**구현 냄새**:
- 블록 상세 정보 상태가 `hoveredBlock`이라는 단일 휘발성 state에만 연결됨.
- 클릭 시 별도의 "선택된 블록" 상태로 전환해 정보를 고정하는 로직이 없음.
- 인스펙터 패널(사이드바)이 hover 상태를 구독하지 않고 아예 존재하지 않음.

**영향**:
값을 비교, 기록, 공유해야 하는 분석 워크플로우에서 정보가 마우스 위치에 종속되어 사라지므로, 사용자가 결국 종이에 값을 받아적거나 여러 번 hover를 반복하는 비효율이 생긴다.

**권장**:
- 클릭(또는 특정 키)으로 블록을 "고정(pin)"하면 hover가 끝나도 정보가 유지되는 인스펙터 패널을 제공한다.
- 여러 블록을 순차적으로 고정해 나란히 비교할 수 있게 한다(멀티 핀).
- hover 툴팁은 빠른 미리보기용으로 유지하되, 영속적 정보는 항상 클릭 기반 고정 상태에 있도록 두 경로를 분리한다.

**탐지**:
- Interaction: 블록에 hover한 뒤 마우스를 치우고 정보가 화면 어딘가에 남아있는지 확인.
- 사용자 테스트: "두 블록의 QP 값을 비교해 보고하라"는 과제를 hover 전용 UI로 수행시켜 소요 시간/오류율 측정.

**Bitvue 판정**: 미정 — 2단계(저장소 감사)에서 채움

### UIX-INPUT-011: modifier key가 플랫폼별로 어긋남

**분류**: 크로스플랫폼 일관성 · **심각도**: High · **탐지**: Domain review

**사용자 목표**:
macOS/Windows/Linux 어느 플랫폼에서 실행하든, 각 OS의 관례에 맞는 modifier 키(Cmd vs Ctrl 등)로 동일한 동작을 일으키고 싶다.

**증상**:
- macOS 빌드인데도 단축키 표시와 실제 동작이 `Ctrl`로 하드코딩되어 있어 macOS 사용자가 기대하는 `Cmd`가 먹히지 않는다.
- 같은 Tauri 앱인데 메뉴바 단축키 표시는 `⌘Z`인데 실제 키 핸들러는 `event.ctrlKey`만 검사해 macOS Cmd 조합이 무시된다.
- Alt/Option 조합이 macOS에서 특수문자를 입력해버려(Option+숫자 등) 단축키가 아니라 엉뚱한 문자가 입력 필드에 들어간다.

**원인**:
단축키 로직을 한 플랫폼(대개 개발자의 주 개발 환경)에서만 테스트하고 `event.ctrlKey`/`event.metaKey`를 플랫폼 분기 없이 한쪽만 검사하도록 작성했기 때문. Tauri 앱은 네이티브 메뉴(OS별 관례를 따름)와 WebView 내부 로직(개발자가 임의로 작성)이 분리되어 있어 이 불일치가 더 쉽게 발생한다.

**구현 냄새**:
- 코드 전반에 `event.ctrlKey` 검사만 있고 `event.metaKey`(Cmd) 분기가 없거나 그 반대.
- 플랫폼 감지(`navigator.platform`, Tauri의 OS API) 없이 단축키 표시 문자열이 고정 텍스트(`Ctrl+S`)로 하드코딩됨.
- 네이티브 메뉴 정의(Rust/Tauri config)의 accelerator와 WebView 쪽 키 핸들러가 서로 다른 소스에서 독립적으로 정의됨.

**영향**:
macOS 사용자 비중이 높은 크리에이티브/미디어 툴 시장에서 이 결함은 "이식만 하고 제대로 다듬지 않은 앱"이라는 인상을 즉시 준다. 실제로 단축키가 전혀 동작하지 않거나 엉뚱한 문자가 입력되는 것은 치명적 사용성 결함이다.

**권장**:
- modifier 검사를 플랫폼 추상화 레이어(`isPrimaryModifier(event)` 같은 헬퍼)로 감싸 macOS에서는 `metaKey`, 그 외에는 `ctrlKey`를 검사하도록 단일화한다.
- 단축키 표시 문자열도 같은 추상화에서 플랫폼에 맞게 생성한다(`⌘`/`Ctrl` 자동 전환).
- 네이티브 메뉴 accelerator와 WebView 단축키 정의를 단일 소스(설정 테이블)에서 파생시켜 두 군데가 어긋나지 않게 한다.
- Bitvue의 경우 `docs/PARITY_CHECKLIST.md` Layer 4에 이미 정리된 단축키 표를 이 항목의 modifier 일관성 여부로 재검토할 가치가 있다(감사 시 상호 참조).

**탐지**:
- 크로스플랫폼 CI 매트릭스에서 동일 단축키 시나리오를 macOS/Windows/Linux 각각 실행해 결과 비교.
- 코드 스캔: `ctrlKey`와 `metaKey` 사용 빈도/위치 대조, 단일 추상화 함수 경유 여부 확인.

**Bitvue 판정**: 미정 — 2단계(저장소 감사)에서 채움

### UIX-INPUT-012: native menu와 WebView shortcut이 충돌

**분류**: Tauri 통합 · **심각도**: High · **탐지**: Interaction

**사용자 목표**:
OS 네이티브 메뉴바의 단축키와 앱 내부(WebView) 단축키가 서로를 가로채지 않고 예측 가능하게 동작하길 원한다.

**증상**:
- `Cmd+W`를 눌렀는데 WebView 내부의 "패널 닫기" 대신 OS가 윈도우 자체를 닫아버려 작업 중이던 세션이 사라진다.
- 네이티브 메뉴에 등록된 accelerator(`Cmd+F` = "찾기")와 WebView 내부 단축키(`Cmd+F` = "필터 적용")가 같은 키에 서로 다른 동작을 붙여놓아 둘 중 하나만 실행되고 어느 쪽이 실행될지 예측 불가능하다.
- 특정 단축키가 네이티브 레이어에서 먼저 소비되어 WebView의 `keydown` 이벤트까지 아예 도달하지 않는다.

**원인**:
Tauri 앱은 네이티브 메뉴(Rust 쪽, OS 레벨 accelerator)와 WebView 내부 JS 단축키 핸들러라는 두 개의 독립된 단축키 시스템을 갖는데, 이 둘을 하나의 팀/하나의 설계 문서 없이 각자 구현했기 때문. 이벤트 전파 순서(네이티브가 먼저 가로채는지, WebView가 먼저 받는지)를 검증하지 않고 각각 "당연히 동작하겠지"라고 가정했다.

**구현 냄새**:
- Rust 쪽 `tauri.conf.json`/메뉴 빌더의 accelerator 목록과 프런트엔드 단축키 레지스트리가 서로 다른 파일에 독립적으로 정의되어 있고 교차 검증 스크립트가 없음.
- 동일 키 조합이 두 레이어에 중복 등록되어 있는지 빌드 타임에 검사하는 로직이 없음.
- 네이티브 메뉴 항목 중 앱 로직과 무관한 OS 기본 동작(윈도우 닫기 등)이 그대로 남아 앱 내부 동작과 키가 겹침.

**영향**:
같은 키를 눌러도 언제는 원하는 동작이, 언제는 전혀 다른(때로는 파괴적인, 예: 창 닫힘) 동작이 발생하는 비결정적 경험은 파워유저 도구에서 특히 신뢰를 크게 훼손한다.

**권장**:
- 네이티브 메뉴 accelerator와 WebView 단축키를 단일 소스(공유 설정 테이블 또는 빌드 타임 코드 생성)에서 파생시켜 중복 등록을 원천 차단한다.
- 앱 특화 단축키와 충돌 가능성이 있는 OS 기본 메뉴 accelerator(창 닫기 등)는 의도적으로 재정의하거나 비활성화 여부를 명시적으로 결정한다.
- Tauri의 전역 단축키 API(global shortcut)와 WebView 로컬 리스너 중 어느 것이 "정본"인지 문서화하고 하나만 사용한다.

**탐지**:
- 빌드 타임 린트: 네이티브 accelerator 목록과 WebView 단축키 레지스트리를 파싱해 키 조합 교집합을 검출하는 스크립트.
- Interaction: 앱의 모든 화면에서 네이티브 메뉴에 등록된 단축키를 눌러 기대한 WebView 동작이 실행되는지 전수 확인.

**Bitvue 판정**: 미정 — 2단계(저장소 감사)에서 채움

### UIX-INPUT-013: 키 반복 입력이 backend 요청을 폭발시킴

**분류**: 입력 스로틀링 · **심각도**: Critical · **탐지**: Performance

**사용자 목표**:
방향키를 길게 눌러 빠르게 여러 프레임을 이동하고 싶을 뿐, 그 과정에서 앱이 멈추거나 응답이 밀리는 것을 원하지 않는다.

**증상**:
- 방향키를 1초만 눌러도 OS의 키 반복(auto-repeat)으로 초당 수십 개의 `keydown` 이벤트가 발생하고, 그때마다 프레임 디코드 IPC 요청이 Tauri backend로 날아간다.
- backend가 각 요청을 순차 처리하느라 큐가 쌓여, 키에서 손을 뗀 후에도 몇 초간 계속 프레임이 넘어가는 "입력 지연 누적" 현상이 발생한다.
- 극단적인 경우 backend 스레드가 포화되어 다른 IPC(오버레이 갱신, 저장 등) 응답까지 지연된다.

**원인**:
`keydown` 이벤트 핸들러가 디바운스/스로틀 없이 매 이벤트마다 즉시 backend 커맨드를 `invoke`하도록 구현되었기 때문. "한 번의 키 입력 = 한 번의 프레임 이동"이라는 단순 모델을 키 반복(auto-repeat)이 초당 수십 회 이벤트를 만든다는 사실과 함께 고려하지 않았다.

**구현 냄새**:
- `onKeyDown` 안에서 직접 `invoke('get_frame', ...)`을 호출하고 디바운스/스로틀 유틸리티를 거치지 않음.
- `event.repeat` 플래그를 검사해 반복 이벤트를 다르게 취급하는 로직이 없음.
- 프런트엔드에 이미 로드된 인접 프레임 캐시가 있어도 매 keydown마다 backend를 다시 호출함(캐시 우회).

**영향**:
파워유저가 가장 흔히 쓰는 제스처(방향키를 눌러 빠르게 훑기)가 오히려 앱을 가장 무겁게 만드는 역설이 발생한다. 응답 지연 누적은 "지금 누른 키가 언제 반영될지 예측할 수 없는" 상태를 만들어 조작감을 심각하게 해친다.

**권장**:
- `keydown` 핸들러에서 `event.repeat`을 검사해 반복 입력은 요청 빈도를 스로틀(예: 최신 요청만 유지하는 latest-wins 큐)하거나 로컬 인터벌 기반으로 재구성한다.
- 프레임 이동은 "목표 프레임 번호"를 프런트엔드 상태로 즉시 갱신(낙관적 UI)하고, backend 디코드 요청은 짧은 디바운스(예: 16~50ms) 후 최신 목표 프레임 하나만 요청한다.
- 인접 프레임 프리페치/캐시를 활용해 backend 왕복 없이 즉시 표시 가능한 프레임은 캐시에서 서빙한다.

**탐지**:
- Performance: 방향키를 2초간 길게 누른 뒤 backend에 실제로 도달한 IPC 요청 수와 최종 표시 프레임의 반영 지연을 측정.
- 코드 스캔: `onKeyDown` 핸들러 내부에서 `invoke`/`emit` 호출 직전에 디바운스/스로틀 래퍼가 존재하는지 확인.

**Bitvue 판정**: 미정 — 2단계(저장소 감사)에서 채움

### UIX-INPUT-014: undo 대상과 navigation history를 혼용

**분류**: 실행 취소 모델 · **심각도**: Medium · **탐지**: Interaction

**사용자 목표**:
Ctrl+Z(Undo)를 누르면 "내가 만든 변경(마커 추가, 주석, 필터 설정)"이 취소되길 원하고, 단순히 "내가 봤던 화면(프레임 이동, 선택 변경)"까지 되감기지는 않길 원한다 — 혹은 그 반대로 명확히 구분되길 원한다.

**증상**:
- 주석을 3개 추가한 뒤 Ctrl+Z를 눌렀더니 주석이 아니라 직전 프레임 이동이 취소되어 엉뚱한 프레임으로 돌아간다.
- 단순히 여러 프레임을 훑어봤을 뿐인데 그 각각의 "보기 이동"이 undo 스택에 쌓여, 정작 되돌리고 싶은 편집 동작에 도달하려면 undo를 수십 번 눌러야 한다.
- Redo(Ctrl+Shift+Z/Ctrl+Y)를 눌렀을 때도 편집 복원인지 화면 이동 복원인지 결과가 예측되지 않는다.

**원인**:
"사용자가 한 모든 행동"을 단일 undo 스택에 시간 순서로 push하는 하나의 커맨드 히스토리 시스템으로 구현했기 때문. 편집(데이터를 바꾸는 행위)과 내비게이션(단지 보는 위치를 바꾸는 행위)은 사용자의 멘탈 모델에서 명백히 다른 카테고리인데 이를 구분하지 않았다.

**구현 냄새**:
- undo 스택에 push되는 커맨드 타입에 "선택 변경", "프레임 이동" 같은 순수 내비게이션 액션과 "마커 추가", "주석 편집" 같은 데이터 변경 액션이 구분 없이 섞여 있음.
- 커맨드 패턴(Command 객체)에 `isUndoable`/`category` 같은 분류 필드가 없음.
- selection history(UIX-INPUT-006)와 edit history가 같은 자료구조를 공유함.

**영향**:
편집을 되돌리려는 사용자의 의도가 매번 좌절되며, "이 앱의 Undo는 못 믿겠다"는 인상을 준다. 결과적으로 사용자가 Undo 대신 수동으로 변경을 역으로 되짚어야 해서 실행 취소 기능의 존재 의미가 사라진다.

**권장**:
- 편집 히스토리(데이터 변경, Ctrl+Z 대상)와 내비게이션 히스토리(선택/화면 이동, Alt+←/→ 대상, UIX-INPUT-006 참고)를 처음부터 별개의 스택으로 분리한다.
- 커맨드 객체에 명확한 카테고리를 부여하고, undo 매니저는 편집 카테고리만 구독하도록 한다.
- 편집이 내비게이션을 동반하는 경우(예: "이 프레임에 마커 추가 후 다음 프레임으로 자동 이동")는 편집만 undo 스택에 기록하고 부수적 이동은 별도 처리한다.

**탐지**:
- 시나리오 테스트: 프레임 이동 5회 + 마커 추가 2회를 수행한 뒤 Ctrl+Z를 2번 눌러 마커 2개만 정확히 취소되는지 확인.
- 코드 스캔: undo 스택 push 호출부를 전수 조사해 내비게이션성 액션이 섞여 있는지 확인.

### UIX-INPUT-015: 기본 browser 동작이 분석기 조작과 충돌

**분류**: WebView 기본 동작 · **심각도**: High · **탐지**: Interaction

**사용자 목표**:
Backspace, Ctrl+F, Ctrl+P, 마우스 우클릭, 드래그 앤 드롭 같은 흔한 조작이 브라우저의 기본 동작(뒤로가기, 페이지 내 찾기, 인쇄, 브라우저 컨텍스트 메뉴)이 아니라 분석기 자체의 기능으로 동작하길 원한다.

**증상**:
- 입력 필드 밖에서 Backspace를 누르면 WebView가 브라우저 "뒤로가기"로 해석해 현재 세션(로드된 프레임, 선택 상태)이 통째로 날아간다.
- Ctrl+F를 눌러 신택스 엘리먼트를 검색하려 했더니 브라우저 기본 "페이지 내 찾기" 팝업이 뜬다.
- 프레임 이미지 영역을 드래그하면 (커스텀 드래그 핸들러 대신) 브라우저 기본 이미지 드래그 고스트가 나타나며 원치 않는 동작이 발생한다.
- 특정 영역을 우클릭하면 분석기 컨텍스트 메뉴 대신 WebView 기본 컨텍스트 메뉴("검사", "다시 로드")가 뜬다.
- 트랙패드의 핀치 줌이나 Ctrl+휠이 앱 내 zoom 대신 OS/브라우저 전체 화면 줌을 트리거한다.

**원인**:
Tauri WebView가 본질적으로 브라우저 엔진이라는 사실을 잊고, 브라우저의 기본 키/제스처 동작(뒤로가기, 찾기, 인쇄, 드래그, 컨텍스트 메뉴, 확대)을 명시적으로 `preventDefault()`하지 않았기 때문. 데스크톱 네이티브 앱처럼 보이지만 내부적으로는 여전히 웹 페이지의 기본 동작 세트를 상속하고 있다.

**구현 냄새**:
- 전역 `keydown`/`contextmenu`/`dragstart`/`wheel` 리스너에 `event.preventDefault()` 호출이 없거나 일부 케이스만 처리됨.
- Tauri 설정에서 WebView의 컨텍스트 메뉴/줌/드래그앤드롭 기본 동작을 비활성화하는 옵션을 사용하지 않음.
- 개발 중 항상 입력 필드에 포커스가 없는 상태로 Backspace/Ctrl+F 등을 테스트해본 적이 없음(테스트 시나리오 누락).

**영향**:
분석 세션 도중 브라우저의 "뒤로가기"가 실수로 발동해 로드된 시퀀스/선택 상태가 통째로 초기화되는 것은 데스크톱 도구에서 용납되기 어려운 데이터 손실급 결함이다. 그 외에도 반복적으로 브라우저 팝업이 끼어들면 "이건 진짜 데스크톱 앱이 아니라 어설픈 웹페이지"라는 인식을 준다.

**권장**:
- 앱 전역에서 브라우저 기본 동작과 충돌 가능한 키(Backspace, Ctrl+F/P/G, F3 등)와 제스처(드래그, 우클릭, 핀치줌)를 감사해 `preventDefault()`로 명시적으로 억제한다.
- Tauri 설정(`tauri.conf.json` 또는 WebView 빌더 옵션)에서 네이티브 컨텍스트 메뉴, 페이지 줌, 드래그앤드롭 기본 동작 비활성화 옵션을 활용한다.
- Backspace/뒤로가기류는 "입력 필드 밖에서" 라는 조건으로도 여전히 위험하므로, History API 네비게이션 자체를 앱 셸 레벨에서 잠근다(단일 페이지 앱으로 라우팅을 자체 관리).

**탐지**:
- Interaction: 입력 필드 밖에서 Backspace, Ctrl+F, Ctrl+P, 우클릭, 이미지 영역 드래그, 핀치줌을 전수 실행해 브라우저 기본 동작이 발동하는지 확인.
- 코드/설정 스캔: Tauri WebView 설정에서 컨텍스트 메뉴/줌 비활성화 플래그 존재 여부, 전역 리스너에서 `preventDefault` 커버리지 확인.

**Bitvue 판정**: 미정 — 2단계(저장소 감사)에서 채움

### UIX-INPUT-016: 단축키 발견 경로(치트시트/커맨드 팔레트) 부재

**분류**: 발견 가능성 · **심각도**: Medium · **탐지**: User test

**사용자 목표**:
어떤 단축키가 존재하는지 문서를 뒤지지 않고 앱 안에서 바로 찾아보거나, 이름으로 검색해 실행하고 싶다.

**증상**:
- `?`나 `F1`을 눌러도 단축키 목록이 뜨지 않는다. 단축키를 알려면 외부 문서나 소스 코드를 뒤져야 한다.
- 메뉴 항목 옆에 단축키가 표시되어 있지 않아, 메뉴를 열어봐도 단축키 존재 여부를 알 수 없다.
- 기능 이름은 아는데 정확한 키 조합이 기억나지 않을 때, 이름으로 검색해 즉시 실행할 수 있는 커맨드 팔레트(Ctrl+Shift+P류)가 없다.

**원인**:
단축키를 기능 구현에 곁들여 추가하면서 "그 단축키의 존재를 사용자가 어떻게 알게 되는가"라는 발견 가능성 문제를 별도 작업 항목으로 다루지 않았기 때문. 단축키 레지스트리(UIX-INPUT-002에서 다룬 중앙화)가 있어도 그것을 사용자에게 노출하는 UI가 따로 없다면 여전히 발견 불가능하다.

**구현 냄새**:
- 단축키 레지스트리는 존재하지만 그것을 렌더링하는 도움말/팔레트 컴포넌트가 없음.
- 메뉴 항목 컴포넌트가 라벨 문자열만 갖고 단축키 텍스트를 함께 렌더링하는 구조가 아님.
- 신규 단축키를 추가할 때 "도움말 화면에도 추가"하는 절차가 강제되지 않아 목록이 있어도 최신 상태와 어긋남.

**영향**:
단축키 자체는 잘 설계되어 있어도(UIX-INPUT-001~004 등을 다 해결했더라도) 사용자가 그 존재를 모르면 결국 마우스로만 조작하게 되어 앞선 개선의 효과가 실현되지 않는다. 신규 사용자의 숙련도 상승 곡선도 가팔라지지 못한다.

**권장**:
- `?` 또는 `F1`로 여는 단축키 치트시트 오버레이를 제공하고, 단축키 레지스트리에서 자동 생성해 항상 최신 상태를 유지한다.
- 이름 기반 검색 + 실행이 가능한 커맨드 팔레트(Ctrl/Cmd+Shift+P 관례)를 제공해 단축키를 몰라도 기능에 접근할 수 있게 한다.
- 메뉴/툴바 항목에 단축키 텍스트를 항상 병기한다.

**탐지**:
- User test: 신규 사용자에게 "다음 오류로 이동하는 방법을 찾아보라"는 과제를 주고 앱 내부 UI만으로 발견 가능한지 관찰.
- 코드 스캔: 단축키 레지스트리 항목 수와 도움말/팔레트 컴포넌트에 렌더링되는 항목 수를 대조해 누락 검출.

**Bitvue 판정**: 미정 — 2단계(저장소 감사)에서 채움

### UIX-INPUT-017: 멀티 패널 동기화 조작이 불가능

**분류**: 다중 뷰 조작 · **심각도**: High · **탐지**: Interaction

**사용자 목표**:
원본/디코드 비교 뷰나 다중 스트림 비교처럼 여러 패널이 동시에 열려 있을 때, 한 패널에서 스크럽·줌·팬 하면 나머지 패널도 함께 움직여 같은 지점을 비교하고 싶다(또는 명시적으로 독립시키고 싶다).

**증상**:
- 좌우 비교 뷰에서 왼쪽 패널을 스크럽하면 오른쪽 패널은 그대로 있어, 매번 두 패널을 각각 같은 프레임으로 수동 맞춰야 한다.
- 한 패널에서 확대한 배율/팬 위치가 다른 패널에 반영되지 않아 같은 영역을 비교하려면 양쪽에서 각각 줌/팬을 맞춰야 한다.
- 동기화 토글 자체가 없어서 "항상 따로 논다"거나 반대로 "끌 수 없이 항상 묶여 있다"는 극단만 존재한다.

**원인**:
각 패널(뷰어 인스턴스)이 자신의 줌/팬/현재 프레임 상태를 완전히 로컬 상태로 캡슐화해 구현했고, 여러 뷰어 인스턴스 간 상태를 공유/브로드캐스트하는 계층을 처음부터 두지 않았기 때문. "비교 보기"라는 유스케이스가 사후에 두 개의 독립 컴포넌트를 나란히 배치하는 방식으로만 구현되었다.

**구현 냄새**:
- 뷰어 컴포넌트가 `zoom`, `pan`, `currentFrame` 등을 각 인스턴스의 로컬 `useState`로만 관리하고 공유 스토어를 구독하지 않음.
- 여러 뷰어 인스턴스를 동시에 렌더링하는 비교 레이아웃 코드가 존재하지만, 인스턴스 간 통신 경로(context, store 구독)가 없음.
- 동기화 온/오프를 위한 상태나 UI 토글이 아예 모델링되어 있지 않음.

**영향**:
스트림 간 비교(원본 vs 인코딩 결과, 코덱 A vs 코덱 B)는 분석기의 핵심 유스케이스 중 하나인데, 수동 동기화 부담이 크면 사용자가 비교 기능 자체를 포기하고 각 스트림을 따로따로 열어 기억에 의존해 비교하게 된다.

**권장**:
- 줌/팬/현재 프레임 상태를 공유 스토어(또는 명시적 pub/sub 채널)로 승격하고, 동기화가 켜진 패널들은 이를 구독하도록 한다.
- 패널별로 동기화 참여 여부를 토글할 수 있는 UI(잠금 아이콘 등)를 제공해 필요할 때만 묶고 필요할 때 풀 수 있게 한다.
- 프레임 번호는 같지만 해상도/좌표계가 다른 스트림 비교를 고려해 동기화가 "인덱스 기준"인지 "정규화 좌표 기준"인지 명확히 정의한다.

**탐지**:
- Interaction: 비교 뷰를 열고 한쪽에서 줌/팬/스크럽을 수행한 뒤 다른 쪽에 반영되는지, 반영 여부를 토글할 수 있는지 확인.
- 코드 스캔: 뷰어 컴포넌트의 줌/팬/프레임 상태가 로컬 state인지 공유 store 구독인지 확인.

**Bitvue 판정**: 미정 — 2단계(저장소 감사)에서 채움

### UIX-INPUT-018: 정밀 좌표·수치를 직접 입력할 수 없음

**분류**: 정밀 입력 · **심각도**: Medium · **탐지**: Interaction

**사용자 목표**:
특정 매크로블록 좌표(예: `(64, 128)`)나 정확한 프레임 번호, 정확한 줌 배율(`400%`)을 마우스로 근사하지 않고 숫자로 직접 타이핑해 정확히 이동/설정하고 싶다.

**증상**:
- 프레임 번호를 알고 있어도 입력창이 없어 타임라인을 마우스로 근사 위치까지 드래그한 뒤 미세 조정을 반복해야 한다.
- 특정 CTU/블록 좌표로 이동하려면 화면을 확대한 뒤 마우스로 대략 그 위치를 클릭하는 수밖에 없어, 재현 가능한 정확한 위치 지정이 불가능하다.
- 줌 배율이 버튼 클릭(+/-) 단위로만 바뀌고 "정확히 200%로 맞추기"가 불가능해 스크린샷 비교나 재현 리포트 작성 시 매번 배율이 미세하게 달라진다.

**원인**:
좌표/수치 조작 UI를 슬라이더·드래그·버튼 같은 "상대적 조작" 위주로만 설계하고, "절대값을 아는 사용자를 위한 직접 입력" 경로를 별도 요구사항으로 다루지 않았기 때문. 마우스 기반 프로토타입에서 출발해 숫자 입력 필드를 나중에 추가할 여지를 남기지 않았다.

**구현 냄새**:
- 프레임 번호 표시가 읽기 전용 텍스트(`<span>`)로만 렌더링되고 편집 가능한 입력 요소로 전환되지 않음.
- 줌 컨트롤이 `zoomIn()`/`zoomOut()` 같은 상대 변경 함수만 있고 `setZoom(percentage: number)` 같은 절대 설정 API가 없음.
- 블록 좌표 선택이 픽셀 단위 마우스 좌표 → 블록 인덱스 변환 로직만 있고, 반대로 블록 인덱스를 입력받아 그 위치로 스크롤/선택하는 경로가 없음.

**영향**:
버그 리포트 작성, 회귀 테스트 재현, 팀 간 "정확히 이 프레임의 이 블록을 보라"는 커뮤니케이션이 전부 "대략 이쯤"이라는 부정확한 근사에 의존하게 된다. 정밀도가 생명인 분석 도구에서 정밀 입력 경로의 부재는 신뢰도를 직접적으로 깎아먹는다.

**권장**:
- 프레임 번호, 줌 배율, 좌표 등 이미 존재하는 모든 "표시용 숫자"는 클릭하면 편집 가능한 입력 필드로 전환되는 패턴(inline edit)을 기본으로 제공한다.
- 절대값 설정 API(`goToFrame(n)`, `setZoom(percent)`, `selectBlockAt(x, y)`)를 상대 조작 API와 별도로 항상 노출한다.
- 입력값 검증(범위를 벗어난 프레임 번호, 음수 좌표 등)과 즉시 피드백을 함께 제공한다.

**탐지**:
- Interaction: 프레임 번호/줌 배율/좌표 표시 요소를 클릭했을 때 편집 가능한 입력으로 바뀌는지 전수 확인.
- User test: "정확히 프레임 4231, 블록 (96, 64)로 이동하라"는 과제를 마우스만으로 수행시켜 소요 시간과 정확도 측정.
