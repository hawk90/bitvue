# Anti-Pattern Catalog — UIX_TIMELINE: Timeline 안티패턴

이 문서는 더 큰 안티패턴 카탈로그의 일부입니다(전체 목록은 별도로 작성 중인 `docs/anti-patterns/INDEX.md` 참고). UI/UX+Tauri Phase 3 웨이브에 속하며, Bitvue의 프레임 크기/QP/GOP 타임라인 — 수백만 프레임, VFR 콘텐츠, 스크러빙을 다뤄야 하는 핵심 탐색 컴포넌트 — 에서 반복적으로 나타나는 사용성·성능·데이터 신뢰성 문제를 다룬다. 본 파일은 일반적이고 도메인 정보에 기반한 참고 자료이며 특정 저장소 감사 결과가 아니다.

---

### UIX-TIME-001: 픽셀 위치를 frame index에 직접 매핑

**분류**: 좌표 변환 · **심각도**: Critical · **탐지**: Code

**사용자 목표**:
타임라인 위 특정 x 좌표를 클릭해 원하는 프레임으로 정확히 이동하고 싶다.

**증상**:
- 줌 레벨이나 VFR 구간에서 클릭한 위치와 실제로 이동한 프레임이 다르다.
- 타임라인 폭을 리사이즈하거나 창 크기를 바꾸면 같은 지점을 클릭해도 다른 프레임으로 이동한다.
- 프레임 수가 픽셀 폭보다 많아지면(수백만 프레임) `pixel = frame_index` 같은 1:1 가정이 깨지며 마지막 구간이 잘리거나 클릭 불가 영역이 생긴다.

**원인**:
좌표 변환을 "픽셀 1개 = 프레임 1개" 또는 `px * scale = frame index` 같은 선형 고정 매핑으로 하드코딩하고, viewport(줌/스크롤 오프셋), 컨테이너 폭 변화, VFR로 인한 비균등 프레임 밀도를 변환식에 반영하지 않는다.

**구현 냄새**:
- `frameIndex = Math.floor(x / pixelsPerFrame)` 같은 단순 나눗셈이 이벤트 핸들러에 인라인으로 박혀 있다.
- 좌표↔프레임 변환 함수가 하나로 통일되어 있지 않고 클릭, 드래그, 렌더링마다 각자 계산한다.
- 컨테이너 리사이즈나 DPI 변경 이벤트를 구독하지 않는다.

**영향**:
사용자가 의도한 프레임과 다른 프레임이 열려 분석 결과를 잘못된 프레임에 대해 내리게 된다. 특히 에러 프레임을 찾아 클릭했는데 옆 프레임이 열리는 경우 디버깅 신뢰도가 크게 떨어진다.

**권장**:
- viewport(시작 인덱스, 보이는 프레임 수, 컨테이너 픽셀 폭)를 단일 소스로 하는 순수 함수 `pixelToFrame(x, viewport)` / `frameToPixel(index, viewport)`를 만들고 모든 인터랙션이 이를 통해서만 좌표 변환하게 한다.
- VFR 등 비균등 간격에서는 프레임 인덱스가 아니라 누적 시간/누적 오프셋 기반 이진 탐색으로 변환한다.
- 컨테이너 리사이즈, DPI 변경 시 viewport를 재계산하고 변환 함수를 재바인딩한다.

**탐지**:
- 시나리오 테스트: 창을 리사이즈한 뒤 같은 화면 좌표를 클릭해 결과 프레임이 바뀌는지 확인.
- 좌표 변환 로직이 여러 파일에 중복 존재하는지 grep.

**Bitvue 판정**: N/A (2026-08-18 재감사, 직전 커밋에서 수정됨) — 가장 최근 커밋 `f9e672e`("make Timeline bar strip responsive")가 이 항목을 정확히 겨냥해 고쳤다. `getFrameIndexFromEvent`/드래그 핸들러는 이제 `document.elementFromPoint(...).closest(".timeline-thumb")`로 실제 클릭된 DOM 엘리먼트의 `data-frame-index`를 직접 읽는 `frameIndexFromPoint`를 우선 사용하고(frontend/components/Timeline.tsx:132-176, 209-176 부근), 순수 `percent * frames.length` 나눗셈은 `elementFromPoint`가 없는 jsdom 테스트 환경에서만 쓰이는 폴백으로 강등됐다(코드 주석이 이 설계를 명시). CSS도 `.timeline-thumb{width:2px}` 고정폭 대신 `flex:1 1 0; min-width:2px; max-width:14px`로 grow-to-fill하고, 다 채워도 안 들어가면 `overflow-x:auto`로 스크롤하도록 바뀌었다(Timeline.css:100-145) — 이전 버전에서 존재했던 "리사이즈 시 같은 좌표가 다른 프레임을 가리키는" 실패 유형은 더 이상 재현되지 않는다. VFR 이진탐색(누적시간 기반)은 여전히 없지만 그건 UIX-TIME-002가 다루는 별개 항목이다.

### UIX-TIME-002: VFR인데 프레임을 동일 간격으로 배치

**분류**: 시간 표현 · **심각도**: High · **탐지**: Domain review

**사용자 목표**:
프레임 재생 시점의 실제 시간 간격을 시각적으로 신뢰할 수 있어야 한다.

**증상**:
- 프레임레이트가 30→15→60fps로 바뀌는 스트림에서도 타임라인 위 프레임 간 픽셀 간격이 항상 동일하다.
- 실제로는 시간상 몰려있는(짧은 간격) 프레임 구간과 듬성듬성한(긴 간격) 구간이 타임라인에서 똑같이 보인다.
- "시간 축으로 이 두 마커 사이는 몇 초인가"라는 질문에 화면만으로는 답할 수 없다.

**원인**:
타임라인을 "프레임 개수" 축으로 설계하고 PTS(presentation timestamp)를 렌더링에 반영하지 않는다. CFR을 가정한 초기 구현이 VFR 콘텐츠(가변 프레임레이트 녹화, 편집된 스트림, 프레임 드롭이 있는 스트림)에 그대로 재사용된 결과다.

**구현 냄새**:
- x좌표 계산에 `frame_index * constant_width`만 등장하고 PTS/duration 필드가 어디에도 쓰이지 않는다.
- 프레임 메타데이터에 duration이나 PTS delta가 존재하는데 타임라인 컴포넌트가 이를 prop으로 받지 않는다.

**영향**:
사용자가 "이 구간에서 프레임레이트가 떨어졌다"는 것을 타임라인만 보고는 알아챌 수 없어, 성능 저하나 인코딩 이상을 놓친다. 시간 기반 편집/구간 선택(예: "이 3초 구간")도 부정확해진다.

**권장**:
- 기본 모드를 "frame index 축"과 "presentation time 축" 두 가지로 제공하고 사용자가 전환 가능하게 한다.
- time 축 모드에서는 프레임 폭을 duration에 비례하게 그리거나, 최소한 프레임 밀도가 급변하는 구간에 시각적 신호(음영, 압축 표시)를 준다.
- CFR 가정이 깨지는 구간(fps 변화, 프레임 드롭)을 별도 마커로 표시한다.

**탐지**:
- 도메인 리뷰: VFR 샘플(가변 프레임레이트 녹화본, 캡처 도중 fps가 바뀐 스트림)을 로드해 타임라인 간격과 실제 PTS 간격을 비교.
- 코드에서 PTS/timestamp 필드 사용 여부 검색.

**Bitvue 판정**: Confirmed (2026-08-18 재감사, 경로 갱신 — Tauri 제거로 원 인용문 `src-tauri/src/commands/file.rs`는 더 이상 존재하지 않음) — 현재 프레임 데이터 경로는 `bitvue-sidecar`의 `get_frames_chunk`가 `UnitNode`를 그대로 직렬화해 보내는 것인데(crates/bitvue-sidecar/src/main.rs:756-798), `UnitNode`(crates/bitvue-engine/src/stream_state.rs:197-260)에는 `pts`/`dts`만 있고 `duration` 필드 자체가 없다. `Timeline.tsx`/`TimelineThumbnails.tsx`는 `frame.pts`를 전혀 참조하지 않고 `.timeline-thumb{flex:1 1 0}`으로 프레임을 항상 동일 폭으로 배치한다(frontend/components/Timeline.css:142-147). 참고: `bitvue-engine::frame_identity::TimelineMapper` 기반의 실제 PTS 정렬 타임라인(`get_timeline` IPC, crates/bitvue-indexer/src/lib.rs:247)이 최근 새로 만들어졌지만 "no live UI consumer yet"(frontend/services/electronBridgeService.ts:794)로 Timeline 컴포넌트는 아직 이를 쓰지 않는다.

### UIX-TIME-003: decode order와 presentation order 혼용

**분류**: 시간 표현 · **심각도**: Critical · **탐지**: Domain review

**사용자 목표**:
타임라인에서 프레임을 선택하면 화면에 보이는 순서(재생 순서)대로 분석하고 싶다.

**증상**:
- B프레임이 있는 GOP 구조에서 타임라인 순서가 재생 순서와 어긋난다(예: I P B B 대신 디코드 순서인 I B B P가 그대로 노출).
- 타임라인 스크럽 시 화면이 순간적으로 시간이 거꾸로 가는 것처럼 보인다.
- "N번째 프레임"이라는 표현이 패널마다 다른 의미(decode index vs display index)로 쓰여 사용자가 다른 패널과 대조할 때 프레임이 어긋난다.

**원인**:
디코더 내부적으로는 decode order(참조 관계에 따른 처리 순서)로 프레임이 나오는데, 이를 그대로 배열 인덱스로 사용해 타임라인에 렌더링한다. presentation order로의 재정렬(PTS 기준 정렬 또는 POC/output order 사용)이 누락되어 있다.

**구현 냄새**:
- 프레임 리스트를 만들 때 디코더가 emit하는 순서를 그대로 push하고 별도 정렬 단계가 없다.
- "frame index"라는 이름의 변수가 코드베이스 여러 곳에서 decode order와 display order 두 가지 의미로 섞여 쓰인다.
- POC(picture order count) 또는 PTS 필드가 파싱은 되지만 타임라인 정렬에는 쓰이지 않는다.

**영향**:
프레임 순서에 대한 사용자의 심성 모델이 실제 재생과 어긋나 GOP 구조 분석, reference 관계 추적, 화질 저하 구간 특정이 모두 신뢰할 수 없게 된다. B프레임 비중이 높은 최신 코덱(HEVC/AV1)일수록 문제가 심각해진다.

**권장**:
- 타임라인의 기본 표시 순서는 반드시 presentation order(PTS/POC 정렬)로 하고, decode order는 별도 뷰(예: GOP 구조 다이어그램)에서만 명시적으로 보여준다.
- 두 순서를 같이 다뤄야 하는 화면(참조 프레임 하이라이트 등)에서는 축 자체에 "Decode Order"/"Display Order" 레이블을 명확히 붙인다.
- 내부 자료구조에서 `decodeIndex`와 `displayIndex`를 별개 필드로 명명해 혼용을 원천 차단한다.

**탐지**:
- 도메인 리뷰: B프레임이 많은 GOP 구조(예: hierarchical B)를 가진 샘플로 타임라인 순서와 실제 재생 순서를 프레임 단위로 대조.
- 코드에서 정렬 없이 디코더 output을 그대로 리스트에 사용하는 경로 확인.

**Bitvue 판정**: Confirmed (2026-08-18 재감사, 경로 갱신) — 원 인용 `src-tauri/src/commands/file.rs`는 Tauri 제거로 사라졌다. 현재도 동일한 문제가 다른 형태로 존재: Timeline이 실제로 소비하는 `get_frames_chunk`(crates/bitvue-sidecar/src/main.rs:756)가 반환하는 `UnitNode`(crates/bitvue-engine/src/stream_state.rs:197-260)에는 `display_order`/`coding_order`/`poc` 필드가 아예 없고 `frame_index`(디코드/유닛 순서) 하나뿐이다. 프론트엔드 `FrameInfo` 타입(frontend/types/video.ts:128-131)은 `poc?`/`display_order?`/`coding_order?`를 옵셔널로 선언해두었지만 wire에서 채워주는 값이 없어 항상 undefined다. **흥미로운 발견**: `bitvue-engine::frame_identity::TimelineMapper`(POC/PTS 기반 실제 재정렬 로직, decode↔display 분리를 정확히 이 항목이 요구하는 방식으로 구현)가 최근 `bitvue-indexer::get_timeline`(crates/bitvue-indexer/src/lib.rs:247, AV1 전용)을 통해 처음으로 실제 호출자를 얻었으나(주석: "had zero production callers before this"), `getTimeline` IPC는 "no live UI consumer yet"(frontend/services/electronBridgeService.ts:794) — 즉 올바른 수정 재료는 백엔드에 이미 있는데 Timeline UI에는 아직 배선되지 않았다.

### UIX-TIME-004: zoom해도 데이터 해상도가 그대로

**분류**: 렌더링/데이터 해상도 · **심각도**: High · **탐지**: Interaction

**사용자 목표**:
타임라인을 확대하면 더 세밀한 프레임 단위 정보를 보고 싶다.

**증상**:
- 전체 스트림 보기에서 다운샘플링된 요약값(예: 100프레임당 평균 QP)을 쓰다가, 줌인해도 여전히 같은 요약값이 늘어나 보일 뿐 개별 프레임 값으로 바뀌지 않는다.
- 최대로 확대해도 뭉개진 블록 형태 그대로이고 프레임 하나하나의 실제 값이 안 보인다.
- 반대로 줌아웃해도 원본 해상도로 수백만 개 포인트를 그대로 그려 성능이 급격히 나빠지는 반대 증상도 같은 근본 원인에서 나온다.

**원인**:
다중 해상도(LOD, level-of-detail) 데이터 파이프라인이 없고 단일 해상도(원본 또는 고정 다운샘플)만 준비되어 있어, 줌 레벨에 따라 적절한 세밀도로 전환하는 로직이 없다.

**구현 냄새**:
- 다운샘플링이 데이터 로드 시점에 한 번만 수행되고 줌 레벨과 무관한 고정 버킷 크기를 쓴다.
- "zoom" 이벤트 핸들러가 CSS transform/scale만 바꿀 뿐 실제 데이터 재요청·재계산을 트리거하지 않는다.

**영향**:
사용자가 이상 구간을 발견해 확대해도 원인을 특정할 세밀한 정보를 얻지 못해 분석이 막힌다. 반대의 경우 전체 개요를 볼 때조차 과도한 렌더링 비용을 치른다.

**권장**:
- 줌 레벨 구간별로 다른 해상도의 데이터를 준비하는 LOD 피라미드(예: 1x, 10x, 100x, 1000x 다운샘플)를 구성하고 뷰포트가 바뀔 때마다 적절한 레벨을 선택한다.
- 최대 줌(1프레임=여러 픽셀)에서는 항상 원본 해상도로 전환되도록 보장한다.
- 다운샘플 시 평균뿐 아니라 min/max(피크 보존)도 함께 저장해 확대 전에도 스파이크가 뭉개지지 않게 한다.

**탐지**:
- 인터랙션 테스트: 이상값(급격한 프레임 크기 스파이크)이 있는 구간을 최대로 줌인했을 때 실제 개별 프레임 값이 표시되는지 확인.
- 줌 레벨 변경 시 네트워크/IPC 요청이나 재계산이 트리거되는지 프로파일링.

### UIX-TIME-005: 수백만 프레임을 DOM element로 생성

**분류**: 성능/렌더링 아키텍처 · **심각도**: Critical · **탐지**: Performance

**사용자 목표**:
수백만 프레임짜리 긴 스트림도 타임라인이 버벅이지 않고 즉시 반응해야 한다.

**증상**:
- 긴 스트림을 로드하면 타임라인 렌더링에 수 초~수십 초가 걸리거나 탭이 멈춘다.
- 스크롤/줌 시 프레임 드롭이 심하고 브라우저 개발자 도구의 DOM 노드 수가 수백만에 달한다.
- 메모리 사용량이 스트림 길이에 선형으로 증가해 긴 스트림에서 OOM에 가까워진다.

**원인**:
타임라인 마커/틱/프레임 셀 하나하나를 React 컴포넌트나 개별 DOM element로 매핑해 렌더링한다. 프레임 수가 적을 때는 문제없지만 수백만 규모에서는 DOM 자체가 병목이 된다.

**구현 냄새**:
- `frames.map(f => <div key={f.index} .../>)` 형태로 프레임 배열 전체를 순회하며 엘리먼트를 생성한다.
- 가상화(virtualization) 라이브러리나 canvas 렌더링이 전혀 쓰이지 않는다.
- 보이지 않는(뷰포트 밖) 프레임까지 DOM에 마운트되어 있다.

**영향**:
대용량 스트림(방송 아카이브, 장시간 캡처)을 다루는 전문 사용자에게 도구 자체가 사용 불가능해진다. 이는 애초에 Bitvue 같은 도구가 존재하는 이유(대용량 스트림 분석)를 정면으로 배반한다.

**권장**:
- 타임라인을 canvas(또는 WebGL) 기반으로 렌더링해 프레임 수와 무관하게 화면에 그려지는 픽셀 수에만 비례하는 비용을 갖게 한다.
- canvas가 과하다고 판단되면 최소한 뷰포트 가상화(현재 보이는 구간 + 여유분만 DOM/캔버스에 그림)를 적용한다.
- 렌더링 비용을 "총 프레임 수"가 아니라 "화면에 보이는 프레임 수"에 종속시키는 것이 핵심 원칙임을 아키텍처 문서에 명시한다.

**탐지**:
- 성능 테스트: 100만 프레임급 합성 데이터로 초기 렌더링 시간, 스크롤 FPS, DOM 노드 수를 측정.
- 프레임 수를 10배씩 늘려가며 렌더링 시간이 선형/초선형으로 증가하는지 벤치마크.

**Bitvue 판정**: Confirmed (2026-08-18 재감사, 경로 갱신 — `Filmstrip/views/TimelineView.tsx`는 최근 리팩터로 삭제됨) — `TimelineThumbnails.tsx` 90행이 `frames.map(...)`로 프레임마다 `<div className="timeline-thumb">`를 무조건 생성하며 가상화 코드가 전혀 없다(grep 결과: 이 파일에 virtualize/react-window 등 없음). `TimelineThumbnails`는 이제 `Filmstrip`이 아니라 최상단 `Timeline.tsx`(항상 마운트되는 하단 스크러버 바로 보임, frontend/components/Timeline.tsx:11)의 직속 자식이며, `Filmstrip.tsx`가 별도로 `VIRTUALIZATION_THRESHOLD=200`(constants/ui.ts:172) 기준 `VirtualizedThumbnailsView`를 조건부로 쓰는 것(Filmstrip.tsx:64, 255)과 대조적으로 이쪽엔 프레임 수 상한 가드가 전혀 없다.

**탐지**:

### UIX-TIME-007: marker가 겹쳐 의미를 읽을 수 없음

**분류**: 정보 밀도/가독성 · **심각도**: Medium · **탐지**: Visual

**사용자 목표**:
줌아웃 상태에서도 어디에 어떤 종류의 이벤트(씬 전환/에러/GOP 경계)가 있는지 파악하고 싶다.

**증상**:
- 축소된 타임라인에서 마커들이 픽셀 단위로 겹쳐 단색 얼룩처럼 보인다.

**영향**:

**권장**:
- 마커 밀도가 임계값을 넘으면 개별 아이콘 대신 "N개 이벤트" 클러스터 배지로 집계 표시하고, 클릭/줌인 시 개별 마커로 분해한다.
- 겹침이 발생하는 줌 레벨에서는 마커 종류별로 레인(수평 트랙)을 분리해 동시에 여러 카테고리를 보여준다.
- 툴팁/호버는 해당 위치에 겹친 모든 마커 목록을 나열한다.

**탐지**:
- 시각 검수: 마커 밀도가 높은 구간을 축소해 겹침·가림 여부 스크린샷 비교.
- 동일 좌표에 서로 다른 타입의 마커 2개 이상을 배치한 합성 데이터로 확인.

**Bitvue 판정**: N/A — UIX-TIME-006과 동일한 이유로 씬 전환/에러/GOP 경계 마커 시스템 자체가 아직 구현되어 있지 않다(frame-type 색상 칠만 존재).

### UIX-TIME-008: scrub 중 모든 프레임을 정밀 분석

**분류**: 성능/인터랙션 · **심각도**: Critical · **탐지**: Performance

**사용자 목표**:
타임라인을 드래그해 훑어보는(scrub) 동안 부드럽게 미리보기가 따라와야 한다.

**증상**:
- 스크럽바를 드래그하면 마우스 이동보다 화면 갱신이 한참 뒤처진다.
- 드래그를 멈춰야만 비로소 화면이 따라잡히고, 그 사이 UI가 얼어붙은 것처럼 보인다.
- CPU/GPU 사용률이 스크럽 중 급격히 치솟는다.

**원인**:
스크럽 이벤트(마우스 이동)마다 지나간 모든 프레임에 대해 전체 디코드/파싱/오버레이 계산을 동기적으로 수행한다. 사람이 스크럽할 때 실제로 필요한 것은 "현재 위치의 저해상도 미리보기"뿐인데 정밀 분석 파이프라인을 그대로 재사용한다.

- 마우스 move 핸들러가 디바운스/스로틀 없이 매 이벤트마다 정밀 디코드 함수를 호출한다.
- "미리보기용 저해상도 경로"와 "정밀 분석 경로"가 별도로 존재하지 않고 하나의 함수만 있다.

**영향**:
도구가 반응성을 잃어 스크럽이라는 핵심 탐색 조작 자체가 무용해진다. 사용자는 결국 스크럽 대신 페이지 단위 점프만 쓰게 되어 세밀 탐색 워크플로가 망가진다.

**권장**:
- 스크럽 중에는 저해상도 썸네일/캐시된 요약 정보만 즉시 표시하고, 드래그가 멈춘 뒤(또는 일정 시간 정지 후) 정밀 분석을 지연 실행한다.
- 스크럽 이벤트를 requestAnimationFrame 또는 스로틀로 묶어 초당 갱신 횟수를 제한한다.
- 진행 중인 정밀 분석 요청은 새 스크럽 위치가 들어오면 즉시 취소(cancel)한다.

**탐지**:
- 성능 테스트: 빠른 드래그 스크럽 동안 프레임 타임/입력 지연을 측정.
- 스크럽 중 호출되는 함수 프로파일링으로 정밀 디코드 경로가 매 이벤트마다 실행되는지 확인.

**Bitvue 판정**: N/A — `Timeline.tsx`의 `handleDragMove`(140-160행)는 드래그 중 로컬 상태(`highlightedFrameIndex`, `hoverPosition`)만 갱신하고, `setFrameSelection`(다른 패널에 전파되는 유일한 트리거)은 `handleDragUp`(162-171행)에서 마우스업 시점에만 호출한다. 즉 스크럽 도중 매 이벤트마다 정밀 분석을 재실행하지 않는다.

### UIX-TIME-009: 재생 head와 선택 frame을 동일하게 취급

**분류**: 상태 모델 · **심각도**: Medium · **탐지**: Interaction

**사용자 목표**:
재생 중인 위치와 내가 분석을 위해 선택해 둔 프레임을 별개로 유지하고 싶다.

**증상**:
- 재생을 누르면 이전에 클릭해 자세히 보고 있던 프레임(오버레이, hex view 등)이 재생 위치로 강제로 바뀐다.
- 재생을 멈추고 다시 특정 프레임을 보려면 처음부터 다시 탐색해야 한다.
- 재생 중에 다른 프레임을 클릭해 비교하려 해도 재생 head가 계속 선택을 덮어써 비교가 불가능하다.

**원인**:
"현재 표시 중인 프레임"이라는 단일 상태 변수로 재생 위치와 사용자 선택을 함께 관리한다. 재생(자동 진행)과 선택(사용자 의도)이 개념적으로 다른 상태임을 반영하지 않는다.

**구현 냄새**:
- 전역 상태에 `currentFrame` 하나만 있고 `playheadFrame`과 `selectedFrame`이 분리되어 있지 않다.
- 재생 tick 콜백이 선택 상태를 담당하는 setter를 직접 호출한다.

**영향**:
재생하면서 특정 프레임을 계속 참조하거나 비교하는(예: "이 프레임과 재생되는 프레임 비교") 워크플로가 원천적으로 불가능해져 분석 효율이 떨어진다.

**권장**:
- `playheadPosition`(재생 진행 위치)과 `selectedFrame`(사용자가 분석 대상으로 지정한 프레임)을 별개 상태로 분리한다.
- 기본 동작은 재생 시 선택도 따라가되(follow 모드), 사용자가 다른 프레임을 클릭하면 자동으로 follow를 해제하고 선택을 고정한다.
- UI에 재생 head(가는 선)와 선택 프레임(강조 박스)을 시각적으로 구분해 표시한다.

**탐지**:

### UIX-TIME-014: thumbnail이 늦게 도착하며 위치가 흔들림

**분류**: 비동기 로딩/레이아웃 안정성 · **심각도**: Medium · **탐지**: Visual

**사용자 목표**:
타임라인을 스크롤하는 동안 썸네일이 채워지면서도 레이아웃이 흔들리지 않아야 한다.

**증상**:
- 썸네일이 비동기로 로드되며 도착하는 순서대로 자리를 차지해, 먼저 도착한 썸네일 때문에 다른 요소가 밀리거나 재배치된다.
- 스크롤 중 이미 봤던 위치의 썸네일이 나중에 도착한 다른 크기의 이미지로 교체되며 깜빡인다(레이아웃 시프트).
- 빠르게 스크롤하면 요청이 밀려 엉뚱한 위치에 이전 스크롤의 썸네일이 표시된다(레이스 컨디션).

**원인**:
썸네일 슬롯의 크기/위치를 로딩 완료 후에야 확정하고, 로딩 중 placeholder 예약이 없다. 또한 비동기 썸네일 요청에 취소/순서 보장이 없어 오래된 요청의 응답이 최신 뷰를 덮어쓴다.

**구현 냄새**:
- 썸네일 `<img>`에 명시적 width/height(또는 aspect-ratio)가 없어 로드 완료 시점에 실제 크기로 리플로우가 발생한다.
- 썸네일 fetch 요청에 요청 ID나 AbortController가 없어 오래된 응답도 그대로 렌더링에 반영된다.

**영향**:
시각적 안정성이 떨어져 사용자가 스크롤하며 훑어보는 탐색 경험이 산만해지고, 잘못된 위치에 잘못된 썸네일이 표시되면 프레임을 오인할 위험도 있다.

**권장**:
- 썸네일 슬롯은 로딩 여부와 무관하게 고정 크기의 placeholder(스켈레톤)를 먼저 예약하고, 이미지는 그 안에서만 교체되게 한다.
- 비동기 요청에 요청 세대(generation) 번호를 부여해, 뷰포트가 바뀌어 무효화된 요청의 응답은 무시(취소)한다.
- 빠른 스크롤 중에는 썸네일 요청 자체를 스로틀/디바운스해 불필요한 요청 폭주를 막는다.

**탐지**:
- 시각 검수: 느린 네트워크/디스크 조건을 시뮬레이션해 스크롤 중 레이아웃 시프트가 발생하는지 확인.
- 빠른 스크롤 후 정지했을 때 표시된 썸네일이 현재 위치와 실제로 일치하는지 확인.

**Bitvue 판정**: Suspected — 썸네일 요청(useFilmstripState.ts의 `loadThumbnails`)에 AbortController/요청 세대 번호가 전혀 없다(grep 확인). 다만 결과가 `Map<frameIndex, dataUrl>`에 인덱스 키로 저장되므로(62-101행) 응답 순서가 뒤바뀌어도 잘못된 위치에 잘못된 썸네일이 붙는 레이스는 구조적으로 발생하기 어렵다. 플레이스홀더가 로딩 중에도 동일 크기 슬롯을 차지하는지는 CSS까지 확인하지 못해 레이아웃 시프트 여부는 미확정.

### UIX-TIME-015: 시간 단위와 frame 단위를 전환할 수 없음

**분류**: 정보 표현 · **심각도**: Medium · **탐지**: User test

**사용자 목표**:
상황에 따라 "몇 번째 프레임인지"와 "몇 분 몇 초 지점인지"를 자유롭게 오가며 확인하고 싶다.

**증상**:
- 타임라인 눈금이 항상 프레임 번호로만 표시되어, 방송 타임코드나 사용자가 다른 도구(편집기, 플레이어)에서 확인한 "몇 분 몇 초"와 대조하기 어렵다.
- 반대로 시간만 표시되는 경우 프레임 단위 정밀 조작(1프레임씩 이동)을 하는 사용자가 지금 몇 번째 프레임인지 알 수 없다.
- 두 단위 사이를 변환하려면 fps로 암산해야 한다.

**원인**:
타임라인 축 레이블과 상태 표시 로직이 프레임 인덱스 또는 시간 중 하나만 지원하도록 고정 구현되어 있고, 전환 토글이나 병기 표시가 설계에 없다.

**구현 냄새**:
- 축 레이블 렌더링 함수가 `frameIndex.toString()`만 반환하거나 반대로 시간 문자열만 반환하며 매개변수로 단위를 받지 않는다.
- fps 정보가 있음에도 시간 변환 유틸리티가 UI 레이어에 노출되어 있지 않다.

**영향**:
방송/QC 워크플로에서는 타임코드가, 코덱 분석 워크플로에서는 프레임 번호가 표준 단위인데, 한쪽만 지원하면 사용자가 매번 수동 변환을 해야 해 실수와 피로가 누적된다.

**권장**:
- 축 레이블/상태 바에 단위 전환 토글(프레임 ↔ HH:MM:SS:FF 타임코드 ↔ 초)을 제공한다.
- 가능하면 주 단위와 보조 단위를 병기(예: "frame 12,345 (00:08:14.500)")해 전환 없이도 양쪽 정보를 노출한다.
- VFR 구간에서는 시간→프레임 변환이 근사치일 수 있음을 표시(예: "~" 접두)한다.

**탐지**:
- 사용자 테스트: 방송/QC 배경의 사용자에게 특정 타임코드의 프레임을 찾아보게 하고 소요 시간과 실수를 관찰.

**Bitvue 판정**: Confirmed — `TimelineHeader.tsx`는 `{currentFrame + 1} / {totalFrames}`(프레임 번호)만 렌더링하며(19-27행), 코드베이스 전체에서 Timeline/Filmstrip 쪽에 타임코드 포맷팅이나 단위 전환 토글을 찾을 수 없었다(grep 결과 없음).

### UIX-TIME-016: keyboard 탐색이 없음

**분류**: 접근성/인터랙션 · **심각도**: High · **탐지**: Interaction

**사용자 목표**:
마우스를 쓰지 않고도 키보드만으로 프레임 단위/구간 단위 탐색을 빠르게 하고 싶다.

**증상**:
- 좌우 화살표 키를 눌러도 타임라인이 반응하지 않거나 포커스가 다른 요소로 이동한다.
- 다음/이전 GOP, 다음/이전 에러 마커로 점프하는 키보드 단축키가 없어 매번 마우스로 정밀 클릭해야 한다.
- 타임라인 자체가 키보드 포커스를 받을 수 있는 요소로 마크업되어 있지 않다(tabindex 없음).

**원인**:
인터랙션 설계가 마우스/트랙패드 중심으로만 이루어지고, 전문가용 도구에서 필수적인 키보드 우선 워크플로(반복적 프레임 단위 이동, 빠른 마커 점프)가 고려되지 않았다.

**구현 냄새**:
- 타임라인 컨테이너에 `tabIndex`나 `onKeyDown` 핸들러가 없다.
- 단축키 처리가 전역 레벨에서만 일부(재생/정지 등) 구현되고 타임라인 탐색용 키는 누락되어 있다.

**영향**:
반복적으로 프레임을 오가며 비교해야 하는 전문 분석 작업에서 마우스 정밀 클릭에만 의존하면 속도와 정확도가 크게 떨어지고 반복 사용자의 손목 피로(RSI) 위험도 커진다. 접근성 요구사항(키보드만으로 조작 가능해야 함)도 충족하지 못한다.

**권장**:
- 좌/우 화살표: 1프레임 이동, Shift+화살표: 큰 폭(예: 1초 또는 GOP 단위) 이동, Home/End: 시작/끝 이동 등 표준적인 키맵을 정의한다.
- 다음/이전 마커(에러, 씬 전환, 키프레임) 점프를 위한 전용 단축키(예: `]`/`[`)를 제공한다.
- 타임라인에 명확한 포커스 링과 `tabIndex`를 부여해 접근성 표준(WAI-ARIA)을 충족한다.

**탐지**:
- 인터랙션 테스트: 마우스 없이 키보드만으로 특정 프레임/마커에 도달할 수 있는지 시나리오 테스트.
- 접근성 감사 도구로 타임라인의 포커스 가능 여부, ARIA role 확인.

**Bitvue 판정**: Suspected (2026-08-18 재감사, 라인 번호 갱신 — 최근 커밋으로 파일 앞부분에 컨텍스트 메뉴 코드가 추가돼 라인이 밀림) — `Timeline.tsx`는 포커스 시 ArrowLeft/Right로 ±1프레임 이동을 지원하고(handleKeyDown, 267행~), 앱 레벨 `useKeyboardNavigation`(hooks/useKeyboardNavigation.ts)도 prev/next frame과 prev/next keyframe 단축키를 제공한다. UIX-TIME-009 재확인 결과 App.tsx는 여전히 `useCurrentFrame`만 쓰고 `useSelection`은 전혀 호출하지 않는 반면 Timeline은 `useSelection`(SelectionContext)만 읽으므로, 두 키보드 경로가 서로 다른 상태를 움직여 실제로는 앱 레벨 단축키로 Timeline 커서를 이동시키지 못하는 경우가 여전히 존재한다. GOP/씬/에러 마커 점프는 해당 기능이 없어 애초에 불가능.

### UIX-TIME-017: 큰 점프와 한 프레임 이동이 같은 조작

**분류**: 인터랙션 설계 · **심각도**: Medium · **탐지**: Interaction

**사용자 목표**:
대략적인 위치로 빠르게 이동하는 것과 한 프레임씩 정밀 조정하는 것을 서로 다른 조작으로 명확히 구분해 쓰고 싶다.

**증상**:
- 클릭 한 번으로 이동하는 거리(수백~수천 프레임)와 화살표 키로 이동하는 거리(1프레임)가 같은 UI 요소, 같은 감도로 처리되어 미세 조정이 거의 불가능하다.
- 트랙패드나 마우스 드래그의 감도가 줌 레벨과 무관하게 고정되어, 확대된 상태에서도 살짝 움직였을 뿐인데 수백 프레임씩 건너뛴다.
- 반대로 축소된 상태에서는 드래그해도 거의 이동하지 않아 먼 거리 이동에 과도한 손동작이 필요하다.

**원인**:
이동 거리(프레임 수)를 화면 픽셀 이동량에만 비례시키고 현재 줌 레벨(화면당 프레임 밀도)을 반영하지 않는다. 또한 "정밀 이동"(키보드, 1프레임 버튼)과 "탐색적 이동"(드래그, 클릭 점프)을 위한 별도 인터랙션 vocabulary가 없다.

**구현 냄새**:
- 드래그 이동량 계산이 `deltaFrames = deltaPixels`처럼 줌 레벨 변수를 참조하지 않는다.
- 정밀 이동(1프레임)과 큰 점프(예: 10% 이동)가 동일한 핸들러/동일한 스텝 크기를 공유한다.

**영향**:
사용자가 원하는 정밀도로 위치를 맞추는 데 반복 시행착오가 필요해지고, 특히 에러 프레임 바로 앞뒤를 비교하는 것과 같은 정밀 작업에서 좌절감을 유발한다.

**권장**:
- 드래그/클릭 기반 이동은 줌 레벨(현재 화면에 보이는 프레임 밀도)에 비례하도록 계산해 "화면상 같은 거리 = 항상 비슷한 상대적 이동감"을 유지한다.
- 키보드 화살표(1프레임), Shift+화살표(큰 스텝), Page Up/Down(뷰포트 단위 점프) 등 스텝 크기가 다른 여러 조작을 명시적으로 구분해 제공한다.
- 미세 조정 모드(예: 확대된 미니 프리뷰에서 드래그)를 별도로 제공해 정밀 위치 지정을 돕는다.

**탐지**:
- 인터랙션 테스트: 다른 줌 레벨에서 동일한 드래그 거리(픽셀)가 실제로 이동하는 프레임 수를 측정해 비례 관계 확인.

**Bitvue 판정**: Suspected (2026-08-18 재감사, 최근 커밋으로 드래그 구현 변경됨) — 키보드(1프레임, handleKeyDown 267행~)와 드래그(handleMouseDown 193행~)는 이미 서로 다른 코드 경로라 완전히 동일한 조작은 아니다. UIX-TIME-001 수정으로 드래그가 이제 `Math.floor(percent*frames.length)` 나눗셈 대신 실제 DOM 엘리먼트 hit-test로 바뀌었지만, 각 프레임 바가 `min-width:2px`(Timeline.css:143)까지 줄어들 수 있어 프레임 수가 많아지면 여전히 마우스로 특정 1프레임을 정확히 겨냥하기 어렵다(줌 레벨 개념 자체가 없는 것은 UIX-TIME-004/011과 동일). 즉 근본 원인은 "선형 나눗셈"에서 "줌 없는 고정 픽셀 폭 하한"으로 바뀌었을 뿐 핵심 증상(많은 프레임 수에서 마우스 정밀 조정이 어려움)은 유사하게 남아있다 — 실측 인터랙션 테스트 없이는 확정하기 어려워 Suspected 유지.

### UIX-TIME-018: 분석되지 않은 영역과 정상 영역이 동일하게 보임

**분류**: 정보 위계/신뢰성 · **심각도**: High · **탐지**: Domain review

**사용자 목표**:
타임라인의 특정 구간이 아직 분석되지 않았는지, 분석했는데 이상이 없는지를 구별해서 알고 싶다.

**증상**:
- 아직 파싱/분석이 끝나지 않은 구간(지연 로딩 중이거나 백그라운드 분석 대기 중)이 "이상 없음"을 뜻하는 것과 똑같은 색(대개 빈 배경색 또는 기본 회색)으로 보인다.
- 스트림 일부만 분석하고 나머지는 건너뛴 경우(샘플링 분석, 부분 로드) 사용자가 이를 알아채지 못하고 전체가 검사된 것으로 오해한다.
- 분석 실패(디코드 에러로 스킵된 프레임)와 "분석했는데 문제 없음"이 시각적으로 구분되지 않는다.

**원인**:
타임라인 상태 모델에 "미분석(unknown)"이라는 명시적 상태가 없고, "정상(ok)"과 "값 없음(default/empty)"이 같은 렌더링 경로를 공유한다. 데이터가 없을 때의 기본값과 실제 정상값의 시각적 표현이 우연히 같아진 결과다.

**구현 냄새**:
- 마커/색상 매핑 함수가 `value ?? defaultColor` 형태로 null과 정상값을 구분하지 않고 처리한다.
- 분석 진행 상태(pending/analyzing/done/failed)를 추적하는 필드가 프레임 데이터 구조에 없다.

**영향**:
사용자가 "이 구간은 문제없다"고 잘못 결론 내렸는데 실제로는 아직 검사조차 되지 않은 구간이었다면, 이는 단순 불편이 아니라 분석 도구로서의 신뢰성을 근본적으로 훼손하는 결함이다.

**권장**:
- 프레임/구간 상태를 `unanalyzed | analyzing | ok | error`처럼 명시적 열거형으로 모델링하고 각각 뚜렷이 구분되는 시각적 표현(예: 빗금 패턴 = 미분석, 녹색 = 정상, 빨강 = 에러)을 부여한다.
- 부분 분석(샘플링)만 수행한 경우 타임라인 전체 또는 요약 바에 "N% 분석됨" 같은 명시적 커버리지 표시를 둔다.
- 미분석 구간에 사용자가 진입(스크럽/클릭)하면 온디맨드 분석을 트리거하고 진행 상태를 시각적으로 피드백한다.

**탐지**:
- 도메인 리뷰: 의도적으로 일부만 분석한 스트림을 로드해 미분석 구간과 정상 구간이 시각적으로 구분되는지 확인.
- 코드에서 상태 필드의 기본값과 "정상" 값이 동일한지 점검.

**Bitvue 판정**: Confirmed — `FrameInfo` 타입(frontend/types/video.ts:121-160)에 분석 진행 상태(`unanalyzed`/`analyzing`/`ok`/`failed` 등) 필드가 전혀 없고, Timeline/Filmstrip 어디에도 이를 구분해 그리는 로직이 없다(grep 결과 없음). 도구에 이 개념 자체가 아직 존재하지 않는다.

### UIX-TIME-019: 누락·중복 프레임이 시각적으로 드러나지 않음

**분류**: 데이터 무결성 표현 · **심각도**: High · **탐지**: Domain review

**사용자 목표**:
스트림에 프레임 손실(드롭)이나 중복이 있을 때 이를 타임라인에서 즉시 인지하고 싶다.

**증상**:
- 캡처/전송 과정에서 프레임이 누락된 구간이 타임라인에서 그냥 인접 프레임처럼 매끄럽게 이어져 보인다.
- 동일 타임스탬프를 가진 중복 프레임이 별개 프레임처럼 각자 자리를 차지해 표시된다.
- PTS 불연속(점프, 역행)이 있어도 타임라인 간격이나 색상에 아무 신호가 없다.

**원인**:
타임라인이 "받은 프레임 목록"을 그대로 순서대로 나열할 뿐, 프레임 간 시간/인덱스 연속성을 검증하고 이상을 마킹하는 단계가 파이프라인에 없다.

**구현 냄새**:
- 프레임 리스트 구축 시 인접 프레임 간 PTS/인덱스 delta를 검사하는 코드가 없다.
- 중복 PTS를 가진 프레임을 걸러내거나 표시하는 로직이 없어 그대로 별개 항목으로 렌더링된다.

**영향**:
프레임 손실/중복은 캡처 장비 문제, 네트워크 스트리밍 문제, 인코더 버그 등 심각한 이슈의 신호인데 이것이 타임라인에서 드러나지 않으면 사용자가 근본 원인을 놓친 채 잘못된 결론(예: "이 구간 화질이 나쁘다"만 보고 원인은 프레임 드롭이라는 것을 놓침)을 내릴 수 있다.

**권장**:
- 프레임 로드/파싱 단계에서 PTS/DTS 연속성 검사를 수행해 gap(누락 추정), duplicate(중복), discontinuity(역행/점프) 상태를 프레임 메타데이터에 명시적으로 기록한다.
- 타임라인에 이 상태를 위한 전용 마커(예: 누락 구간은 빗금 간격, 중복은 겹친 아이콘)를 추가해 정상 프레임과 시각적으로 뚜렷이 구분한다.
- 요약 패널에 "감지된 프레임 드롭 N건, 중복 M건" 같은 무결성 리포트를 제공한다.

**탐지**:
- 도메인 리뷰: 의도적으로 프레임을 제거/중복시킨 합성 스트림으로 타임라인이 이를 표시하는지 확인.
- 파싱 파이프라인에서 PTS 연속성 검증 코드 유무 확인.

**Bitvue 판정**: Confirmed (2026-08-18 재감사, 경로 갱신) — Timeline UI 자체는 여전히 gap/duplicate/discontinuity를 표시하지 않는다(frontend 쪽 grep 결과 없음). 다만 원 인용 백엔드 경로(`src-tauri`)는 Tauri 제거로 사라졌고, 대신 **관련 검증 로직 자체는 이미 존재**한다는 게 확인됐다: `bitvue-engine::frame_identity`가 PTS 중복/비단조 증가를 감지해 `BAD`/`GOOD` 신뢰도로 분류하는 코드를 갖고 있다(crates/bitvue-engine/src/frame_identity.rs:117-163, 272-310, "Check for duplicates using HashSet" 등). 하지만 이는 최근에야 `bitvue-indexer::get_timeline`을 통해 첫 호출자를 얻었을 뿐(UIX-TIME-003 참고) `getTimeline` IPC가 프론트 어디서도 소비되지 않아, 실제 Timeline이 그리는 `get_frames_chunk` 경로에는 gap/duplicate 신호가 전혀 흘러들어가지 않는다 — "검사 로직 부재"가 아니라 "검사 로직은 있는데 UI에 배선 안 됨"에 가깝다.

### UIX-TIME-020: 마우스 드래그 요청에 backpressure가 없음

**분류**: 성능/동시성 · **심각도**: Critical · **탐지**: Performance

**사용자 목표**:
타임라인을 빠르게 드래그해도 UI가 밀리거나 응답이 쌓여 지연되지 않아야 한다.

**증상**:
- 빠르게 드래그하면 화면이 실제 마우스 위치보다 계속 뒤처지다가, 마우스를 멈춘 뒤에도 한참 동안 밀린 갱신이 이어진다("고무줄" 현상).
- IPC(Tauri)나 백엔드 분석 요청이 마우스 이동 이벤트 수만큼 큐에 쌓여 순서대로 모두 처리되느라 최신 위치 반영이 지연된다.
- 메모리/큐 사용량이 드래그 지속 시간에 비례해 계속 증가한다.

**원인**:
마우스 move 이벤트마다 프레임 데이터/썸네일 요청을 발사하고, 이전 요청이 아직 처리 중이어도 새 요청을 무제한으로 큐에 추가한다. 오래된 요청을 취소하거나 최신 요청만 유지하는 backpressure/coalescing 전략이 없다.

**구현 냄새**:
- 이벤트 핸들러에서 IPC invoke를 직접 호출하며 in-flight 요청 수를 추적하지 않는다.
- 요청 취소(AbortController, 요청 세대 번호 등) 메커니즘이 어디에도 없다.
- 큐/채널에 무제한 버퍼가 있어 소비자가 느려도 생산자가 계속 쌓기만 한다.

**영향**:
UIX-TIME-008(스크럽 중 정밀 분석)과 유사하지만 더 근본적인 아키텍처 문제로, 드래그 같은 고빈도 인터랙션 전반에서 UI가 실제 사용자 입력을 놓치거나 뒤늦게 반영해 "만졌는데 반응이 없다"는 근본적 불신을 만든다.

**권장**:
- 최신 요청만 유효하다는 "latest-wins" 전략을 적용해, 새 드래그 위치가 들어오면 이전 in-flight 요청을 취소하거나 결과를 무시한다.
- 이벤트 발사 자체를 requestAnimationFrame 또는 고정 간격 스로틀로 묶어 초당 요청 수 상한을 둔다.
- 백엔드/IPC 큐는 유한 버퍼 + 최신 요청 우선(오래된 대기 요청 폐기) 정책으로 설계한다.

**탐지**:
- 성능 테스트: 빠른 드래그 후 정지했을 때 UI가 즉시 최신 상태로 안정화되는지, 지연된 갱신이 계속 이어지는지 측정.
- IPC 요청 큐 길이를 드래그 도중 모니터링해 무한정 증가하는지 확인.

**Bitvue 판정**: Suspected — `Timeline.tsx` 자체의 스크럽은 드래그 중 IPC를 호출하지 않아(UIX-TIME-008 참고) 이 항목의 핵심 증상은 발생하지 않는다. 다만 `useFilmstripState.ts`의 썸네일 로딩(IntersectionObserver 기반)은 AbortController/요청 취소가 없어(그레프 확인) 빠른 스크롤 시 동시 in-flight 요청 수에 상한이 없다 — 이미 로딩 중인 인덱스는 재요청하지 않는 최소한의 dedup만 존재.

### UIX-TIME-021: 서로 다른 스케일의 지표를 하나의 축에 억지로 겹쳐 그림

**분류**: 정보 표현 · **심각도**: Medium · **탐지**: Visual

**사용자 목표**:
frame size, QP, bitrate처럼 단위와 값 범위가 다른 여러 지표를 동시에 비교하면서도 각각을 올바르게 해석하고 싶다.

**증상**:
- frame size(바이트, 수십 KB 단위)와 QP(정수, 0~51 범위)가 같은 Y축, 같은 스케일로 그려져 QP 그래프가 거의 평평한 직선처럼 보인다.
- 정규화(0~1 스케일링)를 적용했지만 범례나 축 레이블에 원래 단위/범위가 표시되지 않아, 그래프의 절대값을 읽을 수 없다.
- 로그 스케일과 선형 스케일이 지표별로 섞여 있는데 이를 구분할 표시가 없다.

**원인**:
여러 지표를 "겹쳐 보여주면 비교하기 좋다"는 발상만으로 단일 Y축에 정규화해 얹고, 각 지표의 실제 스케일/단위 정보를 축 디자인에서 보존하지 않는다.

**구현 냄새**:
- 정규화 함수(`value / max`)가 렌더링 직전에 한 번 적용되고 원본 값이 툴팁에도 노출되지 않는다.
- Y축 레이블이 "0~1" 같은 무차원 값으로만 표시된다.

**영향**:
사용자가 그래프 모양(트렌드)은 비교할 수 있어도 "이 지점의 실제 QP가 몇인가"라는 구체적 질문에 답하지 못해, 시각화가 장식에 그치고 정량 분석 도구로서 기능하지 못한다.

**권장**:
- 지표마다 별도의 Y축(왼쪽/오른쪽 축 또는 별도 서브트랙)을 제공하고 각 축에 단위와 범위를 명시한다.
- 정규화된 겹쳐보기는 opt-in 트렌드 비교 모드로 별도 제공하되, 호버 시 항상 원본 값을 툴팁으로 노출한다.
- 로그/선형 스케일 선택을 지표별로 명시하고 축에 표기한다.

**탐지**:
- 시각 검수: 값 범위가 크게 다른 두 지표를 동시에 표시했을 때 작은 값 지표의 변화가 식별 가능한지 확인.
- 툴팁/호버에서 원본 단위 값이 노출되는지 확인.

**Bitvue 판정**: N/A — `FrameSizesView.tsx`는 이미 왼쪽(Bitrate/KB)과 오른쪽(QP 0-51) 축을 단위와 함께 분리해 표시한다(127-137행, 242-248행). 정규화해 억지로 한 축에 겹치는 안티패턴은 피해져 있다. 다만 `showBlockMinQP`/`showBlockMaxQP` 토글은 정의만 되어 있고(SizeMetrics 인터페이스) 실제로 렌더링에 쓰이지 않는 죽은 코드다(별개 이슈).

### UIX-TIME-022: 필터링 후 제외된 프레임의 컨텍스트가 사라짐

**분류**: 정보 위계/탐색 컨텍스트 · **심각도**: Medium · **탐지**: Interaction

**사용자 목표**:
"I프레임만 보기", "에러 프레임만 보기" 같은 필터를 적용해도 전체 스트림에서 그 프레임들이 어디쯤 위치하는지 감을 잃고 싶지 않다.

**증상**:
- 필터를 적용하면 걸러진 프레임들이 마치 서로 인접한 것처럼 빈틈없이 재배치되어, 실제 스트림상 간격(예: 에러 프레임 사이에 정상 프레임이 수천 개 있다는 사실)이 사라진다.
- 필터 해제 버튼을 찾기 어렵거나, 필터가 걸려 있다는 사실 자체가 화면에 명확히 표시되지 않아 사용자가 "왜 프레임이 이렇게 적지"라고 혼란스러워한다.
- 필터링된 뷰에서 프레임을 선택해도 원래(비필터) 타임라인상 위치를 알 수 없다.

**원인**:
필터를 "데이터셋 자체를 축소"하는 방식으로 구현해 원본 타임라인과의 위치 대응 관계(비례 간격, 전체 대비 비중)를 버린다. 필터 상태의 시각적 표시(활성 배지, 초기화 버튼)도 누락되어 있다.

**구현 냄새**:
- 필터 적용이 `frames.filter(...)`로 새 배열을 만들고 이후 렌더링은 원본 인덱스/오프셋을 전혀 참조하지 않는다.
- 필터 on/off 상태를 나타내는 전용 UI 요소(칩, 배지)가 없다.

**영향**:
필터가 유용한 만큼 컨텍스트 손실도 커서, 사용자가 "이 에러들이 몰려있는지 퍼져있는지" 같은 분포 정보를 오독하거나, 필터가 걸린 줄 모르고 전체 분석을 했다고 착각하는 위험이 생긴다.

**권장**:
- 필터링된 뷰에서도 원본 타임라인 위 상대적 위치(비례 간격)를 유지하거나, 최소한 미니맵에 필터 결과의 원본 위치를 점으로 표시한다.
- 활성 필터를 항상 눈에 띄는 배지/칩으로 표시하고 원클릭 초기화를 제공한다.
- 필터링된 프레임을 클릭하면 원본(비필터) 타임라인에서의 위치로 점프하는 연결 고리를 제공한다.

**탐지**:
- 인터랙션 테스트: 필터 적용 후 화면만 보고 "필터가 걸려 있는지, 얼마나 걸러졌는지"를 즉시 알 수 있는지 확인.
- 필터링 전후 프레임 간 원본 간격 정보가 유지되는지 코드 검토.

**Bitvue 판정**: Confirmed — `FrameSizesView.tsx`의 `filteredFrames`(117-119행)는 `frames.filter(...)`로 만든 배열이고, 이후 x좌표 계산이 `idx/(filteredFrames.length-1)`(175, 201행)로 필터링된 배열 인덱스를 기준으로 재분배해 원본 간격 정보를 버린다. 다만 `Filmstrip.tsx`에서 `visibleFrameTypes`가 `["I","P","B"]`로 하드코딩되어 있어(67행) 실제로 필터를 바꾸는 UI가 현재 노출되어 있지 않으므로 이 경로는 아직 사용자가 도달할 수 없는 잠재적 결함이다.

Timeline은 일반 DOM보다 canvas/WebGL 또는 가상화 계층이 필요한 경우가 많다. 다만 처음부터 WebGL로 가는 것도 안티패턴일 수 있다 — 데이터 수와 상호작용 복잡도를 기준으로 선택해야 한다.
