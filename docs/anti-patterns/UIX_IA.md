# Anti-Pattern Catalog — UIX_IA: 정보 구조와 탐색

이 문서는 더 큰 안티패턴 카탈로그의 일부입니다 (전체 목차는 별도 작성 중인 `docs/anti-patterns/INDEX.md` 참고). Phase 1(Rust/미디어 엔지니어링: `OWN/MEM/LAYOUT/PARSE/CODEC/IO/CONC/CACHE/IPC/PIXEL/ERR/PERF/API_TYPE/FRONTEND`)과 Phase 2(VQ-Probe 품질 분석 도메인: `ALIGN/SPATIAL/COLOR/METRIC/PIPE/HEAT/STAT`)에 이어, 이 파일은 UI/UX + Tauri Phase 3 웨이브의 첫 번째 카테고리입니다. 이 카테고리는 정적 코드 리뷰가 아니라 제품/UX 품질을 다룹니다 — 여기서 핵심 위험은 "못생김"이 아니라 "사용자가 지금 뭘 보고 있는지 모른다 / 패널마다 선택 상태가 어긋난다 / 오래된 비동기 결과가 화면을 덮어쓴다"는 것입니다. 이 파일은 1단계(일반 참조 카탈로그)이며, 2단계에서 Bitvue 저장소를 실제로 감사해 각 항목의 "Bitvue 판정"을 채웁니다.

## 기준 정보 구조 (Reference IA)

Bitvue와 VQ-Probe 두 축 모두 "사용자가 문제를 좁혀가는 순서"를 그대로 내비게이션 계층으로 반영해야 합니다. 이 순서를 어기는 모든 UI 구성은 이 카테고리의 잠재적 위반입니다.

- **Bitvue (bitstream analyzer)**: 파일 → 트랙 → 구간/GOP → 프레임 → 블록 또는 syntax field → 원본 바이트
- **VQ-Probe (품질 비교)**: 비교 작업 → 영상 쌍 → 전체 품질 요약 → 문제 구간 → 프레임 → 공간 영역 → metric 원인과 전처리 조건

**나쁜 예**: `Demux / Parser / Decode / Metrics` 처럼 내부 구현 crate·모듈 이름을 그대로 최상위 메뉴로 노출하는 구성. 사용자는 "이 프레임에 뭐가 잘못됐는지" 알고 싶을 뿐, 그 정보가 demuxer 단계에서 나왔는지 decoder 단계에서 나왔는지는 관심사가 아닙니다.

**좋은 예**: `Overview / Timeline / Frame Inspector / Syntax / Quality / Compare` 처럼 사용자의 분석 작업 단위를 이름으로 삼는 구성. 내부적으로 여러 모듈(demux, parse, decode, metric)이 협력해 하나의 화면을 채우더라도, 화면 이름은 항상 사용자 목표를 따라갑니다.

### UIX-IA-001: 모든 기능을 탭으로 평면 나열

**분류**: UIX_IA · **심각도**: High · **탐지**: Visual · Domain review

**사용자 목표**:
분석 흐름에 맞춰 자연스럽게 다음 단계로 넘어가고 싶다.

**증상**:
- 상단 탭 바에 Overview, Timeline, Syntax, Hex, Motion Vector, Reference, Quality, Compare, Settings 등 10개 이상의 탭이 같은 위계로 나열되어 있다.
- 탭 간 우선순위나 사용 빈도 차이가 시각적으로 전혀 드러나지 않는다.
- 신규 기능이 추가될 때마다 탭이 하나씩 늘어나며, 탭 바가 스크롤되거나 글자가 줄임표로 잘린다.

**원인**:
내비게이션 설계를 "기능이 생길 때마다 탭 하나 추가"라는 개발 편의 규칙으로 대체했기 때문. 탭이라는 위젯 자체는 평면 구조를 전제하므로, 실제로는 계층이 있는 정보(파일 수준 설정 vs 프레임 수준 뷰 vs 비교 전용 기능)를 억지로 같은 층에 욱여넣게 된다.

**구현 냄새**:
- `<Tabs items={ALL_FEATURES}>` 식으로 기능 목록 배열을 그대로 탭 렌더링에 매핑.
- 탭 추가 시 라우팅/상태 관리 코드만 건드리고 IA 문서나 내비게이션 설계 리뷰는 거치지 않음.

**영향**:
신규 사용자는 어디서 시작해야 할지 판단할 기준이 없고, 숙련 사용자도 자주 쓰는 탭을 찾기 위해 매번 훑어봐야 한다. 탭 수가 늘수록 각 탭의 "선택 비용"이 커져 실제 분석 속도가 느려진다.

**권장**:
- 탭을 1차(핵심 분석 흐름: Overview/Timeline/Frame Inspector)와 2차(세부 도구: Syntax/Hex/MV)로 나누고, 2차는 1차 화면 안의 서브 패널이나 사이드 드로어로 격하한다.
- 비교 전용 기능(Compare)은 물리적으로 다른 워크스페이스로 분리해 "단일 파일 분석"과 섞이지 않게 한다.
- 탭 순서를 분석 파이프라인 순서(파일→트랙→구간→프레임→블록)와 일치시킨다.

**탐지**:
- 최상위 탭 개수를 세어 7±2 원칙을 넘는지 확인.
- 신규 사용자 대상 "처음 3분 안에 프레임 하나의 문제를 찾아보라" 과업 테스트에서 탭 탐색에 걸리는 시간 측정.

**Bitvue 판정**: 미정 — 2단계(저장소 감사)에서 채움

### UIX-IA-002: 분석 흐름보다 구현 모듈 기준으로 메뉴 구성

**분류**: UIX_IA · **심각도**: High · **탐지**: Domain review · Code

**사용자 목표**:
"이 프레임이 왜 깨졌는지" 같은 하나의 질문을 따라가며 화면을 이동하고 싶다.

**증상**:
- 메뉴가 `Demux / Parser / Decode / Metrics` 처럼 내부 crate·모듈 이름을 그대로 노출한다.
- 하나의 분석 질문(예: "이 GOP의 화질 저하 원인")에 답하려면 서로 다른 메뉴 3~4개를 오가야 한다.
- 메뉴 이름이 코드베이스 리팩터링을 따라 바뀐다 (예: `decode` crate가 `codec-core`로 이름이 바뀌면 메뉴도 따라 바뀜).

**원인**:
IA를 화면 설계자가 아니라 각 모듈 담당 개발자가 "내 모듈에 뷰 하나 추가"하는 방식으로 누적 설계했기 때문. 팀 조직도(demux 팀, decode 팀, metric 팀)가 그대로 메뉴 구조에 투영된 것 — Conway's Law의 UX 버전.

**구현 냄새**:
- 라우트 경로가 `/demux`, `/parser`, `/decode`, `/metrics`처럼 내부 모듈 이름과 1:1 대응.
- 화면 컴포넌트 디렉터리 구조가 곧 메뉴 구조 (`components/demux/`, `components/decode/` 가 그대로 사이드바 항목이 됨).

**영향**:
사용자는 코덱 파이프라인 내부 구조를 몰라도 되어야 하는데, 메뉴 자체가 그 구조를 배우도록 강요한다. 특히 신규 사용자·비개발자 QA 인력에게 진입 장벽이 커진다.

**권장**:
- 메뉴/탭 이름은 항상 "사용자가 답하려는 질문"을 기준으로 짓는다 (Overview, Timeline, Frame Inspector, Syntax, Quality, Compare).
- 여러 모듈의 데이터를 한 화면에서 조합해 보여주는 것을 정상으로 간주하고, 이를 위해 프론트엔드에 별도의 뷰 모델 계층을 둔다.
- 코드 리팩터링(모듈 이름 변경, 파일 분할)이 메뉴 이름에 영향을 주지 않도록 IA와 구현을 분리한다.

**탐지**:
- 메뉴 라벨 목록과 백엔드 모듈/crate 이름 목록을 나란히 놓고 문자열 유사도를 비교 — 높은 겹침은 경고 신호.
- "이 화면은 어떤 사용자 질문에 답하는가"를 각 메뉴 항목에 대해 한 문장으로 쓸 수 없다면 재설계 대상.

**Bitvue 판정**: 미정 — 2단계(저장소 감사)에서 채움

### UIX-IA-003: 동일 개념을 패널마다 다른 이름으로 표시

**분류**: UIX_IA · **심각도**: Medium · **탐지**: Visual · Domain review

**사용자 목표**:
한 패널에서 본 값을 다른 패널에서도 같은 이름으로 찾아 서로 연결 짓고 싶다.

**증상**:
- 타임라인 패널에서는 "POC", 프레임 인스펙터에서는 "Display Order", 신택스 뷰에서는 "pic_order_cnt_lsb"로 같은 개념이 세 가지 이름으로 나타난다.
- 품질 비교 패널에서 "Reference"가 어떤 곳에서는 "원본(source)", 다른 곳에서는 "기준(baseline)"을 가리켜 의미가 뒤섞인다.
- 툴팁이나 범례 없이 각 패널이 자체적으로 용어를 정의해 사용한다.

**원인**:
각 패널이 서로 다른 시점에 다른 담당자가 구현했고, 공용 용어집(glossary)이나 UI 텍스트 리소스가 없어 각자 도메인 지식을 기준으로 라벨을 지었기 때문.

**구현 냄새**:
- 라벨 문자열이 컴포넌트마다 하드코딩되어 있고 공통 i18n/용어 상수 파일을 참조하지 않음.
- 동일 데이터 필드(`pic_order_cnt`)가 패널별 컴포넌트에서 각각 다른 하드코딩 라벨 문자열과 매핑됨.

**영향**:
사용자가 패널 간 데이터를 머릿속에서 매핑하는 데 추가 인지 부하가 생기고, 특히 코덱 전문가가 아닌 사용자는 세 용어가 같은 것을 가리키는지조차 확신하지 못해 잘못된 결론을 낼 수 있다.

**권장**:
- 프로젝트 전역 용어집을 만들고 (예: `Display Order (POC)`처럼 사용자 친화 이름 + 스펙 용어 병기) 모든 패널이 이를 참조한다.
- 스펙 원어 용어가 필요한 곳(Syntax/Hex 뷰)에서는 원어를 유지하되, 사용자 친화 이름을 괄호로 병기한다.
- 라벨 문자열을 코드 리뷰 체크리스트에 포함해 새 하드코딩 라벨 추가를 차단한다.

**탐지**:
- 전체 프론트엔드에서 라벨 문자열을 추출해 동일 데이터 필드에 매핑되는 라벨 이형(異形) 개수를 센다.
- 동일 프레임을 여러 패널에서 동시에 열어놓고 같은 값을 가리키는 라벨이 일치하는지 스크린샷 대조.

**Bitvue 판정**: 미정 — 2단계(저장소 감사)에서 채움

### UIX-IA-004: Frame, Picture, Packet, Sample, AU 개념 혼용

**분류**: UIX_IA · **심각도**: High · **탐지**: Domain review · User test

**사용자 목표**:
"몇 번째 프레임"을 이야기할 때 화면의 다른 곳에서도 같은 단위로 셀 수 있길 바란다.

**증상**:
- 타임라인은 "Access Unit" 단위로 seek하는데 프레임 인스펙터는 "Picture" 단위로 카운트해 인덱스가 어긋난다.
- 컨테이너 레벨(MP4 sample)과 코덱 레벨(AVC picture, decode order vs display order)의 인덱스가 같은 숫자 라벨("Frame #42")로 노출되지만 실제로는 서로 다른 시퀀스를 가리킨다.
- field-coded 콘텐츠에서 필드 하나를 "프레임 1개"로 셀지 "프레임의 절반"으로 셀지가 화면마다 다르다.
- B-프레임이 있는 스트림에서 decode order 인덱스와 display order 인덱스가 뒤섞여 표시된다.

**원인**:
컨테이너(Packet/Sample), 코덱 비트스트림(Access Unit/NALU), 디코더 출력(Picture/Frame)이라는 세 개의 서로 다른 도메인 모델을 UI가 구분 없이 "프레임"이라는 단일 개념으로 뭉뚱그렸기 때문. 각 도메인은 실제로 카운트, 순서, 심지어 총 개수까지 다를 수 있다 (예: alternative frame가 있으면 packet 수 ≠ picture 수).

**구현 냄새**:
- 프론트엔드 상태에 `frameIndex: number` 필드 하나만 있고, 이것이 packet index인지 decode-order picture index인지 display-order picture index인지 타입 수준에서 구분되지 않음.
- 백엔드 IPC 응답에 `frame_number`라는 필드명이 여러 커맨드에서 재사용되지만 실제 의미(정의 도메인)가 커맨드마다 다름.

**영향**:
사용자가 타임라인에서 클릭한 지점과 신택스 뷰/hex 뷰에서 실제로 열리는 데이터가 어긋나는, 신뢰를 해치는 버그로 직결된다. B-프레임이 많은 HEVC 콘텐츠에서 특히 자주 재현된다.

**권장**:
- 컨테이너 sample index, decode order index, display order(POC) index를 별도 필드로 항상 함께 보관하고, UI에는 현재 어떤 순서 기준인지 명시적으로 라벨링한다 (예: "Display #42 (Decode #39)").
- 타입 시스템에서 세 인덱스를 서로 다른 nominal 타입(newtype)으로 분리해 실수로 섞어 쓰는 것을 컴파일 타임에 막는다.
- 필드/interlaced 콘텐츠는 "필드 1개"와 "프레임 1개"를 명확히 구분하는 토글이나 표기를 둔다.

**탐지**:
- B-프레임이 많은 샘플 스트림으로 타임라인 클릭 → 프레임 인스펙터 → 신택스 뷰까지 인덱스가 끝까지 일치하는지 회귀 테스트.
- 코드에서 `frame_number`, `frameIndex` 등 모호한 이름의 필드를 검색해 도메인(sample/decode/display)이 타입이나 이름에 명시되어 있는지 점검.

**Bitvue 판정**: 미정 — 2단계(저장소 감사)에서 채움

### UIX-IA-005: 코덱별 개념을 무리하게 공통 UI에 넣음

**분류**: UIX_IA · **심각도**: Medium · **탐지**: Domain review · Visual

**사용자 목표**:
지금 열려 있는 코덱(AV1이든 HEVC든 VP9든)에 실제로 존재하는 개념만 보고 싶다.

**증상**:
- HEVC 스트림을 열었는데 AV1 전용 개념인 "Superblock" 필드가 회색으로 비활성화된 채 여전히 UI에 남아있다.
- VP9에는 없는 "Long-term Reference Picture" 토글이 모든 코덱에서 공통으로 노출된다.
- 코덱마다 참조 프레임 관리 모델이 근본적으로 다른데(HEVC의 RPS vs VP9의 8-slot reference buffer vs AV1의 reference frame update) 하나의 "Reference" 패널 레이아웃으로 억지로 통일했다.

**원인**:
공통 컴포넌트를 재사용하려는 개발 압력이 "코덱 개념의 최대공약수만 보여준다"가 아니라 "모든 코덱 개념의 합집합을 하나의 폼에 넣고 해당 없는 건 숨기거나 비활성화한다"는 방향으로 흘렀기 때문.

**구현 냄새**:
- 하나의 `<ReferencePanel codec={codec}>` 컴포넌트 내부에 `if (codec === 'hevc') ... else if (codec === 'vp9') ...` 분기가 필드 단위로 촘촘히 박혀 있음.
- disabled/hidden 처리된 필드가 많아 실제로 렌더링되는 DOM 노드 수가 활성 필드 수의 몇 배.

**영향**:
사용자가 "이 필드가 이 코덱에 진짜 없는 개념인지, 아니면 이번 파일에 우연히 값이 없는 것인지" 구분할 수 없어 잘못된 결론(버그로 오인)을 내릴 위험이 생긴다. 화면도 불필요하게 복잡해진다.

**권장**:
- 코덱별로 실제 개념 모델이 다르면 공통 셸(레이아웃, 내비게이션)만 공유하고 내용 컴포넌트는 코덱별로 분리한다.
- 코덱 간 진짜 공통 개념(예: "참조 프레임 개수")만 공통 컴포넌트로 추상화하고, 나머지는 코덱 전용 서브패널로 렌더링한다.
- disabled 필드를 만들지 말고, 해당 코덱에 없는 개념이면 아예 렌더링하지 않는다.

**탐지**:
- 코덱을 전환해가며 같은 패널을 열어 비활성화된 필드 비율을 측정 — 비율이 높으면 공통화 과잉 신호.
- 코덱 전문가 리뷰: "이 필드가 이 코덱 스펙에 실제로 존재하는가"를 항목별로 체크.

### UIX-IA-006: 중요한 상태와 부가 정보를 같은 시각적 무게로 표시

**분류**: UIX_IA · **심각도**: High · **탐지**: Visual · User test

**사용자 목표**:
화면을 한 번 훑어보고 "지금 문제가 있는지 없는지"를 즉시 판단하고 싶다.

**증상**:
- "디코드 실패", "프레임 손상" 같은 치명적 상태가 파일 이름, 코덱 태그, 해상도 같은 메타데이터와 동일한 폰트 크기·색상으로 나열된다.
- 품질 비교 패널에서 "PSNR 급락 구간"이 다른 통계 수치들과 똑같은 표 셀 스타일로 표시되어 스캔 시 눈에 띄지 않는다.
- 경고/에러 아이콘이 있어도 색상 대비가 낮거나 다른 정보 아이콘과 크기가 같아 시각적으로 구분되지 않는다.

**원인**:
정보 위계(hierarchy)를 시각 디자인 단계에서 의도적으로 설계하지 않고, 데이터 스키마 순서(백엔드 응답의 필드 순서)를 그대로 화면에 나열했기 때문. "이 값이 사용자의 의사결정에 얼마나 중요한가"라는 질문이 UI 설계 과정에서 빠졌다.

**구현 냄새**:
- 메타데이터 렌더링이 `Object.entries(metadata).map(...)`처럼 범용 key-value 리스트 컴포넌트 하나로 모든 필드를 동일하게 순회.
- 심각도(severity) 필드가 데이터에는 존재하지만 그 값을 스타일(색상/크기/아이콘)에 매핑하는 로직이 없거나 일부 컴포넌트에만 부분 적용됨.

**영향**:
사용자가 화면을 훑어봐도 진짜 문제를 놓치고, 결국 모든 값을 하나하나 읽어야 해서 "한눈에 파악"이라는 분석 도구의 핵심 가치가 무너진다.

**권장**:
- 심각도 등급(정상/주의/경고/치명)을 데이터 모델에 명시적 필드로 두고, 모든 렌더링 컴포넌트가 이를 색상·크기·위치(상단 고정 배너 등)에 일관되게 매핑하도록 디자인 토큰화한다.
- 페이지 상단에 "현재 파일/구간의 최고 심각도 상태"를 요약하는 배너를 항상 고정 배치한다.
- 부가 메타데이터(파일명, 코덱 태그 등)는 보조 영역(사이드바, 접힌 섹션)으로 시각적 무게를 낮춘다.

**탐지**:
- 5초 노출 테스트(사용자에게 화면을 5초만 보여주고 "문제가 있었는지"를 묻는 방식)로 치명적 상태의 시각적 두드러짐을 측정.
- 색상 대비(WCAG) 및 상대적 폰트 크기를 심각도 등급별로 감사.

### UIX-IA-007: 세부 정보가 기본 화면을 점유

**사용자 목표**:

**원인**:

**영향**:

**권장**:
- 파일을 열면 항상 Overview 화면이 먼저 뜨도록 기본 라우트를 고정한다.
- Overview는 최소한 "전체 구간에서 문제 의심 지점"을 한눈에 보여주는 타임라인/히트맵을 포함해야 한다.
- 세부 뷰(신택스/hex)는 Overview에서 특정 지점을 클릭해 들어가는 2차 화면으로 위치시킨다.

**탐지**:
- 파일 열기 → 첫 화면이 무엇인지 스크린샷으로 확인하는 스모크 테스트.
- 신규 사용자 대상 "이 파일에 문제가 있는지 30초 안에 판단하라" 과업에서 실패율 측정.

### UIX-IA-008: 사용자가 문제 지점으로 들어갈 진입 경로 없음

**분류**: UIX_IA · **심각도**: Critical · **탐지**: Interaction · Domain review

**사용자 목표**:
"이 구간에 문제가 있다"는 요약 정보를 보자마자 바로 그 구간의 상세 화면으로 이동하고 싶다.

**증상**:
- Overview 화면의 그래프나 히트맵에서 이상치(spike, 붉은 구간)를 클릭해도 아무 반응이 없다.
- 문제 구간을 발견한 뒤, 해당 프레임 번호를 수동으로 확인하고 다른 패널에서 그 번호를 다시 입력해야 한다.
- 품질 비교 히트맵에서 낮은 점수 영역을 클릭해도 해당 프레임/공간 영역으로 프레임 인스펙터가 이동하지 않는다.

**원인**:
요약 시각화(그래프/히트맵) 컴포넌트를 "보여주기 전용"으로만 구현하고, 클릭 이벤트를 다른 패널의 내비게이션 상태와 연결하는 작업(딥링크, 공유 선택 상태)을 별도 작업으로 미루거나 누락했기 때문. 대개 시각화 라이브러리 도입 자체는 빠르지만 상호작용 배선은 후순위로 밀린다.

**구현 냄새**:
- 차트 컴포넌트에 `onClick` 핸들러 자체가 없거나, 있어도 툴팁 표시에만 쓰이고 라우팅/상태 변경으로 이어지지 않음.
- 프레임 번호, 시간 오프셋 등 "위치 정보"가 차트 데이터에는 있지만 클릭 이벤트 페이로드에 전달되지 않음.

**영향**:
Overview가 문제를 "보여주기"는 하지만 "가리키기"는 못해서, 사용자가 결국 수동으로 프레임 번호를 옮겨 적는 작업을 반복해야 한다. 문제를 발견하는 것과 문제를 조사하는 것 사이에 불필요한 마찰이 생긴다.

**권장**:
- 모든 요약 시각화의 각 데이터 포인트(프레임, 구간, 공간 영역)를 클릭하면 해당 위치로 다른 관련 패널이 함께 이동하도록 공유 선택 상태(shared selection)를 설계한다.
- 클릭 가능한 요소는 커서 스타일, 호버 하이라이트로 상호작용 가능함을 명시한다.
- 딥링크(URL 또는 상태 스냅샷)로 "이 구간을 가리키는 링크"를 공유할 수 있게 한다.

**탐지**:
- Overview의 모든 시각적 이상치 마커에 대해 클릭 시 상태 변화가 있는지 체크리스트로 순회.
- Interaction 테스트: 히트맵 클릭 → 프레임 인스펙터 인덱스 변경까지의 엔드투엔드 테스트.

**Bitvue 판정**: 미정 — 2단계(저장소 감사)에서 채움

### UIX-IA-009: 탐색 계층이 너무 깊어 현재 위치를 잃음

**분류**: UIX_IA · **심각도**: Medium · **탐지**: Interaction · User test

**사용자 목표**:
지금 보고 있는 값이 전체 구조 어디에 위치하는지 항상 알고 있고 싶다.

**증상**:
- 파일 → 트랙 → GOP → 프레임 → CTU → CU → syntax field까지 6~7단계를 내려가야 하는데, 현재 깊이를 보여주는 breadcrumb이 없다.
- 뒤로가기를 여러 번 눌러야 상위 계층으로 돌아갈 수 있고, 어느 시점에 몇 번 눌러야 하는지 예측 불가능하다.
- 깊은 화면에서 "이 syntax field가 몇 번째 프레임, 몇 번째 CTU에 속하는지"를 화면 어디에서도 확인할 수 없다.

**원인**:
각 계층 전환을 독립적인 화면 전환(모달 열기, 페이지 이동)으로 구현하면서 상위 컨텍스트를 함께 넘기지 않았기 때문. breadcrumb이나 지속적 컨텍스트 바 없이 "지금 화면"만 렌더링하는 방식이 계층이 얕을 때는 문제되지 않다가, 계층이 깊어지며 드러난다.

**구현 냄새**:
- 라우팅 상태에 상위 계층 식별자(트랙 ID, GOP 범위, 프레임 인덱스)가 URL이나 전역 상태로 유지되지 않고 컴포넌트 로컬 state로만 존재.
- 각 하위 화면 컴포넌트가 상위 컨텍스트 없이도 독립적으로 마운트 가능하도록 설계되어 있어, 반대로 "지금 어디서 왔는지"를 자연스럽게 표현할 데이터가 없음.

**영향**:
사용자가 세부 화면에서 길을 잃고, 처음부터 다시 탐색을 시작하는 경우가 잦아진다. 특히 반복적인 비교 작업(여러 프레임을 오가며 확인)에서 누적 피로가 커진다.

**권장**:
- 모든 세부 화면 상단에 전체 계층을 보여주는 breadcrumb을 고정 배치한다 (예: `파일.mp4 > Track 0 > GOP 12 > Frame 340 > CTU(4,7)`).
- breadcrumb의 각 단계를 클릭하면 즉시 해당 계층으로 돌아갈 수 있게 한다.
- 계층 상태를 URL 또는 전역 상태로 관리해 새로고침/딥링크에도 유지되게 한다.

**탐지**:
- 세부 화면으로 4단계 이상 진입한 뒤 "지금 어느 파일, 어느 프레임을 보고 있는가"를 사용자에게 묻는 정지 테스트.
- 계층 전환 경로를 그래프로 그려 breadcrumb 부재 화면 수를 카운트.

**Bitvue 판정**: 미정 — 2단계(저장소 감사)에서 채움

### UIX-IA-010: 검색 결과에서 원래 문맥으로 이동할 수 없음

**분류**: UIX_IA · **심각도**: Medium · **탐지**: Interaction

**사용자 목표**:
특정 syntax 값이나 프레임을 검색해 찾은 뒤, 그 값이 있는 실제 위치(프레임, 트랙, 구간)에서 계속 작업하고 싶다.

**증상**:
- syntax field 검색(예: "qp_delta가 임계값 이상인 프레임 찾기")으로 결과 리스트를 얻지만, 결과 항목을 클릭해도 아무 데도 이동하지 않는다.
- 검색 결과 리스트가 별도의 모달/팝업으로만 표시되고 닫으면 검색 컨텍스트가 사라진다.
- 검색 결과 항목에 프레임 번호는 있지만 트랙/구간 정보가 없어 어느 트랙의 것인지 알 수 없다.

**원인**:
검색 기능을 "결과를 나열하는 것"까지만 요구사항으로 잡고, 결과에서 원본 데이터 위치로의 내비게이션(딥링크)을 별도 기능으로 취급하지 않았기 때문. 검색 인덱스와 뷰 상태 관리가 서로 다른 모듈에서 개발되어 연결 고리가 빠졌을 가능성도 있다.

**구현 냄새**:
- 검색 결과 데이터 모델에 위치 식별자(트랙 ID, 프레임 인덱스, 필드 경로)가 표시용 텍스트로만 존재하고 구조화된 값으로 없음.
- 검색 UI 컴포넌트가 다른 패널의 라우팅/선택 상태 setter에 접근할 수 없는 위치에 격리되어 있음.

**영향**:
검색이 "찾기"까지만 되고 "이동하기"가 안 되면, 사용자는 검색 결과를 손으로 옮겨 적어 다시 찾아가야 해서 검색 기능의 효용이 크게 줄어든다.

**권장**:
- 검색 결과 각 항목을 클릭하면 해당 트랙/구간/프레임/필드로 전체 UI 상태가 이동하도록 구현한다.
- 검색 결과 항목에 항상 계층 경로(breadcrumb 형태)를 함께 표시해 클릭 전에도 위치를 예측 가능하게 한다.
- 검색 후 이동한 화면에서 "검색으로 돌아가기"를 제공해 왕복 탐색을 지원한다.

**탐지**:

### UIX-IA-011: 필터가 어떤 패널에 적용됐는지 불명확

**분류**: UIX_IA · **심각도**: Medium · **탐지**: Visual · Interaction

**사용자 목표**:
지금 화면에 보이는 데이터가 필터링된 부분집합인지 전체인지, 어떤 조건으로 필터링됐는지 즉시 알고 싶다.

**증상**:
- NAL 유형 필터, 프레임 타입 필터(I/P/B), 심각도 필터 등을 걸어도 어느 패널까지 그 필터가 적용되는지(타임라인만? 신택스 뷰도?) 화면에 표시되지 않는다.
- 필터를 건 채로 다른 탭으로 이동했다가 돌아오면 필터가 여전히 걸려 있는지, 초기화됐는지 알 수 없다.
- 여러 필터(코덱 필터 + 심각도 필터 + 시간 범위 필터)가 동시에 걸려 있을 때 활성 필터 전체 목록을 한눈에 볼 곳이 없다.

**원인**:
필터 상태를 패널별 로컬 state로 각자 구현해, 어떤 필터가 전역(모든 패널 공통)이고 어떤 필터가 패널 로컬인지에 대한 설계 원칙이 없었기 때문. 필터 적용 범위에 대한 시각적 피드백(활성 필터 칩, 배지)도 별도로 설계되지 않았다.

**구현 냄새**:
- 필터 상태가 여러 컴포넌트에 각각 `useState`로 중복 선언되어 있고 서로 동기화되지 않음.
- 필터 적용 후 결과 개수(예: "128개 중 12개 표시 중")를 렌더링하는 공통 UI 패턴이 없음.

**영향**:
사용자가 "필터 때문에 데이터가 안 보이는 것"과 "실제로 데이터가 없는 것"을 구분하지 못해 잘못된 결론(버그로 오인하거나 반대로 실제 문제를 놓침)을 내릴 수 있다.

**권장**:
- 필터의 적용 범위(전역/패널 로컬)를 설계 시점에 명시적으로 결정하고 상태를 그에 맞는 위치(전역 스토어 vs 컴포넌트 로컬)에 둔다.
- 필터가 하나라도 활성화되어 있으면 항상 눈에 띄는 위치에 "활성 필터 칩" 목록과 전체 초기화 버튼을 표시한다.
- 필터링된 패널에는 "전체 N개 중 M개 표시" 형태의 카운트를 항상 노출한다.

**탐지**:
- 필터를 건 상태로 여러 패널을 오가며 필터 적용 범위가 일관되는지 수동 점검.
- 데이터가 0건으로 보이는 화면마다 "필터 때문인지 실제 데이터 없음인지"를 시각적으로 구분할 수 있는지 체크.

**Bitvue 판정**: 미정 — 2단계(저장소 감사)에서 채움

### UIX-IA-012: 프로젝트 수준 설정과 뷰 수준 설정 혼용

**분류**: UIX_IA · **심각도**: Medium · **탐지**: Domain review · Interaction

**사용자 목표**:
설정을 바꿀 때 그 변경이 "지금 보는 화면만"에 적용되는지 "이 프로젝트/파일 전체"에 적용되는지 예측하고 싶다.

**증상**:
- 색공간 변환 설정(YUV→RGB matrix)을 바꿨더니 프레임 인스펙터뿐 아니라 다른 탭에서 열어둔 비교 뷰까지 함께 바뀐다 — 혹은 반대로, 바뀌길 기대했는데 안 바뀐다.

**원인**:

**구현 냄새**:

- 설정 변경 함수가 스코프를 매개변수로 받지 않고 항상 같은 저장 위치에 write.

**영향**:
사용자가 설정을 바꿀 때마다 부작용을 예측할 수 없어 조심스러워지고, 실제로 의도치 않은 범위까지 바뀌어 다른 비교 대상의 조건이 오염되는 사고(특히 VQ-Probe의 색공간/정렬 전처리 설정)로 이어질 수 있다.

**권장**:
- 설정을 스코프별(애플리케이션 전역/프로젝트/파일/뷰)로 명확히 분리된 저장소에 둔다.
- 설정 UI에서 각 항목 옆에 적용 범위를 라벨로 표시한다 (예: "이 파일에만 적용" 배지).
- 스코프가 넓은 설정을 바꿀 때는 영향받는 다른 뷰 개수를 알려주는 확인 UX를 둔다.

**탐지**:
- 설정 변경 → 다른 탭/뷰에서 실제로 반영되는 범위를 표로 정리해 문서화된 의도와 대조.
- 설정 스토어 구조를 코드 리뷰해 스코프 필드가 명시적으로 존재하는지 확인.

### UIX-IA-013: 파일·트랙·프레임 선택 계층이 표현되지 않음

**분류**: UIX_IA · **심각도**: High · **탐지**: Visual · Interaction

**사용자 목표**:
여러 파일/트랙을 열어놓은 상태에서 "지금 어떤 파일의 어떤 트랙, 어떤 프레임"이 선택되어 활성 상태인지 항상 알고 싶다.

**증상**:
- 여러 파일을 동시에 열어둔 상태에서 현재 활성 파일이 어느 것인지 탭/사이드바 어디에도 강조 표시가 없다.
- 멀티 트랙 컨테이너(예: 여러 화질의 adaptive streaming 세트)를 열었을 때 트랙 선택 UI가 있지만 선택 상태가 다른 패널(신택스 뷰, hex 뷰)에 반영되는지 불확실하다.
- 비교 모드에서 "왼쪽 영상"과 "오른쪽 영상"에 각각 어떤 파일/프레임이 매핑되어 있는지 헷갈린다.

**원인**:
단일 파일·단일 트랙만 다루던 초기 설계에서 다중 파일/다중 트랙 지원을 추가하면서, "현재 선택"이라는 개념을 계층적 상태(파일 ID → 트랙 ID → 프레임 인덱스)로 명시적으로 모델링하지 않고 각 패널이 암묵적으로 "마지막으로 열린 것"을 기준으로 동작하도록 확장했기 때문.

**구현 냄새**:
- 전역 상태에 `activeFile`, `activeTrack` 같은 필드가 없거나, 있어도 일부 컴포넌트만 이를 구독하고 나머지는 자체 local state를 유지.
- 비교 모드의 좌/우 슬롯이 별도 컴포넌트 트리로 구현되어 선택 상태 동기화 로직이 중복 또는 누락.

**영향**:
다중 파일/트랙 작업 시 사용자가 잘못된 프레임을 비교하거나 잘못된 트랙의 데이터를 분석하는 실수를 저지르기 쉽고, 이는 특히 화질 비교 작업에서 결론 자체를 틀리게 만드는 심각한 문제로 이어진다.

**권장**:
- "현재 선택"을 파일 → 트랙 → 프레임의 계층적 전역 상태로 명시적으로 모델링하고 모든 패널이 이를 단일 소스로 구독한다.
- 활성 파일/트랙에는 항상 시각적 강조(테두리, 배경색, 굵은 라벨)를 일관되게 적용한다.
- 비교 모드에서는 좌/우 각각의 파일명·트랙·프레임 정보를 헤더에 상시 고정 표시한다.

**탐지**:
- 파일 2개, 트랙 2개 이상을 열어놓고 각 패널이 "현재 선택"을 일관되게 반영하는지 상호작용 테스트.
- 비교 모드에서 좌/우 슬롯 전환 시 모든 하위 패널(신택스, hex, metric)이 함께 전환되는지 확인.

**Bitvue 판정**: 미정 — 2단계(저장소 감사)에서 채움

### UIX-IA-014: 빈 패널을 계속 노출

**분류**: UIX_IA · **심각도**: Low · **탐지**: Visual

**사용자 목표**:
지금 볼 수 있는 데이터가 있는 패널과 없는 패널을 구분해 시간을 낭비하지 않고 싶다.

**증상**:
- 현재 코덱/파일에 해당하지 않는 패널(예: HEVC 파일인데 AV1 전용 Film Grain 패널)이 빈 상태로 계속 탭에 남아있다.
- 아직 로딩되지 않았거나 데이터가 없는 패널이 "빈 화면" 또는 placeholder 텍스트 없이 완전히 공백으로 남는다.
- 분석이 아직 완료되지 않은 metric 패널이 값 없이 빈 표로 표시되어, 사용자가 계산이 안 된 것인지 값이 0인 것인지 구분하지 못한다.

**원인**:
패널의 "표시 가능 여부"를 데이터 존재 여부와 연동하지 않고 항상 렌더링하도록 구현했기 때문. 빈 상태(empty state) 디자인을 별도 작업으로 간주하지 않고 기본 렌더링에 맡겨버린 경우가 흔하다.

**구현 냄새**:
- 조건부 렌더링 없이 모든 패널 컴포넌트가 항상 마운트되고, 데이터가 없을 때의 fallback UI가 없어 빈 테이블/빈 차트가 그대로 노출.
- 로딩 중 상태와 데이터 없음 상태가 동일한 빈 화면으로 렌더링되어 구분 불가.

**영향**:
사용자가 빈 패널을 눌러보고 나서야 "이건 해당 없음"임을 알게 되는 시행착오가 반복되고, 탭 개수가 실제 유효 정보량보다 많아 보여 전체 UI가 산만해진다.

**권장**:
- 현재 파일/코덱에 해당하지 않는 패널은 탭 자체를 숨기거나 명시적으로 비활성화하고 이유를 툴팁으로 설명한다.
- 로딩 중/데이터 없음/에러를 서로 다른 empty state 컴포넌트로 명확히 구분해 표시한다.
- 값이 0인 것과 계산되지 않은 것을 시각적으로 구분한다 (예: "—" vs "0").

**탐지**:
- 다양한 코덱/파일 조합으로 열어보며 빈 패널 비율을 카운트.
- 로딩 상태를 인위적으로 지연시켜 로딩 중 화면과 데이터 없음 화면이 실제로 다르게 렌더링되는지 확인.

### UIX-IA-015: 선택하지 않은 기능까지 eager load

**분류**: UIX_IA · **심각도**: Medium · **탐지**: Performance · Code

**사용자 목표**:
지금 보려는 화면이 빠르게 뜨길 바란다 — 아직 열어보지도 않은 다른 탭 때문에 기다리고 싶지 않다.

**증상**:
- 파일을 열면 아직 클릭도 안 한 Hex 뷰, MV 오버레이, 품질 비교 모듈까지 모든 탭의 초기 데이터 요청이 동시에 발생한다.
- 대형 파일을 열 때 초기 로딩 스피너가 길게 유지되는데, 실제로는 사용자가 원하는 Overview 화면과 무관한 백그라운드 계산(예: 전체 프레임 신택스 파싱)까지 함께 기다리고 있다.
- IPC/네트워크 탭을 열어보면 화면 전환 없이도 여러 무거운 커맨드(코덱별 파서, 메트릭 계산기)가 앱 시작 시점에 한꺼번에 호출된다.

**원인**:
프론트엔드 모듈 번들링과 백엔드 데이터 요청을 "탭 전환 시점에 지연 로드"가 아니라 "앱/파일 열기 시점에 전부 준비"하는 것이 구현하기 쉬웠기 때문. 특히 여러 패널이 공통 컨텍스트(파일 핸들)를 공유하도록 설계하면서, 초기화 코드를 한 곳에 몰아넣는 경우 흔히 발생한다.

**구현 냄새**:
- 코드 스플리팅(동적 import) 없이 모든 탭 컴포넌트가 최상위 번들에 포함되어 초기 로드에 함께 딸려옴.
- 파일 열기 커맨드 하나가 모든 코덱별 파싱/메트릭 계산을 동기적으로 트리거하고, 탭별로 필요할 때 요청하는 구조가 아님.

**영향**:
실제로 필요한 화면(Overview)조차 무관한 작업 때문에 늦게 뜨고, 대형 파일이나 고해상도 콘텐츠에서는 체감 지연이 수 초 단위로 커져 도구 전체가 느리다는 인상을 준다.

**권장**:
- 탭/패널 단위로 코드 스플리팅(동적 import)을 적용해 실제로 클릭한 탭의 번들만 로드한다.
- 백엔드 데이터 요청도 탭 활성화 시점에 지연 발행(lazy fetch)하고, 필요하면 백그라운드 프리페치는 유휴 시간에 우선순위 낮춰 수행한다.
- 초기 화면(Overview)에 필요한 최소 데이터만 우선 로드하고 나머지는 점진적으로 채운다(progressive disclosure).

**탐지**:
- 파일 열기 직후 네트워크/IPC 호출 타임라인을 프로파일링해 아직 열지 않은 탭에 대한 요청이 있는지 확인.
- 번들 분석 도구로 초기 번들 크기에 미사용 탭 컴포넌트가 포함되어 있는지 점검.
