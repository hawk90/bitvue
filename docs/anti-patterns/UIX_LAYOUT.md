# Anti-Pattern Catalog — UIX_LAYOUT: 레이아웃과 패널

이 문서는 더 큰 안티패턴 카탈로그의 일부입니다 (전체 목차는 `docs/anti-patterns/INDEX.md` 참고, 별도 작성 중). 이 파일은 UI/UX+Tauri Phase 3 웨이브에 속하며, Phase 1(Rust/미디어 엔지니어링)과 Phase 2(VQ-Probe 도메인)에 이어 Bitvue의 다중 도킹 패널 데스크톱 셸(Stream Tree, Player, Timeline, Syntax, Hex, Selection Info, Status Bar 등) 레이아웃 문제를 다룬다. 각 항목은 1단계(일반 참조 카탈로그)이며, 2단계에서 Bitvue 저장소를 실제로 감사해 "Bitvue 판정"을 채운다. Bitvue의 Mode 메뉴는 이미 목표 메뉴 구조와 코덱별 패널/오버레이 가시성을 문서화해 두었으므로(`docs/UX_PARITY_MATRIX.md` §10, 구 스펙의 메뉴-구조 섹션에서 이관됨), 감사 시 특히 UIX-LAYOUT-006/007/008을 그 내용과 교차 검증할 가치가 있다.

---

### UIX-LAYOUT-001: 모든 패널을 동시에 보여줌

**분류**: UIX_LAYOUT · **심각도**: High · **탐지**: Visual

**사용자 목표**:
지금 하고 있는 작업(예: 특정 프레임의 QP 분포 확인)에 필요한 정보에 집중하고 싶다.

**증상**:
- 첫 실행 화면에 Stream Tree, Player, Timeline, Syntax, Hex, Selection Info, Status Bar가 모두 열려 있어 각 패널의 실사용 영역이 화면의 1/7 수준으로 쪼그라든다.
- 사용자가 Hex 패널을 한 번도 열어본 적이 없어도 매번 화면 한켠을 차지한다.
- 실제 작업(재생, 프레임 탐색)에 쓰이는 Player 패널이 다른 보조 패널들과 동일한 시각적 비중으로 취급된다.

**원인**:
"모든 기능을 항상 접근 가능하게 하자"는 발상이 "모든 패널을 항상 화면에 렌더링하자"로 잘못 번역된 것. 패널 표시 여부와 패널 존재 여부를 구분하지 않는 초기 레이아웃 설계.

**구현 냄새**:
- 레이아웃 설정에 패널별 `visible: boolean`이 없고 전부 하드코딩된 도킹 트리 하나만 존재.
- 앱 최초 실행 시 기본 레이아웃이 "전부 펼침"이며, 사용자가 필요 없는 패널을 접었다가도 다음 파일을 열면 다시 전부 펼쳐짐.
- 패널 컴포넌트가 하나의 `<Workspace>` 루트에 조건 없이 나열되어 있음.

**영향**:
정보 밀도가 낮아 핵심 작업(디코딩 이슈 진단)에 쓸 화면 면적이 부족해짐. 신규 사용자는 어느 패널이 지금 중요한지 판단 기준을 못 얻어 인지 부하가 커짐. 전문가 사용자도 화면 재배치를 매 세션 반복해야 함.

**권장**:
- 코덱/작업 모드별 기본 프리셋(예: "빠른 검사" = Player+Timeline만, "신택스 디버깅" = Syntax+Hex+Selection Info)을 제공하고 최초 실행 시 이 중 하나를 기본값으로.
- 각 패널에 독립적인 표시/숨김 토글을 두고 마지막 상태를 세션 간 유지.
- 패널 중요도에 따라 기본 크기 비율을 차등화(Player/Timeline 우선).

**탐지**:
- 최초 설치 후 앱을 열어 화면에 동시에 보이는 패널 수를 센다. 스크린샷을 찍어 각 패널의 픽셀 면적을 측정, 특정 임계치(예: 5개 이상 동시 표시) 초과 여부 확인.
- 신규 사용자 대상 5분 사용성 테스트에서 "지금 화면에서 뭘 봐야 할지 모르겠다"는 발화가 나오는지 관찰.

**Bitvue 판정**: 미정 — 2단계(저장소 감사)에서 채움

### UIX-LAYOUT-002: 좁은 화면에서도 고정 폭 패널 유지

**분류**: UIX_LAYOUT · **심각도**: High · **탐지**: Visual

**사용자 목표**:
노트북 화면이나 창을 반으로 나눠 쓰는 환경에서도 핵심 패널(Player, Syntax)을 온전히 보고 싶다.

**증상**:
- 13인치 노트북에서 창을 열면 Stream Tree가 300px, Hex 패널이 400px를 고정으로 차지해 Player가 200px 이하로 눌린다.
- 창을 아무리 좁혀도 사이드 패널 폭이 줄지 않고, 대신 Player/Timeline 같은 중심 콘텐츠 영역만 계속 줄어들다가 음수 폭이 되어 내용이 잘린다.
- 외부 4K 모니터에서는 반대로 고정 폭 패널이 화면 대비 지나치게 좁아 보이는데 늘어나지 않는다.

**원인**:
패널 폭을 픽셀 고정값으로 하드코딩하고, 가변 영역(주로 중앙 콘텐츠)이 "나머지 공간을 흡수"하는 flex 모델을 처음부터 고려하지 않음. 대상 해상도를 개발자의 개발 모니터(예: 27인치) 하나로만 가정.

**구현 냄새**:
- CSS/레이아웃 정의에 `width: 320px` 같은 고정값이 패널 컨테이너에 박혀 있고 `min-width`/`max-width` 상한·하한이 없음.
- 컨테이너 쿼리나 뷰포트 폭 기반 반응형 분기(breakpoint)가 전혀 없음.
- 창 최소 크기(`minWidth`) 설정이 사이드 패널 총합보다 작게 잡혀 있어 렌더링이 깨질 수 있는 조합을 애초에 차단하지 못함.

**영향**:
노트북/듀얼 세로 모니터 등 비표준 해상도 사용자가 핵심 작업 영역을 확보하지 못해 도구를 사실상 못 씀. 창 크기 조절이라는 기본 OS 상호작용이 깨진 UI를 만들어냄.

**권장**:
- 패널 폭을 비율(`flex-grow`/`fr` 단위) 기반으로 설계하고, 절대 폭은 min/max 범위로만 제약.
- 창 폭이 임계치 이하로 줄면 보조 패널을 자동으로 접거나 탭으로 전환하는 반응형 규칙 도입.
- 최소 창 크기를 "모든 필수 패널이 최소 유효 폭을 유지할 수 있는 값"으로 역산해 설정.

**탐지**:
- 창을 1024px, 1280px, 1920px, 2560px 폭으로 각각 리사이즈하며 스크린샷 비교, 콘텐츠 잘림/음수 폭 여부 확인.
- 자동화 테스트로 뷰포트 폭을 스윕하며 각 패널의 `getBoundingClientRect().width`가 0 이하가 되는 지점을 탐지.

**Bitvue 판정**: 미정 — 2단계(저장소 감사)에서 채움

### UIX-LAYOUT-003: splitter 위치를 저장하지 않음

**분류**: UIX_LAYOUT · **심각도**: Medium · **탐지**: Interaction

**사용자 목표**:
내가 조정한 패널 크기 배치가 다음에 앱을 열었을 때도 그대로 유지되길 바란다.

**증상**:
- Syntax와 Hex 패널 사이 스플리터를 드래그해 60:40으로 조정해도, 앱을 재시작하면 기본 50:50으로 되돌아간다.
- 같은 세션 내에서도 파일을 새로 열면(스트림 교체) 레이아웃이 초기화된다.
- 멀티 모니터 환경에서 창을 옮겼다가 돌아오면 스플리터 위치가 리셋되는 경우도 있다.

**원인**:
스플리터 컴포넌트의 상태(각 패널 크기 비율)가 컴포넌트 로컬 state로만 존재하고, 영속 저장소(로컬 설정 파일, localStorage 등)에 반영되는 경로가 없음.

**구현 냄새**:
- 레이아웃 크기 정보가 `useState`에만 있고 저장 시점(`onDragEnd`, `beforeunload` 등)에 디스크/설정으로 쓰는 코드가 없음.
- 앱 시작 시 레이아웃을 항상 하드코딩된 기본값으로 초기화.
- 스트림/파일 전환 로직이 레이아웃 상태까지 함께 리셋하는 공용 "앱 상태 초기화" 함수를 재사용하고 있음.

**영향**:
전문가 사용자가 반복 작업마다 레이아웃을 재조정해야 해서 누적 시간 손실이 큼. "설정이 저장되지 않는 도구"라는 인상은 신뢰도를 떨어뜨림.

**권장**:
- 스플리터 크기/패널 표시 상태를 워크스페이스 설정으로 취급해 파일 전환과 무관하게 영속화.
- 드래그 종료 시 디바운스된 저장, 앱 종료 시 최종 상태 flush.
- 스트림 전환은 "콘텐츠"만 리셋하고 "레이아웃"은 건드리지 않도록 상태를 분리.

**탐지**:
- 스플리터를 임의 위치로 옮긴 뒤 앱 재시작 → 위치 비교 회귀 테스트.
- 파일 A 열기 → 레이아웃 조정 → 파일 B 열기 → 레이아웃 유지 여부 확인.

**Bitvue 판정**: 미정 — 2단계(저장소 감사)에서 채움

### UIX-LAYOUT-004: 패널 최소 크기가 없어 내용이 붕괴

**분류**: UIX_LAYOUT · **심각도**: High · **탐지**: Visual

**사용자 목표**:
패널을 아무리 작게 줄여도 최소한 무엇이 있는지는 알아볼 수 있어야 한다.

**증상**:
- Selection Info 패널을 좁히면 숫자 컬럼(예: QP, MV x/y)이 겹쳐 보이거나 텍스트가 서로 침범한다.
- Timeline을 세로로 좁히면 프레임 썸네일이 1px 폭으로 뭉개진다.
- Stream Tree를 극단적으로 좁히면 트리 아이콘과 라벨이 겹쳐 클릭 대상을 구분할 수 없다.

**원인**:
스플리터/도킹 프레임워크가 자식 콘텐츠의 실제 렌더 요구사항과 무관하게 임의의 픽셀 값까지 리사이즈를 허용함. 패널 내부 콘텐츠가 "이 이하로는 의미가 없다"는 자체 최소 폭/높이를 선언하지 않음.

**구현 냄새**:
- 스플리터 설정에 `minSize`가 없거나 0으로 되어 있음.
- 내부 콘텐츠가 `overflow: hidden`만으로 잘라내고 있어 붕괴가 시각적으로 어색하게(겹침, 잘림) 나타남.
- 반응형 축약 뷰(아이콘만 표시 등)가 별도로 구현되어 있지 않아 "정상 뷰의 축소판"이 아니라 "정상 뷰가 찌그러진 것"이 된다.

**영향**:
사용자가 실수로 패널을 과도하게 좁혔을 때 데이터를 오독하거나(겹친 숫자를 잘못 읽음) 조작 불가 상태(클릭 대상 소실)에 빠짐. 특히 정밀 수치를 다루는 분석 도구에서는 오독이 곧 잘못된 결론으로 이어질 수 있어 심각도가 높음.

**권장**:
- 각 패널에 콘텐츠 기반 `minWidth`/`minHeight`를 정의하고 스플리터가 이를 하드 제약으로 존중하도록.
- 최소 크기 이하로 줄이려는 제스처는 "패널 접기(collapse to tab/icon)"로 전환.
- 축소 상태 전용의 단순화된 표시(예: 아이콘 + 배지)를 별도로 설계.

**탐지**:
- 각 패널을 1px까지 강제로 드래그해보는 시각 회귀 테스트, 겹침/잘림 스크린샷 diff.
- 최소 크기 도달 시 자동으로 접힘 상태로 전환되는지 인터랙션 테스트.

**Bitvue 판정**: 미정 — 2단계(저장소 감사)에서 채움

### UIX-LAYOUT-005: 중요한 player가 부가 패널에 밀림

**분류**: UIX_LAYOUT · **심각도**: High · **탐지**: Visual

**사용자 목표**:
비트스트림 분석 도구를 열면 가장 먼저, 가장 크게 영상(Player)을 보고 싶다 — 이것이 모든 분석의 출발점이다.

**증상**:
- 기본 레이아웃에서 Player가 화면의 25% 이하를 차지하고, Stream Tree/Hex/Syntax 패널이 더 넓은 면적을 가져간다.
- 창을 처음 띄우면 Player가 화면 구석에 작게 배치되어 있어 사용자가 직접 찾아 키워야 한다.
- 도킹 레이아웃 저장/복원 로직이 모든 패널을 동등한 "타일"로 취급해 우선순위 개념이 없다.

**원인**:
도킹 시스템을 범용 그리드로 설계하면서 "이 앱에서 가장 중요한 콘텐츠가 무엇인가"라는 정보 위계(hierarchy) 결정을 UI 프레임워크에 떠넘김. 결과적으로 모든 패널이 동일한 기본 크기 정책을 공유.

**구현 냄새**:
- 레이아웃 트리 정의에 패널별 `defaultSize`가 균등 분할(모두 동일 비율)로 되어 있음.
- Player 컴포넌트가 다른 보조 패널과 동일한 `Panel` 래퍼를 사용해 시각적으로도 구조적으로도 차별화 요소가 없음.
- "핵심 vs 보조" 패널 분류가 코드/설정 어디에도 명시되어 있지 않음.

**영향**:
분석 워크플로의 진입점이 흐려짐 — 사용자가 매번 레이아웃을 수동 조정해야 "정상적으로" 도구를 쓸 수 있음. 신규 사용자는 이 도구의 중심이 무엇인지 첫 화면만으로 파악하지 못함.

**권장**:
- 기본 레이아웃에서 Player(+Timeline)가 화면의 과반 이상을 차지하도록 명시적 가중치 부여.
- 패널을 "primary(Player/Timeline)"와 "auxiliary(Stream Tree/Hex/Syntax/Selection Info)"로 코드 레벨에서 분류하고 기본 크기 정책을 분리.
- 모든 프리셋(§UIX-LAYOUT-007)에서 Player 최소 비율 하한을 강제.

**탐지**:
- 최초 실행 화면 스크린샷에서 각 패널의 픽셀 면적 비율 측정, Player가 최대 면적 패널인지 확인.
- 사용자 테스트에서 "이 화면에서 가장 먼저 보라고 만든 곳이 어디 같냐"는 질문에 대한 응답과 실제 의도 일치 여부.

**Bitvue 판정**: 미정 — 2단계(저장소 감사)에서 채움

### UIX-LAYOUT-006: 패널을 닫은 뒤 다시 찾기 어려움

**분류**: UIX_LAYOUT · **심각도**: Medium · **탐지**: Interaction

**사용자 목표**:
실수로 혹은 의도적으로 닫은 패널(예: Hex)을 다시 열고 싶을 때 쉽게 찾을 수 있어야 한다.

**증상**:
- 패널의 X 버튼을 눌러 닫은 뒤, 이를 되돌리는 메뉴 항목/버튼을 찾지 못해 사용자가 앱을 재시작하거나 레이아웃 프리셋을 초기화한다.
- View 메뉴나 유사 위치에 "패널 표시" 토글 목록이 없거나, 있어도 닫은 패널만 골라 다시 켤 수 있는 대칭적 UI가 아니다.
- 우클릭 컨텍스트 메뉴 등 대체 경로도 존재하지 않는다.

**원인**:
"패널 닫기"라는 단방향 동작만 구현하고 그 역동작("패널 열기")을 위한 발견 가능한(discoverable) 진입점을 별도로 설계하지 않음. 닫기 버튼은 눈에 잘 띄지만 복구 경로는 숨겨져 있거나 없는 비대칭 설계.

**구현 냄새**:
- 패널 표시 상태 토글 함수는 존재하지만 이를 호출하는 메뉴 UI가 없거나 일부 패널만 등록되어 있음.
- View 메뉴 항목이 정적으로 하드코딩되어 있어 새 패널 추가 시 토글 목록 갱신을 깜빡하기 쉬운 구조.

**영향**:
사용자가 패널을 실수로 닫으면 복구를 위해 워크스페이스 초기화라는 과도한 조치를 취하게 되어 다른 커스터마이징(스플리터 위치 등)까지 함께 잃는다. 이는 애초에 "패널 닫기"라는 안전해 보이는 동작을 위험한 동작으로 체감시킨다.

**권장**:
- View(또는 Window) 메뉴에 모든 패널을 나열하는 체크박스형 토글 목록을 두고, 코드베이스의 패널 레지스트리에서 자동 생성.
- Bitvue의 Mode 메뉴가 이미 코덱별 패널/오버레이 가시성을 문서화하고 있으므로(`docs/UX_PARITY_MATRIX.md` §10), 이 문서에 정의된 패널 집합과 "닫기/열기" 토글 목록이 실제로 1:1 대응하는지 확인.
- 닫기 동작에 대한 즉각적인 되돌리기(toast + "실행 취소") 제공을 고려.

**탐지**:
- 각 패널을 하나씩 닫아본 뒤 메뉴에서 다시 열 수 있는지 전수 점검하는 시나리오 테스트.
- `docs/UX_PARITY_MATRIX.md` §10의 패널/오버레이 목록과 실제 View 메뉴 항목을 대조하는 체크리스트.

**Bitvue 판정**: 미정 — 2단계(저장소 감사)에서 채움

### UIX-LAYOUT-007: workspace preset이 없음

**분류**: UIX_LAYOUT · **심각도**: Medium · **탐지**: Interaction

**사용자 목표**:
작업 성격(빠른 프레임 검사, 신택스 디버깅, 픽셀 비교 등)에 따라 레이아웃을 한 번에 전환하고 싶다.

**증상**:
- 사용자가 "Hex+Syntax만 크게" 보고 싶을 때마다 스플리터를 수동으로 드래그해야 하고, 나중에 원래 레이아웃으로 돌아갈 방법이 없다.
- 저장된 프리셋 개념이 아예 없어 매 세션 동일한 수동 조정을 반복.
- 여러 작업을 오가는 전문가 사용자가 "레이아웃 A ↔ 레이아웃 B" 전환에 매번 수십 초를 소모.

**원인**:
레이아웃을 단일 가변 상태로만 설계하고, 이름 붙여 저장·전환 가능한 "프리셋" 개념을 데이터 모델에 넣지 않음.

**구현 냄새**:
- 레이아웃 상태가 단일 객체(현재 상태)로만 존재하고 프리셋 목록을 담는 배열/저장소가 없음.
- 프리셋 저장/불러오기 UI(이름 짓기, 목록, 삭제)가 없음.

**영향**:
반복 작업 효율이 떨어지고, 동료 간 "이 레이아웃으로 봐" 같은 공유도 불가능(파일로 내보낼 프리셋 자체가 없으므로). Bitvue의 Mode 메뉴가 코덱별로 다른 오버레이/패널 조합을 요구하는 만큼(`docs/UX_PARITY_MATRIX.md` §10), 프리셋 부재는 코덱 전환마다 수동 재배치를 강제하는 문제로 직결된다.

**권장**:
- 최소한 "기본", "신택스 디버깅", "픽셀/오버레이 비교" 등 몇 가지 내장 프리셋 제공.
- 사용자가 현재 레이아웃을 이름 붙여 저장하고 단축키/메뉴로 전환할 수 있게.
- 코덱 전환(Mode 메뉴) 시 해당 코덱에 유효한 프리셋으로 자동 제안(강제 전환은 아님).

**탐지**:
- 프리셋 저장 → 레이아웃 변경 → 프리셋 재적용 → 원래 상태로 정확히 복원되는지 회귀 테스트.
- 코덱 전환 시나리오에서 프리셋 제안 UI 노출 여부 확인.

**Bitvue 판정**: 미정 — 2단계(저장소 감사)에서 채움

### UIX-LAYOUT-008: 코덱에 필요 없는 패널도 표시

**분류**: UIX_LAYOUT · **심각도**: Medium · **탐지**: Domain review

**사용자 목표**:
현재 열려 있는 스트림의 코덱과 무관한 컨트롤/패널로 혼란받고 싶지 않다.

**증상**:
- VP9 스트림을 열었는데 HEVC 전용 오버레이 토글(예: PU Type, MV Heat Map)이 그대로 활성 메뉴 항목으로 남아있다.
- AVC 스트림에서 AV1/VP9 전용 옵션(Block Type, Efficiency Map)이 클릭 가능한 상태로 노출되어, 눌러도 아무 일도 없거나 에러를 낸다.
- Selection Info 패널이 현재 코덱에 존재하지 않는 신택스 필드(예: AVC에서 AV1의 segmentation 관련 필드)를 빈 값으로 계속 표시한다.

**원인**:
UI 컴포넌트 트리가 코덱 문맥(codec context)을 인지하지 못하고 "가능한 모든 필드/토글을 항상 렌더링"하는 정적 목록으로 구현됨. `docs/UX_PARITY_MATRIX.md` §10에 정의된 코덱별 F키/오버레이 매핑이 실제 메뉴 렌더링 로직에 반영되지 않음.

**구현 냄새**:
- Mode 메뉴/Info Overlays 목록이 코덱 조건 없이 하드코딩된 배열 하나로 렌더링됨.
- 오버레이 토글 컴포넌트에 `disabled` 처리는 있지만 "숨김" 처리가 없어 무의미한 항목이 계속 시야에 남음(또는 반대로 아무 처리 없이 클릭 시 조용히 실패).
- 코덱별 유효 필드 매핑표가 문서(`VQA_PARITY_SPEC_V3.md` §4.4 등)에만 존재하고 코드의 단일 진실 공급원(source of truth)으로 연결되어 있지 않음.

**영향**:
사용자가 "이 코덱에서 이 기능이 되나?"를 실제로 눌러보기 전까지 알 수 없어 시행착오 비용이 큼. 전문가 사용자에게는 툴에 대한 신뢰도 저하(사용 불가능한 옵션이 항상 보이는 것은 미완성 인상을 줌).

**권장**:
- `docs/UX_PARITY_MATRIX.md` §10의 코덱별 F키/오버레이 매핑을 코드의 코덱 capability 테이블로 이식하고, 메뉴/패널 렌더링이 이를 단일 진실 공급원으로 참조.
- 코덱에 없는 오버레이/필드는 disabled가 아니라 아예 숨김(또는 별도 "이 코덱 미지원" 섹션으로 묶어 축소 표시).
- 코덱 전환 시 현재 활성화된 오버레이 중 새 코덱에 없는 것은 자동으로 끔.

**탐지**:
- 코덱별(AVC/HEVC/VP9/AV1/VVC)로 스트림을 열어보며 Mode 메뉴/Selection Info에 노출되는 항목을 `docs/UX_PARITY_MATRIX.md` §10 매핑표와 대조.
- 비활성 코덱 전용 토글을 강제로 클릭했을 때의 동작(무반응/에러/크래시) 확인.

**Bitvue 판정**: 미정 — 2단계(저장소 감사)에서 채움

### UIX-LAYOUT-009: panel resize가 매 pixel마다 무거운 계산 유발

**분류**: UIX_LAYOUT · **심각도**: High · **탐지**: Performance

**사용자 목표**:
스플리터를 드래그하는 동안 화면이 끊김 없이 부드럽게 따라와야 한다.

**증상**:
- Syntax 패널 폭을 드래그로 조절하는 동안 프레임레이트가 눈에 띄게 떨어지고, 드래그가 마우스 커서보다 뒤처져 따라온다.
- 드래그를 멈춘 뒤에도 잠시 동안 UI가 프리징된다.
- 특히 Hex 패널(대용량 바이트 그리드)이나 Syntax 패널(깊은 트리)의 폭을 바꿀 때 증상이 심하다.

**원인**:
스플리터의 `onDrag` 콜백이 매 픽셀 이동마다 자식 패널 내부의 무거운 재계산(가상 스크롤 재측정, 신택스 트리 전체 재레이아웃, 텍스트 줄바꿈 재계산 등)을 동기적으로 트리거함. 리사이즈 중간 상태와 최종 상태를 구분하지 않음.

**구현 냄새**:
- 드래그 이벤트 핸들러에 디바운스/쓰로틀이 전혀 없이 `setState`가 매 `mousemove`마다 호출됨.
- 자식 패널이 `width` prop 변경을 감지해 매번 전체 콘텐츠(가상 리스트, 신택스 트리 등)를 처음부터 다시 계산.
- 리사이즈 중에는 "빈 플레이스홀더/저해상도 미리보기"로 대체하는 최적화 경로가 없음.

**영향**:
드래그라는 가장 기본적인 조작이 버벅여 도구 전체의 반응성 인상을 해침. 대용량 스트림(4K/8K, 긴 시퀀스)일수록 체감이 심해져 정작 이 도구가 가장 필요한 무거운 작업에서 가장 불편해지는 역설이 발생.

**권장**:
- 드래그 중에는 스플리터 자체의 위치만 갱신(가벼운 CSS transform)하고, 자식 패널의 무거운 재계산은 `mouseup`(드래그 종료) 시점에 한 번만 수행.
- 드래그 중 자식 콘텐츠는 낮은 비용의 자리표시자(고정 스켈레톤)로 렌더링하는 옵션 고려.
- 리사이즈 콜백에 requestAnimationFrame 기반 쓰로틀 적용.

**탐지**:
- 스플리터를 빠르게 드래그하며 프레임레이트/입력 지연을 프로파일링(Chrome DevTools Performance 탭 등).
- 대용량 스트림(4K, 긴 GOP) 로드 상태에서 드래그 시 CPU 사용률과 프레임 드롭 측정.

**Bitvue 판정**: 미정 — 2단계(저장소 감사)에서 채움

### UIX-LAYOUT-010: scroll container가 중첩됨

**분류**: UIX_LAYOUT · **심각도**: Medium · **탐지**: Interaction

**사용자 목표**:
마우스 휠로 스크롤할 때 내가 의도한 영역(예: Syntax 트리)만 스크롤되길 바란다.

**증상**:
- Syntax 패널 안에서 스크롤하다가 트리 끝에 도달하면 스크롤 이벤트가 부모 컨테이너로 "새어나가" 전체 워크스페이스가 스크롤되거나, 반대로 의도한 패널이 아니라 바깥쪽 패널이 스크롤된다.
- Hex 뷰 안에 있는 좁은 서브패널(예: ASCII 사이드바)에서 스크롤하면 Hex 뷰 전체가 함께 스크롤되는 등 스크롤 소유권이 불명확하다.
- 트랙패드 관성 스크롤 시 여러 컨테이너가 동시에 반응해 화면이 어지럽게 움직인다.

**원인**:
여러 패널이 독립적인 스크롤 컨테이너(`overflow: auto/scroll`)를 겹겹이 중첩해 배치하면서, 스크롤 이벤트의 경계(scroll boundary)와 전파 차단(overscroll containment) 처리를 하지 않음.

**구현 냄새**:
- 중첩된 `overflow: auto` 요소들에 `overscroll-behavior: contain`(또는 동등한 이벤트 차단 로직)이 설정되어 있지 않음.
- 스크롤 가능 영역의 경계가 시각적으로 구분되지 않아(스크롤바만으로 판단해야 함) 사용자가 어느 영역에 커서를 둬야 할지 예측하기 어려움.
- 가상 스크롤 라이브러리와 네이티브 스크롤 컨테이너가 같은 패널 안에 혼재되어 스크롤 이벤트 소유권이 이중으로 걸림.

**영향**:
탐색(navigation)이라는 가장 빈번한 조작이 예측 불가능해져 사용자가 "지금 어느 영역을 스크롤하고 있는지" 매번 확인해야 하는 인지 부담이 생김. 특히 Hex/Syntax처럼 스크롤이 핵심 탐색 수단인 패널에서 치명적.

**권장**:
- 모든 독립 스크롤 컨테이너에 `overscroll-behavior: contain`을 적용해 경계에서 스크롤 전파를 차단.
- 스크롤 가능 영역에 시각적 경계(그림자, 테두리)를 줘 소유권을 명확히.
- 중첩이 꼭 필요한 경우 안쪽 컨테이너 하나만 스크롤 가능하도록 바깥 컨테이너는 `overflow: hidden` 고정.

**탐지**:
- 각 패널 안에서 스크롤 끝까지 이동한 뒤 계속 휠을 굴려 상위 컨테이너가 반응하는지 확인.
- 트랙패드 관성 스크롤 시나리오를 수동 QA에 포함.

**Bitvue 판정**: 미정 — 2단계(저장소 감사)에서 채움

### UIX-LAYOUT-011: sticky header가 데이터 영역을 과도하게 가림

**분류**: UIX_LAYOUT · **심각도**: Medium · **탐지**: Visual

**사용자 목표**:
Hex/Syntax처럼 긴 목록을 스크롤할 때 컬럼 헤더(오프셋, 필드명 등)는 계속 보이되, 실제 데이터를 가리지 않았으면 한다.

**증상**:
- Hex 뷰를 스크롤할 때 sticky offset 헤더 + sticky 컬럼 레이블이 이중으로 겹쳐 화면 상단 15~20%를 차지, 특히 세로로 좁힌 패널에서는 유효 데이터 행이 몇 줄 안 남는다.
- Syntax 트리에서 sticky 상위 노드 경로(breadcrumb 형태)가 계속 쌓여 스크롤할수록 헤더 영역이 늘어나는 경우도 있다.
- 헤더가 반투명 없이 불투명 배경으로 데이터를 완전히 덮어, 헤더 바로 아래 행이 시각적으로 "잘린" 것처럼 보인다.

**원인**:
"헤더는 항상 보여야 좋다"는 규칙을 패널 높이나 콘텐츠 밀도에 대한 고려 없이 일률 적용. sticky 요소가 몇 겹으로 중첩될 수 있는지, 총 높이가 패널 가용 공간 대비 얼마나 되는지 예산(budget)을 두지 않음.

**구현 냄새**:
- sticky 헤더 높이가 고정 픽셀로 여러 레벨(오프셋 행 + 컬럼 레이블 + breadcrumb 등) 하드코딩되어 있고 패널이 좁아져도 줄어들지 않음.
- 헤더 CSS `z-index`/배경이 데이터 영역과 시각적으로 명확히 분리되지 않아 겹침이 "의도된 것"인지 "버그"인지 구분 안 됨.
- 패널 높이가 헤더 총 높이보다 작아지는 극단적 케이스에 대한 처리(헤더 자동 축소/생략)가 없음.

**영향**:
좁은 패널에서 실질적으로 볼 수 있는 데이터 행 수가 급감해 스크롤 빈도가 늘고 탐색 효율이 떨어짐. 특히 Hex 뷰처럼 대용량 데이터를 다루는 패널에서 헤더가 화면을 잠식하면 도구의 핵심 기능이 훼손됨.

**권장**:
- sticky 헤더 총 높이에 상한을 두고, 패널이 일정 높이 이하로 좁아지면 헤더를 축약 모드(1줄)로 전환.
- 헤더에 약간의 반투명/블러 처리를 줘 데이터가 "지나가는" 느낌을 주고 완전 은폐를 피함.
- breadcrumb류 sticky 요소는 개수 상한을 두고 초과 시 생략 부호(...)로 축약.

**탐지**:
- 패널을 최소 높이까지 좁혀가며 sticky 헤더가 차지하는 비율(%)을 측정, 특정 임계치(예: 30%) 초과 여부 확인.
- 스크롤 시 헤더 바로 아래 행이 실제로 클릭/선택 가능한지(가려서 히트박스가 어긋나지 않는지) 인터랙션 테스트.

### UIX-LAYOUT-012: modal이 장시간 작업을 막음

**분류**: UIX_LAYOUT · **심각도**: High · **탐지**: Interaction

**사용자 목표**:
프레임 추출이나 내보내기처럼 시간이 걸리는 작업을 백그라운드로 돌리면서 동시에 다른 프레임을 계속 분석하고 싶다.

**증상**:
- "Extract Frames..." 실행 중 모달 진행률 창이 뜨고, 이 창이 닫히기 전까지 나머지 UI(Player, Timeline 등)를 전혀 조작할 수 없다.
- 대용량 스트림에서 익스포트가 수십 초~수 분 걸리는 동안 사용자는 화면 앞에서 기다리는 것 외에 할 수 있는 일이 없다.
- 진행률 모달을 실수로 닫으면(또는 취소 버튼이 없어) 작업 자체가 중단되는지 백그라운드 지속되는지 불명확하다.

**원인**:
장시간 실행 작업(프레임 추출, NAL/OBU 유닛 저장, 비교 익스포트 등)의 진행 상태 표시를 "모달 다이얼로그"라는 본질적으로 블로킹 UI 패턴으로 구현. 진행률 표시와 입력 차단을 분리하지 않음.

**구현 냄새**:
- 진행률 컴포넌트가 `<Modal>` 래퍼 안에 있고, 모달 오버레이가 배경 클릭/키보드 입력을 전부 가로챔(`pointer-events: none` on backdrop 부재).
- 작업 취소(cancel) API/버튼이 없거나, 있어도 실제 백엔드 작업(Rust 쪽 추출 스레드 등)에 취소 신호를 전달하지 못함.
- 작업 상태가 전역 상태(예: 알림 센터, 상태 바)로 승격되지 않고 모달 컴포넌트 로컬 state에만 존재해 모달을 닫으면 진행 상황을 더 이상 알 수 없음.

**영향**:
전문가 사용자의 작업 병렬성을 원천 차단해 생산성이 크게 떨어짐. 특히 4K/8K 대용량 스트림 익스포트처럼 실행 시간이 긴 작업일수록 피해가 커짐.

**권장**:
- 장시간 작업은 비차단(non-blocking) 방식으로 전환: 상태 바 또는 알림 트레이에 진행률 표시, 나머지 UI는 계속 조작 가능.
- 명시적 취소 버튼을 제공하고 백엔드 작업까지 실제로 중단시킴.
- 모달은 "예/아니오" 같은 즉답형 확인에만 한정하고, 진행률 표시에는 사용하지 않는 원칙을 UI 가이드라인화.

**탐지**:
- 대용량 스트림으로 프레임 추출을 실행하는 동안 다른 패널(Player 재생, Timeline 스크럽)을 조작해 응답하는지 확인.
- 진행 중 취소 버튼을 눌렀을 때 실제로 파일 쓰기가 중단되는지(디스크 I/O 모니터링) 확인.

### UIX-LAYOUT-013: floating panel이 핵심 데이터를 덮음

**분류**: UIX_LAYOUT · **심각도**: Medium · **탐지**: Visual

**사용자 목표**:
호버 툴팁이나 미니 컨트롤 같은 부유(floating) 요소가 지금 보고 있는 핵심 데이터를 가리지 않았으면 한다.

**증상**:
- 프레임 위에서 블록을 호버하면 나타나는 상세 툴팁이 항상 커서 오른쪽 아래 고정 오프셋으로 뜨는데, 화면 우하단 근처에서는 이 위치가 Player 밖으로 나가거나 Selection Info 패널을 덮어버린다.
- QP 히트맵 범례(legend)가 플로팅 오버레이로 항상 같은 좌표에 고정되어, 줌인한 프레임의 관심 영역과 겹친다.
- 여러 개의 플로팅 요소(툴팁 + 범례 + 미니맵)가 동시에 뜨면 서로 겹쳐 어느 것도 온전히 읽을 수 없다.

**원인**:
플로팅 요소의 위치 계산이 "커서/앵커 기준 고정 오프셋"만 반영하고, 뷰포트 경계 충돌 회피(collision avoidance)나 다른 플로팅 요소와의 상호 배치를 고려하지 않음.

**구현 냄새**:
- 툴팁 위치 로직이 `{ x: cursorX + 12, y: cursorY + 12 }` 식의 단순 오프셋이며 뷰포트/부모 경계 클램핑이 없음.
- 여러 플로팅 레이어(툴팁, 범례, 미니맵)가 서로의 존재를 모른 채 독립적으로 좌표를 계산.
- z-index만으로 "위에 뜨게" 처리하고, 겹칠 때 회피하거나 반투명 처리하는 로직이 없음.

**영향**:
가장 정밀한 정보 확인이 필요한 순간(호버로 상세값 조회)에 오히려 데이터가 가려지는 역설이 발생. 특히 QP/MV 같은 수치를 정확히 읽어야 하는 분석 작업에서 신뢰도를 해침.

**권장**:
- 툴팁/팝오버 라이브러리의 충돌 회피(flip/shift) 기능을 사용해 뷰포트 경계에서 자동으로 반대편으로 재배치.
- 범례처럼 상시 존재하는 플로팅 요소는 사용자가 드래그로 위치를 옮길 수 있게 하거나, 반투명 + 최소화 토글 제공.
- 여러 플로팅 요소가 겹칠 가능성이 있는 영역을 사전에 파악해 우선순위 기반 배치 규칙 수립.

**탐지**:
- 화면 네 모서리 근처에서 각각 호버해 툴팁이 화면 밖으로 나가거나 다른 패널을 가리는지 스크린샷 비교.
- 여러 플로팅 요소가 동시에 활성화되는 시나리오(줌인 + 호버 + 범례 표시)를 재현해 겹침 여부 확인.

### UIX-LAYOUT-014: DPI scaling에서 text와 canvas가 어긋남

**분류**: UIX_LAYOUT · **심각도**: High · **탐지**: Visual

**사용자 목표**:
고해상도(레티나/HiDPI) 모니터에서도 프레임 위 오버레이 텍스트(좌표, QP 값)가 실제 픽셀 위치와 정확히 일치해야 한다.

**증상**:
- 200% 스케일 디스플레이에서 QP 오버레이 숫자가 블록 경계선에서 몇 픽셀씩 어긋나 보인다.
- HTML 오버레이(DOM 텍스트)와 canvas에 그린 프레임 콘텐츠가 서로 다른 배율로 렌더링되어, 확대할수록 어긋남이 누적된다.
- 외부 모니터(100% 스케일)와 내장 레티나 디스플레이(200% 스케일)를 오가며 창을 옮기면 어긋남 정도가 달라진다.

**원인**:
Canvas의 실제 픽셀 버퍼 크기(`canvas.width/height`)와 CSS 표시 크기, 그리고 `devicePixelRatio`를 일관되게 반영하지 않음. DOM 오버레이(텍스트 라벨)와 canvas 그리기가 서로 다른 좌표계/배율 가정을 사용.

**구현 냄새**:
- `canvas.width = cssWidth` 형태로 `devicePixelRatio`를 곱하지 않고 캔버스 버퍼를 설정.
- 오버레이 텍스트를 canvas에 직접 그리지 않고 별도 DOM 레이어로 절대 좌표 배치하면서, 두 레이어가 서로 다른 반올림 규칙(예: canvas는 정수 픽셀, DOM은 subpixel)을 사용.
- `devicePixelRatio` 변경 이벤트(모니터 간 창 이동, OS 스케일 변경)를 리스닝하지 않아 값이 최초 마운트 시점에 캐시된 채로 고정됨.

**영향**:
분석 도구의 핵심 신뢰성(오버레이 숫자가 정확한 픽셀/블록을 가리키는가)이 훼손됨. HiDPI 사용자 비중이 높은 전문가 그룹(디자이너, 비디오 엔지니어)에서 특히 체감이 크다.

**권장**:
- 모든 canvas에 `devicePixelRatio`를 반영해 버퍼 크기를 설정하고 컨텍스트를 `scale(dpr, dpr)`로 보정하는 공통 유틸리티 사용.
- 가능하면 오버레이 텍스트도 같은 canvas/좌표계에 그려 어긋남 자체를 구조적으로 제거하거나, DOM을 쓴다면 동일한 반올림 규칙을 강제.
- `devicePixelRatio` 변경을 감지하는 리스너(`matchMedia` 트릭 등)를 두어 모니터 이동 시 재계산.

**탐지**:
- 100%, 150%, 200% 스케일 디스플레이에서 동일 프레임을 렌더링해 오버레이 텍스트와 블록 경계 정렬을 스크린샷 비교.
- 창을 스케일이 다른 두 모니터 사이로 드래그하며 어긋남 발생 여부 실시간 관찰.

**Bitvue 판정**: 미정 — 2단계(저장소 감사)에서 채움

### UIX-LAYOUT-015: macOS·Windows title bar 영역 차이를 무시

**사용자 목표**:
어느 OS에서 실행하든 창 컨트롤(닫기/최소화/최대화)과 앱 콘텐츠가 서로 겹치거나 밀리지 않아야 한다.

**증상**:
- macOS에서 커스텀 타이틀바(신호등 버튼 자리 확보)를 고려하지 않고 상단 툴바를 배치해 신호등 버튼과 첫 메뉴/탭이 겹친다.
- Windows에서는 반대로 신호등 공간만큼의 좌측 여백이 불필요하게 남아 툴바가 비대칭으로 보인다.
- 창을 최대화했을 때와 일반 창 모드일 때 타이틀바 높이가 달라지는 것을 반영하지 않아 상단 콘텐츠가 위아래로 미세하게 흔들린다.

**원인**:
Tauri 앱의 커스텀 타이틀바(또는 타이틀바 오버레이) 구현 시 단일 OS(주로 개발자의 개발 환경) 기준으로만 여백을 하드코딩. macOS의 트래픽라이트 버튼 영역과 Windows의 캡션 버튼 영역이 크기·위치·동작이 다르다는 플랫폼 차이를 추상화하지 않음.

**구현 냄새**:
- 타이틀바 좌측 패딩이 `paddingLeft: 78px` 같은 macOS 전용 값으로 하드코딩되어 있고 플랫폼 분기가 없음.
- Tauri의 `platform()` API나 빌드 타임 타깃 분기를 사용하지 않고 CSS에 매직 넘버만 존재.
- 창 최대화/복원 이벤트에 따른 타이틀바 높이 변화를 리스닝하지 않음.

**영향**:
크로스 플랫폼 데스크톱 앱이라는 정체성에도 불구하고 한쪽 OS에서는 클릭 불가 영역이 발생(신호등 버튼과 UI 겹침)하거나 다른 쪽에서는 어색한 여백이 남아 완성도가 떨어져 보임.

**권장**:
- Tauri의 플랫폼 감지 API로 OS별 타이틀바 여백/버튼 위치를 분기 처리.
- 타이틀바 오버레이 영역을 상수가 아니라 OS별 설정 테이블로 관리하고, 신규 OS(예: Linux) 추가 시 확장 가능하게.
- 창 상태 변화(최대화/복원/풀스크린) 이벤트에 맞춰 타이틀바 높이를 동적으로 재계산.

**탐지**:
- macOS와 Windows 각각에서 동일 빌드를 실행해 상단 타이틀바 영역 스크린샷 비교.
- 창 최대화/복원을 반복하며 상단 콘텐츠 위치가 흔들리는지(레이아웃 시프트) 관찰.

**Bitvue 판정**: 미정 — 2단계(저장소 감사)에서 채움
