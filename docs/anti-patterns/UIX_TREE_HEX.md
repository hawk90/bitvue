# Anti-Pattern Catalog — UIX_TREE_HEX: Syntax Tree와 Hex View

이 문서는 더 큰 안티패턴 카탈로그의 일부이며(전체 색인은 `docs/anti-patterns/INDEX.md`, 별도 작성 예정), UI/UX+Tauri Phase 3 웨이브에 속한다. 트리와 hex view를 서로 연결하는 선택 상태 설계(양방향 링킹, 어느 쪽이 진실의 원천인가, 하이라이트 전파 타이밍)는 `UIX_SYNC.md`가 다루는 별도 관심사이며, 본 파일은 그 연결이 이미 존재한다고 가정한 뒤 — 트리와 hex view 각각이 "링크된 상태로 무엇을, 어떻게 보여줘야 정확하고 신뢰할 수 있는가"라는 렌더링/정보설계 정합성 문제에 집중한다.

---

## Tree — Syntax Tree 안티패턴 (UIX-TREE-*)

### UIX-TREE-001: 전체 트리를 한 번에 펼침

**분류**: 초기 상태 설계 · **심각도**: High · **탐지**: Interaction, Performance

**사용자 목표**:
파일을 열자마자 관심 있는 NAL 유닛/box/프레임으로 빠르게 이동하고 싶다.

**증상**:
- 파일을 열면 수천 개 노드가 이미 펼쳐진 채로 나타나 첫 화면부터 압도적인 스크롤 영역이 생성된다.
- 초기 렌더링이 눈에 띄게 지연되고, 원하는 노드를 찾기 위해 화면을 끝없이 스크롤해야 한다.
- "Collapse All" 같은 구제 버튼을 눌러야만 겨우 탐색 가능한 상태가 된다.

**원인**:
"모든 정보를 처음부터 보여주는 것이 정직하다"는 암묵적 가정, 또는 트리 라이브러리의 기본 expand 상태를 별도로 관리하지 않고 그대로 사용한 결과.

**구현 냄새**:
- 노드 모델의 `expanded` 기본값이 `true`.
- mount 시점에 재귀적으로 전체 트리를 펼치는 초기화 로직이 존재.
- depth별 기본 확장 레벨을 설정할 수 있는 옵션이 없음.

**영향**:
대형 파일(수 GB, 수만 프레임)에서 첫 렌더가 초 단위로 지연되고, 사용자가 무엇을 먼저 봐야 할지 판단하지 못한 채 도구에 대한 신뢰가 떨어진다.

**권장**:
- 최상위 1~2 depth만 기본으로 확장하고 나머지는 지연 렌더링한다.
- 마지막 세션에서 사용자가 펼쳤던 경로를 기억해 다음 실행 시 복원한다.
- "depth N까지 펼치기" 같은 명시적 컨트롤을 제공한다.
- 검색 시에는 매치 경로만 자동으로 확장한다(UIX-TREE-006 참조).

**탐지**:
- 대형 합성 파일로 콜드 스타트 렌더 시간을 측정한다.
- 신규 사용자 온보딩 테스트에서 "특정 필드까지 도달하는 클릭 수"를 측정한다.

**Bitvue 판정**: N/A — 반대로 구현됨: `StreamTreePanel.tsx`와 `SyntaxDetailPanel/index.tsx` 모두 `expandedNodes`를 빈 `Set()`으로 초기화해 기본적으로 전부 접힌 상태로 시작한다(마운트 시 재귀 전개 로직 없음).

### UIX-TREE-002: 수만 개 노드를 DOM에 렌더링

**분류**: 렌더링 성능 · **심각도**: Critical · **탐지**: Performance

**사용자 목표**:
대형 스트림(수천 프레임 × 수백 신택스 요소)의 구조를 끊김없이 스크롤하며 탐색하고 싶다.

**증상**:
- 트리를 스크롤할 때 프레임 드랍이 발생하고, 메모리 사용량이 급격히 증가한다.
- 검색 후 결과로 스크롤 이동할 때 버벅임이 발생한다.
- 대형 스트림을 열면 브라우저/WebView 탭이 일시적으로 응답 없음(unresponsive) 상태가 된다.

**원인**:
트리 컴포넌트가 windowing(가상 스크롤) 없이 전체 노드를 실제 DOM 요소로 mount한다.

**구현 냄새**:
- 재귀 컴포넌트가 자식 배열 전체를 `.map()`으로 렌더링.
- `react-window`/`react-virtualized`류 windowing 라이브러리 미사용.
- key가 안정적 식별자가 아닌 배열 index 기반이라 리렌더 diff 비용이 큼.

**영향**:
4K/8K 세션이나 GOP가 긴 스트림에서 트리 패널 자체가 앱을 멈추게 해 사실상 사용 불가능해진다.

**권장**:
- 접힌 서브트리를 렌더 트리에서 완전히 제외하고, 가시 노드 목록에만 windowing을 적용한다.
- 스크롤 위치 → 노드 index 계산이 O(1)이 되도록 고정 높이 row를 사용한다(가변 높이가 필요하면 캐시된 측정값 사용).
- 노드 수가 임계값을 넘으면 청크 단위 그룹화(예: "프레임 100~199")를 고려한다.

**탐지**:
- 10만+ 노드 합성 트리로 스크롤 FPS를 프로파일링한다.
- Chrome/WebView 성능 탭에서 layout·paint 비용을 측정한다.

**Bitvue 판정**: Confirmed — `StreamTreePanel.tsx`의 `renderChildren`(292-308행)이 windowing 없이 자식 배열 전체를 재귀 `.map()`으로 렌더링하고, `frontend/package.json`에 `react-window`/`react-virtualized` 의존성이 전혀 없다. 단, `FrameSyntaxTab.tsx`의 별도 필드 트리는 120노드 초과 시 자체 `VirtualSyntaxTree`(190-328행)로 windowing을 적용해 이 패턴을 완화하고 있어 전면 적용은 아님.

### UIX-TREE-003: 노드 이름만 있고 의미 설명이 없음

**분류**: 정보 설계 · **심각도**: High · **탐지**: Domain review, User test

**사용자 목표**:
낯선 신택스 요소(예: `pic_order_cnt_lsb`)를 스펙 문서를 별도로 열지 않고도 이해하고 싶다.

**증상**:
- 트리에 스펙 그대로의 약어만 나열되고 툴팁이나 설명이 전혀 없다.
- 신규 사용자가 신택스 요소를 이해하기 위해 별도 창에서 스펙 PDF를 검색한다.
- 같은 이름의 필드가 코덱마다 의미가 미묘하게 다른데도 구분 없이 동일하게 표시된다.

**원인**:
개발자가 스펙 필드명을 그대로 노출하면 충분하다고 가정하며, 설명 문서화 작업이 파싱 로직 구현보다 우선순위에서 밀려 방치된다.

**구현 냄새**:
- 노드 렌더 컴포넌트가 필드명 문자열만 표시.
- 설명/스펙 섹션 참조를 담는 메타데이터 테이블이 파서 정의와 분리되어 관리되지 않음.

**영향**:
전문가 사용자조차 신규 코덱/신택스 확장(예: 새 AV1 툴)을 만나면 헤매고, 도구가 "파서"에 머물러 "분석기"로 성장하지 못한다.

**권장**:
- 각 필드에 1줄 설명 + 스펙 섹션 번호를 hover 툴팁/사이드 패널로 제공한다.
- 필드 설명 데이터를 파서 정의와 함께 버전관리해 코덱 갱신 시 동시에 유지보수한다.
- 설명이 없는 필드는 침묵하지 말고 "설명 없음"이라고 명시적으로 표시한다.

**탐지**:
- 무작위 신택스 노드 20개를 뽑아 설명 커버리지 비율을 측정한다.
- 신규 사용자에게 "이 필드가 무엇을 뜻하는지 30초 안에 알아내라" 과제를 부여해 관찰한다.

**Bitvue 판정**: Suspected — 인프라는 존재한다: `SyntaxNode.description`이 `title` 툴팁으로 렌더되고(`FrameSyntaxTab.tsx` 284, 356행) 백엔드 `syntax.rs`가 다수 노드에 설명을 채워 넣는다(예: "H.264 profile (Baseline, Main, High)", 663행). 다만 `build_avc_syntax_tree`(608행~)가 실제 비트스트림을 파싱하지 않고 하드코딩된 소수 필드만 생성하므로, 실제 코덱 신택스 전반(수백 개 필드)에 대한 설명 커버리지는 확인 불가 — 미구현 상태로 추정.

### UIX-TREE-004: raw 값과 해석된 값을 구분하지 않음

**분류**: 정보 설계 · **심각도**: High · **탐지**: Domain review, Code

**사용자 목표**:
실제 비트/바이트 원본값과 그 의미(enum 라벨, 스케일링된 값)를 모두 신뢰성 있게 확인하고 싶다.

**증상**:
- 트리에 `profile: 2`만 표시되고 "High 4:2:2 Profile" 같은 사람이 읽을 라벨이 없다.
- 반대로 해석된 라벨만 있고 원본 정수값이 사라져, 버그 리포트에서 재현이 불가능하다.
- 스펙에 정의되지 않은 값을 만나면 UI가 크래시하거나 아무 것도 표시하지 않고 침묵한다.

**원인**:
파서가 enum을 문자열로 즉시 변환하며 원본 정수를 버리거나, UI 레이어가 편의상 값 하나만 선택해 표시한다.

**구현 냄새**:
- 트리 노드의 값 모델에 필드가 하나뿐(raw 또는 interpreted 중 택1).
- enum 매핑이 파서 출력 이후 비가역적으로 적용됨.

**영향**:
디버깅 시 "실제 비트가 무엇이었는지" 알 수 없어 hex view와 대조가 불가능해지고, 스펙 위반 값을 만난 순간 도구의 신뢰도가 급락한다.

**권장**:
- 값 모델을 `{ raw, interpreted, is_reserved_or_invalid }` 형태로 유지한다.
- 트리에는 "raw (해석)" 형식(예: `2 (High 4:2:2 Profile)`)으로 병기한다.
- 정의되지 않은 값은 raw만 표시하고 경고 아이콘으로 구분한다.

**탐지**:
- 코드 리뷰에서 파서 출력 타입에 raw 필드가 살아있는지 확인한다.
- 스펙 밖 값을 의도적으로 가진 합성 스트림으로 회귀 테스트를 수행한다.

**Bitvue 판정**: Confirmed — `src-tauri/src/commands/syntax.rs` 660-667행에서 `profile` 필드가 `SyntaxValue::String("High")`처럼 해석된 값만 저장하고 원본 `profile_idc` 정수는 어디에도 보존되지 않는다. `SyntaxValue` enum(String/Number/Float/Boolean/Array) 자체에 raw+interpreted 쌍을 담는 필드가 없다.

### UIX-TREE-005: 단위·bit 길이·offset을 숨김

**분류**: 정보 설계 · **심각도**: Medium · **탐지**: Domain review

**사용자 목표**:
특정 필드가 비트스트림에서 몇 비트를 차지하고 어디서 시작하는지 파악해 hex/bit 뷰와 정확히 대조하고 싶다.

**증상**:
- 노드를 클릭해도 몇 비트짜리 필드인지 알 수 없다.
- `ue(v)`/`se(v)` 같은 가변 길이 필드의 실제 소비 비트수가 표시되지 않는다.
- bit offset이 노출되더라도 파일 시작 기준인지 현재 구조체 기준인지 불명확하다.

**원인**:
파서 내부적으로는 비트 길이를 알고 있지만(스트림 커서 이동량) 이를 UI 계층까지 전달하는 필드가 파이프라인 어딘가에서 누락된다.

**구현 냄새**:
- 노드 모델의 `bit_offset`/`bit_length`가 옵셔널이거나 디버그 전용으로만 존재.
- UI 컴포넌트가 해당 필드를 렌더링 경로에 연결하지 않음.

**영향**:
가변 길이 코덱(exp-golomb 등) 분석 시 "왜 이 범위가 선택됐는지" 사용자가 이해하지 못해, 트리-hex 연동(UIX-SYNC 영역)이 있어도 그 결과를 검증할 수단이 없다.

**권장**:
- 모든 노드에 파일 시작 기준 bit offset과 bit length를 상시 표시한다(축약은 가능하되 완전히 숨기지 않음).
- 가변 길이 필드는 실제로 소비된 비트수를 명시한다.
- 단위(bit/byte) 표기를 화면 전체에서 일관되게 고정한다.

**탐지**:
- 임의 노드 10개를 골라 offset/length 표시 여부 체크리스트를 만든다.
- exp-golomb 필드가 많은 SPS/PPS 등으로 회귀 테스트를 수행한다.

**Bitvue 판정**: Confirmed — 프론트/백엔드 어디에도 `bit_offset`/`bit_length` 개념이 없다(`node_modules` 외 검색 결과 0건). `SyntaxNode`(`FrameSyntaxTab.tsx` 20-26행)와 백엔드 `syntax.rs`는 `byte_offset: Option<u64>`만 갖는데, 실제로는 파일 전체에서 `byte_offset: Some(...)`으로 설정되는 곳이 단 한 곳도 없다(`byte_offset: None`이 58회 등장, `Some`은 0회) — hex-jump 링크 자체가 사실상 죽어있다.

### UIX-TREE-006: 검색 시 조상 경로를 표시하지 않음

**분류**: 탐색성 · **심각도**: High · **탐지**: Interaction

**사용자 목표**:
검색 결과 노드가 트리 어디에 속하는지(어느 프레임, 어느 슬라이스인지) 즉시 파악하고 싶다.

**증상**:
- 검색 결과를 클릭하면 트리가 해당 노드로 스크롤은 되지만 조상 체인이 접혀 있어 "몇 번째 프레임의 어느 슬라이스 헤더인지" 알 수 없다.
- breadcrumb이나 경로 표시가 없어 위로 스크롤하며 수동으로 조상을 재구성해야 한다.

**원인**:
검색 기능이 결과 하이라이트와 스크롤 이동만 구현하고, 컨텍스트(조상 경로) 노출은 별도 작업으로 취급되어 누락된다.

**구현 냄새**:
- 검색 결과 클릭 핸들러가 `scrollIntoView`만 호출.
- breadcrumb 컴포넌트가 존재하지 않음.
- 검색 시 자동 확장 로직이 대상 노드까지의 경로를 계산하지 않음.

**영향**:
검색이 "찾았다"에서 끝나고 "이해했다"로 이어지지 않아, 검색이 절약해야 할 시간이 조상 재구성 작업으로 다시 소모된다.

**권장**:
- 검색 결과 클릭 시 조상 경로를 자동 확장하고, 고정 breadcrumb 바(예: `Frame 42 > Slice 0 > Macroblock 12 > mb_type`)를 표시한다.
- 검색 결과 목록 자체에도 축약된 경로를 함께 노출한다.

**탐지**:
- 검색 → 결과 클릭 → 조상 경로 파악까지 걸리는 클릭 수/시간을 사용자 테스트로 측정한다.

**Bitvue 판정**: Confirmed — `StreamTreePanel.tsx`의 `flattenUnits`(253-266행)가 필터 활성화 시 매치된 노드를 조상 체인 없이 평탄한 배열로 만들고, 렌더링도 전부 `depth={0}`으로 표시된다(387-400행). breadcrumb 컴포넌트는 코드베이스 어디에도 없다.

### UIX-TREE-007: 접힌 노드 내부 match를 알리지 않음

**분류**: 탐색성 · **심각도**: Medium · **탐지**: Interaction

검색어가 트리 전체에서 몇 건, 어디에 있는지 한눈에 파악하고 싶다.

**탐지**:

### UIX-TREE-008: 이전 프레임과 비교 기능 없음

**분류**: 분석 기능 · **심각도**: High · **탐지**: Domain review, User test

**사용자 목표**:
현재 프레임의 신택스가 이전 프레임(또는 참조 프레임) 대비 무엇이 달라졌는지 파악하고 싶다 — 인코더 회귀 디버깅의 핵심 워크플로우.

**증상**:
- 프레임을 하나씩 넘기며 눈으로 트리를 대조해야 한다.

**구현 냄새**:

**권장**:

**탐지**:

- 실사용자 인터뷰에서 "프레임을 어떻게 비교하시나요"를 질문한다.

**Bitvue 판정**: Confirmed — `diffFrame`/`compareFrame`/구조적 diff 관련 코드가 frontend·src-tauri 어디에도 없다(grep 0건). 트리/신택스 뷰는 항상 단일 프레임만 표시하며 프레임 간 비교 기능이 로드맵상 미구현 상태로 확인됨.

### UIX-TREE-009: 동일 값 반복으로 중요한 변화가 묻힘

**분류**: 정보 설계 · **심각도**: Medium · **탐지**: Domain review

**사용자 목표**:
수백 개의 반복 구조(매크로블록, CTU 등) 중 예외적인 값을 빠르게 찾고 싶다.

**증상**:
- 동일 패턴이 반복되는 신택스(예: 슬라이스 내 모든 매크로블록의 `mb_type`)가 그대로 나열되어, 예외 값 하나가 수백 개 동일 노드 사이에 파묻힌다.
- 반복 구간을 스크롤하며 눈으로 값을 하나씩 비교해야 한다.

**원인**:
트리가 반복 구조를 요약·집계하지 않고 raw 순서 그대로 flat하게 나열하며, "이상치 강조"라는 개념이 렌더링 계층에 존재하지 않는다.

**구현 냄새**:
- 반복 노드 렌더링에 통계적 요약(최빈값, 분포) 계산이 없음.
- 모든 노드가 시각적으로 동일한 무게(색·굵기)로 렌더링됨.

**영향**:
바로 이런 반복 구조에서 예외를 찾는 것이 이 도구가 존재하는 핵심 이유 중 하나인데, 그 지점에서 가장 취약해져 전문가 사용자의 생산성을 직접적으로 깎아먹는다.

**권장**:
- 반복 구조는 기본적으로 최빈값 요약(예: `mb_type=16x16 × 240, 예외 3개`)으로 접고 예외만 펼쳐서 강조한다.
- run-length 압축 표시(같은 값이 N개 연속)를 제공한다.
- 이상치를 다른 색/아이콘으로 하이라이트한다.

**탐지**:
- 반복 구조 비율이 높은 실제 스트림(정적 배경 등)으로 "이상치를 찾는 데 걸리는 시간"을 측정한다.

**Bitvue 판정**: Confirmed — `StreamTreePanel.tsx`/`FrameSyntaxTab.tsx` 어디에도 최빈값 요약, run-length 압축, 이상치 강조 로직이 없다(grep으로 outlier/run-length/최빈값 관련 코드 미발견). 노드는 `getUnitColor`(unit_type 기준 고정 색상표, 50-63행)로만 스타일링되어 반복 여부와 무관하게 모두 동일한 시각적 무게로 렌더링된다.

### UIX-TREE-010: 선택 노드가 스크롤 중 재사용되어 바뀜

**분류**: 상태 관리 · **심각도**: Critical · **탐지**: Interaction, Code

**사용자 목표**:
노드를 한 번 선택하면 스크롤하거나 다른 작업을 해도 선택 상태와 그에 연동된 hex 하이라이트가 그대로 유지되길 기대한다.

**증상**:
- virtualization(가상 스크롤) 적용 후 스크롤하면 선택 표시(배경색 등)가 엉뚱한 노드로 옮겨가거나 사라진다.
- hex view의 하이라이트도 함께 어긋난다.

**원인**:
virtualized 리스트가 DOM 노드를 재사용(recycle)할 때 컴포넌트 key를 화면상 index로 부여해, "선택된 것은 다섯 번째로 렌더된 DOM"이라는 잘못된 가정으로 상태를 연결한다.

**구현 냄새**:
- 선택 상태를 노드의 안정적 식별자(bit_offset, path)가 아니라 렌더 순서/index로 저장.
- virtualization 라이브러리의 `key` prop이 index 그대로 사용됨.

**영향**:
트리-hex 선택 연동(UIX-SYNC 영역)이 근본적으로 깨져, 사용자가 선택한 필드와 실제 강조되는 필드가 스크롤 한 번에 어긋나 잘못된 바이트를 확인하게 되는 치명적 신뢰 손상이 발생한다.

**권장**:
- 선택 상태 저장에 `bit_offset + path` 같은 안정적 키를 사용한다.
- virtualization의 `key`를 데이터 고유 ID로 명시한다.
- 선택 상태(데이터 모델)와 렌더링 상태(뷰 레이어)를 분리한다.

**탐지**:
- 노드 선택 후 빠르게 스크롤 다운/업을 반복하며 선택 하이라이트가 동일 노드에 유지되는지 확인하는 자동화 테스트(대형 트리 기준)를 수행한다.

**Bitvue 판정**: N/A — `TreeNode`/`SyntaxTreeNode`는 안정적 식별자(`child.key`, `path`)를 React `key`로 사용하고(`StreamTreePanel.tsx` 296행, `FrameSyntaxTab.tsx` 282/393행) 선택 상태도 같은 키로 비교한다. 실제 windowing이 구현된 유일한 곳인 `VirtualSyntaxTree`(`FrameSyntaxTab.tsx` 233-328행)도 안정 키 기반 `flatNodes` 배열에 절대 인덱스로 슬라이싱할 뿐 index-as-key 재사용 방식이 아니라 이 증상이 적용되지 않는다.

## Hex — Hex/Bit View 안티패턴 (UIX-HEX-*)

### UIX-HEX-001: byte와 bit 선택 경계가 모호함

**분류**: 선택/입력 UX · **심각도**: High · **탐지**: Interaction

**사용자 목표**:
바이트 경계에 걸치지 않는 임의 비트 범위(예: 3비트짜리 필드)를 정확히 선택하고 그 경계를 눈으로 확인하고 싶다.

**증상**:
- 마우스로 hex 셀을 클릭하면 항상 byte 단위로만 선택되어 byte 중간에서 시작/끝나는 필드를 정확히 선택할 수 없다.
- 선택은 되더라도 정확히 몇 번째 비트부터인지 시각적으로 구분되지 않는다.

**원인**:
hex view가 애초에 byte-grid 렌더링으로 설계되어 있어, 각 셀이 원자적 byte 단위이고 bit 단위 하위 선택을 표현할 인터랙션 모델 자체가 없다.

**구현 냄새**:
- 선택 상태 모델이 byte offset만 저장하고 bit offset이 없음.
- 셀 내부의 부분 강조(sub-cell highlight)를 그리는 로직이 없어 배경색 전환만 존재.

**영향**:
exp-golomb 등 가변 비트 필드가 지배적인 코덱(H.264/HEVC)에서 hex view가 사실상 "바이트만 보여주는 뷰"로 전락하고, 트리에서 선택한 필드와 hex 강조가 부정확하게 매핑되어(예: 실제로는 3비트인데 byte 전체가 강조) 사용자 혼동을 유발한다.

**권장**:
- hex byte 셀 내부를 비트 단위로 세분화해 부분 배경(sub-highlight)을 그릴 수 있게 렌더링한다.
- 셀 하단에 옵션으로 bit ruler(0~7)를 표시한다.
- 선택 시 "byte 3, bit 2~4" 같은 명시적 텍스트를 함께 표시한다.

**탐지**:
- 3비트 미만 필드를 가진 합성 스트림으로 선택 정확도를 시각 검증한다.
- 픽셀 단위 스크린샷 비교 회귀 테스트를 수행한다.

**Bitvue 판정**: Confirmed — `HexViewTab.tsx`의 선택 상태는 `selectedByte: number | null` 하나뿐이고(36행), `onClick={() => setSelectedByte(byteOffset)}`(245행)로 byte 단위 클릭만 지원한다. sub-cell 하이라이트나 bit ruler를 그리는 로직이 없다.

### UIX-HEX-002: 큰 payload를 한 번에 렌더링

**분류**: 렌더링 성능 · **심각도**: Critical · **탐지**: Performance

**사용자 목표**:
수십 MB~GB 단위 프레임/슬라이스 payload도 끊김없이 스크롤하며 탐색하고 싶다.

**증상**:
- 큰 NAL 유닛이나 프레임 payload를 열면 초기 렌더가 수 초씩 걸린다.
- 스크롤 시 프레임 드랍이 발생하고 메모리 사용량이 급증한다.

**원인**:
hex view가 전체 바이트 배열을 한 번에 문자열/DOM으로 변환해 렌더링한다(예: 각 바이트를 개별 DOM 요소로 mount).

**구현 냄새**:
- hex dump 생성 함수가 전체 버퍼 길이만큼 DOM 요소를 생성.
- windowing/virtualization이 적용되지 않음.
- 16진 문자열 변환이 memoize 없이 매 리렌더마다 재계산됨.

**영향**:
4K 인트라 프레임, RAW payload 등 대형 스트림에서 hex view 자체가 병목이 되어 도구가 사실상 사용 불가능해진다 — 트리(UIX-TREE-002)와 동일한 근본 원인이 hex 쪽에도 반복된 것이다.

**권장**:
- 가시 영역(viewport)에 해당하는 바이트 범위만 backend에서 청크 단위로 fetch/렌더하는 virtual scrolling을 적용한다.
- 고정 폭 row 레이아웃으로 스크롤 위치 → offset 계산을 O(1)로 유지한다.
- 대형 payload는 초기에 요약(첫/마지막 N바이트 + "더 보기")만 표시한다.

**탐지**:
- 수십 MB payload로 초기 렌더 시간과 스크롤 FPS를 측정한다.

**Bitvue 판정**: Suspected — 렌더 경로 자체는 windowing 없이 전체를 `Array.from({length: lines}, ...)`로 한 번에 mount한다(`HexViewTab.tsx` 219-269행). 다만 프론트가 `invoke("get_frame_hex_data", { maxBytes: 2048 })`로 하드코딩 호출해(60행) 현재는 DOM이 128줄로 제한되어 체감 문제가 가려져 있다. 반면 백엔드 `MAX_HEX_BYTES`는 1MB까지 허용하므로(`src-tauri/src/constants.rs:42`), 향후 이 하드코딩된 2048 제한만 올라가도 windowing 부재로 인한 정체가 그대로 재현될 구조.

### UIX-HEX-003: offset 표기를 10진/16진 중 하나로 고정

**분류**: 정보 설계 · **심각도**: Low · **탐지**: Domain review, User test

**사용자 목표**:
스펙 문서(보통 16진)와 파일 크기·시간 계산(보통 10진에 익숙)을 오가며 offset을 자유롭게 참조하고 싶다.

**증상**:
- offset 컬럼이 16진수로만, 혹은 10진수로만 표시되어 다른 표기가 필요할 때마다 사용자가 수동 변환한다.

**원인**:
개발 초기에 "hex view니까 offset도 hex로"라는 단일 가정으로 결정되고 이후 재검토되지 않는다.

**구현 냄새**:
- offset 포맷팅 함수가 하드코딩된 base(16 또는 10)로 고정.
- 토글 UI나 사용자 설정이 없음.

**영향**:
사소해 보이지만 반복 작업(파일 크기 대비 offset 비율 계산, 다른 도구의 10진 로그와 대조)에서 마찰이 누적되고, 특히 툴 간 상호 검증(cross-check) 워크플로우에서 계산 실수를 유발한다.

**권장**:
- offset 표기를 10진/16진 토글 가능하게 하고, hover 시 두 표기를 함께 tooltip으로 제공한다.
- 사용자 설정으로 기본값을 기억한다.

**탐지**:
- 설정 패널에 offset 표기 토글이 존재하는지 확인한다.
- 두 표기가 hover 텍스트에 동시 노출되는지 시각 확인한다.

**Bitvue 판정**: Confirmed — `HexViewTab.tsx`의 offset 표기는 `offset.toString(16).padStart(8, "0").toUpperCase()`(230-231행)와 byte-info 패널(283행)에서 모두 16진수로 하드코딩되어 있고, 토글 UI나 설정값이 없다.

### UIX-HEX-004: endian·bit order를 설명하지 않음

**분류**: 정보 설계 · **심각도**: Medium · **탐지**: Domain review

**사용자 목표**:
여러 바이트에 걸친 필드(32비트 정수, NAL length prefix 등)가 어떤 endian·bit order로 해석됐는지 확신하고 싶다.

**증상**:
- 멀티바이트 필드의 해석된 값(트리)과 raw hex(hex view)를 대조할 때 byte 순서가 명시되지 않아 big-endian인지 little-endian인지 알 수 없다.
- 비트필드의 MSB-first/LSB-first 규약도 어디에도 명시되지 않는다.

**원인**:
endian/bit order가 파서 내부에서는 코덱 스펙에 따라 올바르게 처리되지만, 개발자에게는 자명한 사실이라 그 자체가 UI에 노출되지 않은 채 우선순위에서 밀린다.

**구현 냄새**:
- 값 표시 컴포넌트에 endian 메타데이터 필드가 없음.
- byte order를 명시하는 범례(legend)나 아이콘이 부재.

**영향**:
신규 사용자나 크로스체크 상황에서 잘못된 endian으로 수동 계산해 오판하기 쉽고, 특히 컨테이너(MP4 big-endian)와 코덱 내부 비트필드(MSB-first exp-golomb) 관례가 다른 지점에서 혼동이 발생한다.

**권장**:
- 멀티바이트 필드의 hover/상세 패널에 "big-endian" 등 명시적 라벨과 byte 순서 화살표를 제공한다.
- 코덱별 bit order 규약을 앱 어딘가(도움말/legend)에 고정 노출한다.
- 값 계산식을 `bytes[0..4] → BE u32 → 0x1A2B3C4D`처럼 단계별로 보여주는 옵션을 제공한다.

**탐지**:
- 멀티바이트 필드 10개 샘플에서 endian 표시 존재 여부를 체크한다.
- 사용자 인터뷰에서 "이 값이 어떻게 계산됐는지 설명해달라"고 요청한다.

**Bitvue 판정**: Confirmed — `HexViewTab.tsx`에는 endian/byte-order 라벨이나 범례가 전혀 없다. 애초에 멀티바이트 값 조합(`bytes[0..4] → u32`) 자체를 만들지 않고 byte 단위로만 표시하므로(219-269행), endian 모호성을 설명할 지점 자체가 UI에 존재하지 않는다.

### UIX-HEX-006: 범위가 여러 줄에 걸칠 때 시작·끝을 찾기 어려움

**분류**: 시각 언어 · **심각도**: Medium · **탐지**: Visual, Interaction

**사용자 목표**:
여러 hex 행(row)에 걸친 긴 필드(예: 슬라이스 payload 전체)의 정확한 시작과 끝 위치를 한눈에 파악하고 싶다.

**증상**:
- 긴 범위가 하이라이트되면 중간 행들과 시작/끝 행 사이에 시각적 차이가 없다.

**원인**:
하이라이트 렌더링이 "이 셀이 범위 안에 있는가"라는 단순 boolean만 계산하고, 범위의 첫/마지막 셀이라는 위치 정보를 스타일에 반영하지 않는다.

**구현 냄새**:
- 하이라이트 CSS 클래스가 단일 종류(`.highlighted`)뿐이고 start/end/middle 구분이 없음.

**권장**:
- 범위의 시작 행과 끝 행에 강조 테두리 또는 아이콘("▶ 시작", "■ 끝")을 표시한다.
- 사이드 미니맵/스크롤바에 범위 위치 마커를 제공한다.
- "선택 범위 시작/끝으로 이동" 버튼을 제공한다.

**탐지**:
- 여러 행에 걸친 범위 선택 시나리오로 시각 회귀 테스트를 수행한다.
- 사용자 테스트에서 "이 필드의 정확한 마지막 바이트 offset을 찾아달라" 과제 시간을 측정한다.

**Bitvue 판정**: N/A — `HexViewTab.tsx`에는 다중 바이트 범위 선택 기능 자체가 없다(`selectedByte: number | null` 단일 값만 존재, 36행). 여러 행에 걸친 범위 하이라이트라는 전제 조건이 아직 구현되지 않아 start/end 구분 여부를 논할 대상이 없음.

### UIX-HEX-007: hover 시 매번 backend query

**분류**: 성능/IPC · **심각도**: High · **탐지**: Performance, Code

**사용자 목표**:
hex 위를 마우스로 훑으면서 각 바이트가 어느 신택스 필드에 속하는지 지연 없이 즉각 확인하고 싶다.

**증상**:
- hex 바이트에 마우스를 올릴 때마다 눈에 띄는 지연(수십~수백 ms) 후에 툴팁이 나타난다.
- 빠르게 마우스를 움직이면 오래된 응답이 뒤늦게 도착해 잘못된 위치에 툴팁이 표시된다(race condition).

**원인**:
hover 이벤트마다 프론트엔드가 Tauri IPC를 통해 백엔드에 "이 offset이 어느 노드에 속하는가"를 매번 새로 질의하며, 디바운스나 캐시 없이 직결되어 있다.

**구현 냄새**:
- `onMouseMove` 핸들러가 곧바로 `invoke()`를 호출.
- 결과에 요청 순서 검증(stale response 무시) 로직이 없음.
- offset → node 매핑을 프론트엔드에 캐시하지 않음.

**영향**:
체감 반응성이 떨어져 "탐색하며 빠르게 훑어보기"라는 hex view의 핵심 사용 패턴 자체가 느려지고, race condition으로 잘못된 필드 정보가 표시되는 신뢰성 문제까지 겹친다.

**권장**:
- 파일/프레임 로드 시 offset → node 매핑을 프론트엔드 메모리에 한 번에 캐시(또는 구간 prefetch)해 hover를 로컬 조회로 처리한다.
- 불가피하게 backend 질의가 필요하면 디바운스와 요청 취소(최신 요청만 반영)를 반드시 적용한다.

**탐지**:
- 빠른 마우스 이동 시 초당 IPC 호출 횟수를 계측한다.
- 네트워크/IPC 탭에서 stale response 도착 여부를 확인한다.

**Bitvue 판정**: N/A — `HexViewTab.tsx`에 `onMouseMove`/hover 핸들러가 없다. `invoke("get_frame_hex_data", ...)`는 `frameIndex` 변경 시 한 번만 호출되고(48-93행), byte 정보는 클릭 시 로컬 상태(`selectedByte`)만 갱신한다(245행) — hover마다 IPC를 쏘는 코드 경로 자체가 없다.

### UIX-HEX-008: 선택 범위를 문자열 복사해 메모리 폭증

**분류**: 성능/메모리 · **심각도**: High · **탐지**: Performance, Code

**사용자 목표**:
선택한 hex 범위를 클립보드로 복사해 다른 도구(스크립트, 이슈 트래커)에 붙여넣고 싶다.

**증상**:
- 큰 범위(수백 KB~MB)를 복사하려 하면 UI가 잠깐 멈춘다.
- 반복 복사할 때마다 메모리 사용량이 계속 증가한다.

**원인**:
복사 시 선택 범위 전체를 hex 문자열(`"1A 2B 3C ..."`)로 즉석 생성하는 과정이 비효율적이거나(문자열 concatenation 반복, 불필요한 중간 배열 생성), 생성된 결과 문자열을 앱 상태에 계속 보관해 GC되지 않는다.

**구현 냄새**:
- 문자열 생성이 `+=` 반복(quadratic) 또는 매번 새 배열 생성 후 join.
- 복사 완료 후에도 마지막 생성 문자열을 컴포넌트 state에 남겨둠.
- undo 히스토리 등에 큰 문자열이 계속 누적됨.

**영향**:
대형 payload를 자주 복사·분석하는 워크플로우(버그 리포트 첨부 등)에서 반복 사용할수록 앱이 점점 느려지고 결국 OOM에 가까워진다.

**권장**:
- 사전 크기 계산된 버퍼와 lookup table 기반 hex 변환으로 O(n) 처리한다.
- 복사 완료 후 임시 버퍼는 즉시 해제하고 state에 보관하지 않는다.
- 매우 큰 범위는 복사 전 확인 대화상자를 띄우거나 파일로 저장하는 대안을 제시한다.

**탐지**:
- 반복 복사(예: 100회) 후 메모리 사용량 추이를 프로파일링한다.
- 대형 범위(수 MB) 복사 시 UI freeze 시간을 측정한다.

**Bitvue 판정**: N/A — `UnitHexPanel` 디렉터리 전체에 clipboard/copy/writeText 관련 코드가 없다(grep 0건). 복사 기능 자체가 아직 구현되지 않아 이 버그가 발생할 수 없음.

---

### UIX-HEX-009: invalid/truncated 영역을 일반 데이터처럼 표시

**분류**: 정보 설계/신뢰성 · **심각도**: Critical · **탐지**: Domain review, Visual

**사용자 목표**:
파싱이 실패했거나 파일이 잘린(truncated) 영역과 정상 파싱된 데이터를 명확히 구분해, 분석 결과를 어디까지 신뢰할 수 있는지 알고 싶다.

**증상**:
- 파일 끝이 잘렸거나 파서가 특정 구간에서 실패해도 hex view는 해당 바이트를 다른 정상 데이터와 동일한 스타일로 표시한다.
- 그 구간이 "분석되지 않은 raw 잔여물"인지 "정상 파싱된 유효 데이터"인지 구분할 시각적 단서가 없다.

**원인**:
hex view가 파서의 성공/실패 상태와 독립적으로 동작한다 — 파서가 에러를 던지거나 조기 종료해도 hex view는 여전히 파일의 원본 바이트를 그대로 렌더링하도록 설계되어, "이 바이트가 어떤 신택스 노드에도 속하지 않는다"는 사실이 렌더링 계층까지 전달되지 않는다.

**구현 냄새**:
- hex 렌더러가 offset → node 매핑이 없는 구간(unmapped bytes)을 매핑이 있는 구간과 동일한 기본 스타일로 처리.
- 파서 에러/truncation 위치를 프론트엔드로 전달하는 필드가 API 응답에 없거나 무시됨.

**영향**:
사용자가 실제로는 신뢰할 수 없는 구간(파일 손상, 미지원 신택스로 파싱 중단)을 정상 데이터로 오인해 잘못된 결론을 내릴 수 있다 — 분석 도구에서 가장 치명적인 신뢰성 위반 유형이다.

**권장**:
- unmapped/invalid/truncated 구간을 명확히 다른 시각 스타일(회색 빗금, "unparsed" 라벨, 경고 아이콘)로 표시한다.
- 파서가 실패한 지점부터 파일 끝까지를 별도 배너("이 지점부터 파싱 실패: <이유>")로 명시한다.
- 해당 구간 클릭 시 실패 원인(에러 메시지, 예상 vs 실제)을 상세 표시한다.

**탐지**:
- 의도적으로 잘리거나 손상된 스트림을 로드해 hex view가 실패 구간을 시각적으로 구분하는지 확인하는 회귀 테스트를 수행한다.
- 코드 리뷰에서 파서 에러 상태가 hex 렌더링 props까지 전달되는 경로를 추적한다.

**Bitvue 판정**: Confirmed — `get_frame_hex_data`(`src-tauri/src/commands/frame.rs` 480-558행)는 프레임 전체 단위의 `success`/`error`와 단일 `truncated` 플래그만 반환하고, 바이트별 "파싱 안 됨/무효" 상태 개념이 없다. `HexViewTab.tsx`도 이에 대응하는 스타일 분기가 없어(`getByteStyle`, 144-161행), 부분적으로 파싱 실패했거나 손상된 프레임의 바이트는 정상 데이터와 동일하게 렌더링된다.

### UIX-HEX-010: hex 편집기로 오해하게 만드는 affordance

**분류**: 상호작용 설계/정신모델 · **심각도**: Medium · **탐지**: Interaction, User test

**사용자 목표**:
이 도구는 읽기 전용 분석기라는 것을 명확히 인지한 채 안전하게 탐색하고 싶다.

**증상**:
- hex 셀이 텍스트 입력 필드처럼 보인다(커서 깜빡임, 포커스 시 테두리).
- 값을 타이핑하면 로컬에서 반영되는 것처럼 보이지만 실제로는 저장되지 않거나 아무 동작도 하지 않는데, 사용자는 "편집됐다"고 착각한 채 넘어간다.

**원인**:
hex 표시에 흔한 hex 에디터 UI 패턴(등폭 그리드, 클릭 시 커서, `contenteditable` 사용)을 그대로 차용하면서 "읽기 전용"이라는 차이를 시각적으로 구분하지 않는다.

**구현 냄새**:
- hex 셀 마크업이 읽기 전용 목적임에도 `<input>` 또는 `contenteditable` 요소를 사용.
- 클릭 시 텍스트 커서(caret)가 나타나는 브라우저 기본 동작을 막지 않음.
- "읽기 전용" 상태를 알리는 시각적 신호(자물쇠 아이콘, 다른 배경색)가 없음.

**영향**:
사용자가 값을 "수정"했다고 믿고 그 상태로 분석을 계속하거나 동료에게 잘못된 결과를 공유할 수 있다 — 실제로는 아무것도 바뀌지 않았는데 UI가 편집 가능한 것처럼 행동해 발생하는 신뢰 오류이며, 향후 실제 편집 기능이 추가될 때 "이미 편집되는 줄 알았다"는 혼란까지 유발할 수 있다.

**권장**:
- hex 셀을 비-editable 요소(div/span 등, 선택은 가능하되 입력은 불가)로 구현하고 클릭 시 caret이 아닌 명시적 선택 하이라이트만 표시한다.
- 헤더/모드 표시줄에 "읽기 전용" 상태를 상시 노출한다.
- 향후 편집 기능을 계획 중이라면 명확히 별도 모드(예: "패치 모드" 진입 버튼)로 분리해 오해 소지를 없앤다.

**탐지**:
- 신규 사용자에게 "이 값을 바꿔보세요"라고 요청했을 때 실제로 편집을 시도하는지 관찰하는 사용성 테스트를 수행한다.
- 접근성 감사에서 `contenteditable`/`input` 요소 존재 여부를 스캔한다.

**Bitvue 판정**: N/A — hex 셀은 `<span className="hex-byte">`로 구현되어 있고(`HexViewTab.tsx` 241-251행) `<input>`/`contentEditable` 요소가 `UnitHexPanel` 전체에 없다(grep 0건). caret이나 편집 어포던스가 생길 여지가 없음.
