# Anti-Pattern Catalog — UIX_A11Y: 접근성

이 문서는 더 큰 안티패턴 카탈로그의 일부입니다(전체 목록은 별도로 작성 중인 `docs/anti-patterns/INDEX.md` 참고). UIX_A11Y는 UI/UX+Tauri Phase 3 웨이브에 속하는 카테고리로, Phase 1(Rust/media-core 엔지니어링)·Phase 2(VQ-Probe 도메인)와 달리 프론트엔드 상호작용/렌더링 계층을 다룬다.

Bitvue 같은 전문 비트스트림 분석 도구에서 접근성은 법적 컴플라이언스 항목이 아니라 **작업 정확성(correctness)의 일부**다. QP 히트맵, MV 오버레이, RD 커브 diverging 팔레트처럼 색상 범례에 크게 의존하는 도구이기 때문에, 색각 이상 사용자가 히트맵 범례를 잘못 읽는 것은 "포용성이 부족한" 문제가 아니라 "잘못된 인코딩 튜닝 결론을 내리는" 정확성 버그다. 이 카테고리에서 반복적으로 등장하는 근본 원인은 대부분 동일하다 — **단일 인코딩 채널(색상 hue 하나)에 상태·값·방향 정보를 모두 몰아넣는 설계**. 그래서 권장안도 거의 항상 같은 형태를 띤다: 색상 + 패턴/해칭 + 윤곽/형태 + 숫자를 조합해 어떤 한 채널이 실패해도 정보가 완전히 소실되지 않게 하는 것.

---

### UIX-A11Y-001: 색만으로 상태 구분

**분류**: 색상 인코딩 · **심각도**: Critical · **탐지**: Visual

**사용자 목표**:
여러 블록/프레임 중 어떤 것이 정상이고 어떤 것이 오류·경고 상태인지 한눈에 구분하고 싶다.

**증상**:
- QP 히트맵에서 "정상 QP"와 "높은 QP(품질 저하 의심)"이 녹색/빨강 hue 차이만으로 구분됨
- 디코딩 오류가 발생한 프레임이 필름스트립에서 빨간 테두리 "색"으로만 표시되고 아이콘이나 텍스트가 없음
- MV 오버레이에서 forward/backward reference 방향이 파란색/빨간색 화살표로만 구분되어 색각이상 사용자는 방향 정보를 읽지 못함

**원인**:
상태를 구분하는 유일한 채널이 hue이며, "빨강=나쁨, 초록=좋음"이라는 문화적 관습 하나에만 의존해 구현되었기 때문이다.

**구현 냄새**:
- `.error { color: red }` / `.ok { color: green }` 처럼 클래스명과 실제 구분 신호가 색상 하나뿐
- 범례(legend)에 색상 견본만 있고 패턴·아이콘이 병기되지 않음
- 디자인 시스템에 "상태 색상 토큰"은 있지만 "상태 아이콘/패턴 토큰"이 없음

**영향**:
전 세계 남성 인구 약 8%(적록색각이상 포함)가 QP 히트맵에서 문제 영역과 정상 영역을 구분하지 못하거나 반대로 읽어, 잘못된 인코딩 튜닝 결론을 내릴 수 있다.

**권장**:
- 색상 + 형태(아이콘) + 패턴(해칭/점선) + 텍스트/숫자 라벨을 항상 함께 제공
- 히트맵은 색각이상 안전(colorblind-safe) 팔레트(예: viridis, cividis)를 사용하고, 임계값 초과 지점은 윤곽선/해칭으로 이중 인코딩
- 상태 배지는 색상 배경 위에 텍스트/아이콘을 겹쳐 표시

**탐지**:
- Chrome DevTools의 vision deficiency emulation(protanopia/deuteranopia/tritanopia)으로 QP 히트맵·MV 오버레이·필름스트립 오류 표시를 렌더링해 색만으로 구분되는 요소가 있는지 스캔
- 그레이스케일로 변환한 스크린샷에서도 상태 구분이 가능한지 육안 검토

**Bitvue 판정**: Confirmed — `QP_COLOR_STOPS`(blue→cyan→yellow→red, `frontend/components/panels/OverlayRenderer/utils/colors.ts:14-19`)가 `QPMapRenderer.tsx`(`frontend/components/panels/OverlayRenderer/renderers/QPMapRenderer.tsx:33-39`)에서 hue 하나로만 QP 값을 인코딩하고 패턴/해칭/숫자 라벨 병기가 없음(전체 min/max 텍스트만 canvas에 그려짐, 블록별 값 없음). 단, 필름스트립 오류 표시는 이미 아이콘("!") + `role="alert"` + `aria-label`을 병행하므로(`frontend/components/Filmstrip/views/ThumbnailsView.tsx:269-276`) 그 증상은 해당 안 됨; MV forward/backward 색 구분도 현재 `MVFieldRenderer.tsx`가 단일 색상(`mvColor`)만 사용해 방향 구분 자체가 아직 구현되어 있지 않음(N/A에 가까움).

### UIX-A11Y-002: keyboard focus 표시 없음

**분류**: 키보드 내비게이션 · **심각도**: High · **탐지**: Interaction

**사용자 목표**:
마우스 없이 Tab/화살표 키만으로 패널·타임라인 프레임·툴바 버튼 사이를 이동하며 현재 위치를 파악하고 싶다.

**증상**:
- Tab으로 이동해도 어느 버튼/프레임이 선택되었는지 화면에서 전혀 보이지 않음
- 커스텀 canvas 기반 타임라인/필름스트립에서 focus ring이 아예 렌더링되지 않음
- `outline: none`으로 브라우저 기본 focus indicator를 제거했지만 대체 스타일을 넣지 않음

**원인**:
디자이너가 focus ring을 "지저분한 파란 테두리"로 보고 미관상 제거했고 대체 시각 신호를 마련하지 않았다. canvas/WebGL 기반 커스텀 컨트롤은 DOM 포커스 개념이 없어 focus 상태를 별도로 그려야 하는데 이 작업 자체가 누락된 경우도 많다.

**구현 냄새**:
- 전역 CSS에 `* { outline: none }` 또는 `:focus { outline: none }` 만 있고 `:focus-visible` 대체 스타일이 없음
- canvas 위에 그려지는 커스텀 컨트롤에 focus 상태를 나타내는 별도 draw call이 없음
- 키보드로만 조작해 본 적 없는 상태로 QA가 종료됨

**영향**:
키보드 사용자(모터 장애, 반복사용긴장성손상증후군, 스크린리더 겸용 사용자, 파워 유저)가 포커스가 프레임 12에 있는지 45에 있는지 알 수 없어 잘못된 프레임에서 삭제·북마크·비교 같은 조작을 실행하게 된다.

**권장**:
- `outline: none`을 쓰는 모든 곳에 `:focus-visible` 대체 스타일(고대비 테두리, 최소 2px 이상)을 명시
- 커스텀 canvas 컨트롤은 포커스된 요소 위에 명시적 하이라이트(테두리, 인디케이터)를 별도로 그림
- 포커스 인디케이터의 대비비가 배경 대비 3:1 이상(WCAG 2.4.11 등)이 되도록 검증

**탐지**:
- 마우스를 치우고 Tab/Shift+Tab/화살표 키만으로 전체 화면을 순회하며, 매 순간 "스크린샷만으로 지금 포커스가 어디에 있는지 알 수 있는가"를 검증하는 시나리오 테스트
- axe-core 등 자동 접근성 린터로 `outline: none` 사용처와 `:focus-visible` 대응 여부 교차 검사

**Bitvue 판정**: N/A(DOM 컨트롤) / Confirmed(canvas 컨트롤) — DOM 기반 버튼/탭/드롭다운은 `outline: none`이 항상 `:focus-visible` 대체(고대비 outline, `forced-colors` 모드 포함)와 짝지어 구현됨(`frontend/App.css:308-384`, `frontend/theme/buttons.css:174-186`, `frontend/components/common/TabContainer.css:82-85`) — 이 패턴은 부재. 그러나 순수 canvas 기반 커스텀 컨트롤(`frontend/components/panels/HRDBufferPanel.tsx:339-344`의 HRD 버퍼 차트)은 `tabIndex`/`role`/focus 전용 draw call이 전혀 없어 애초에 키보드로 포커스조차 안 됨 — 이 부분은 Confirmed.

### UIX-A11Y-003: canvas 요소에 대체 탐색 방법 없음

**분류**: 대체 인터페이스 · **심각도**: High · **탐지**: Code

**사용자 목표**:
MV 벡터, QP 블록, RD 커브 등 canvas/WebGL로 렌더링된 데이터를 스크린리더나 키보드만으로도 항목 단위로 탐색하고 값을 확인하고 싶다.

**증상**:
- QP 히트맵이 `<canvas>` 하나로 통째로 그려져 있고 대응하는 DOM 요소가 전혀 없음
- 스크린리더가 canvas를 만나면 "그래픽"이라고만 안내하고 더 이상 정보를 제공하지 않음
- 블록 단위 값(QP, MV 크기 등)을 확인하는 유일한 방법이 마우스 hover뿐임

**원인**:
canvas/WebGL은 픽셀만 그리고 접근성 트리(accessibility tree)에 아무 정보도 노출하지 않는데, 개발자가 시각적 렌더링만 구현하고 병행하는 논리적 데이터 구조(DOM fallback, ARIA)를 만들지 않았다.

**구현 냄새**:
- `<canvas>` 태그에 `role`, `aria-label` 없이 렌더링 로직만 존재
- 블록/벡터 데이터가 canvas 그리기 함수 내부의 지역 변수로만 존재하고, 순회 가능한 별도 데이터 모델/DOM 미러가 없음
- "hover 시 tooltip으로 값 표시"가 유일한 값 확인 경로

**영향**:
스크린리더 사용자는 QP 히트맵/MV 오버레이의 존재 자체를 인지하지 못하거나 내용에 전혀 접근할 수 없어, 해당 데이터를 이용한 분석 작업을 처음부터 수행할 수 없다 — 기능적으로 완전히 배제된다.

**권장**:
- canvas 옆에 숨겨진(그러나 접근 가능한) 데이터 테이블 또는 `role="img"` + 상세 설명(`aria-describedby`)을 병행 제공
- 블록/화살표 단위로 키보드 화살표 이동 + 값 낭독이 가능한 "논리적 그리드" 모델을 canvas 렌더링과 별도로 유지
- 최소한 "현재 선택된 블록의 QP/MV 값"을 텍스트로 보여주는 사이드 패널을 항상 키보드로 접근 가능하게 제공

**탐지**:
- VoiceOver/NVDA 등 스크린리더를 켜고 QP 히트맵/MV 오버레이 패널에 진입했을 때 무엇이 낭독되는지 시나리오 테스트
- canvas 렌더링 컴포넌트마다 대응하는 접근 가능한 데이터 경로(DOM/ARIA)가 존재하는지 코드 검사

**Bitvue 판정**: Confirmed — 메인 비디오 canvas는 `role="img"` + `aria-label`이 있지만 라벨이 `Video frame ${currentFrameIndex}` 뿐이라(`frontend/components/panels/YuvViewerPanel/VideoCanvas.tsx:236-239`) 그 위에 그려지는 QP 히트맵/MV 오버레이 값은 전혀 노출되지 않음. QP 블록 값은 `qp[idx]`가 `QPMapRenderer.tsx`(`frontend/components/panels/OverlayRenderer/renderers/QPMapRenderer.tsx:29-39`) 내부 지역 변수로만 존재하고 순회 가능한 DOM/ARIA 미러가 없음. `HRDBufferPanel.tsx`의 `<canvas>`(`:339`)는 `role`/`aria-label` 자체가 없음.

### UIX-A11Y-004: 작은 클릭 영역

**분류**: 상호작용 대상 크기 · **심각도**: Medium · **탐지**: Interaction

**사용자 목표**:
프레임 단위 이동 버튼, 필름스트립 썸네일, 타임라인 마커 등을 정확히 클릭/탭하고 싶다.

**증상**:
- 프레임 스텝 버튼, 북마크 아이콘 등이 16px 이하로 렌더링됨
- 고밀도 필름스트립에서 인접 썸네일 사이 클릭 가능 영역이 1~2px밖에 안 되어 자주 옆 프레임이 선택됨
- 타임라인 위 마커(키프레임, anomaly 지점)의 클릭 히트박스가 시각적 크기와 동일해, 확대해야만 정확히 클릭 가능

**원인**:
정보 밀도를 최대화하려고 컨트롤을 시각 크기 그대로 축소했고, 히트박스를 시각 크기보다 넓게 잡는 별도 처리를 하지 않았다.

**구현 냄새**:
- 버튼/아이콘의 CSS width/height가 WCAG 권장 최소 타깃 크기(데스크톱 24x24px, 터치 44x44px)보다 명백히 작음
- 클릭 이벤트 핸들러가 시각 요소의 실제 bounding box에만 바인딩되고 padding을 통한 히트박스 확장이 없음
- "확대 후 클릭"이 정밀 조작의 유일한 우회로로 문서화되어 있음

**영향**:
손 떨림·운동 장애가 있는 사용자뿐 아니라 일반 사용자도 고밀도 필름스트립/타임라인에서 반복적으로 오클릭하여 분석 작업 속도가 느려지고, 잘못 선택된 프레임을 기준으로 분석을 계속하면 결과 자체가 틀린다.

**권장**:
- 모든 상호작용 요소의 클릭 히트박스를 시각 크기와 무관하게 최소 24x24px(마우스 기준) 이상 확보
- 고밀도 뷰(필름스트립)에서는 인접 항목이 겹치는 지점의 클릭을 "가장 가까운 항목"으로 스냅하는 로직 추가
- 확대 없이도 정밀 조작이 가능하도록 키보드 화살표 기반 정밀 이동을 항상 병행 제공

**탐지**:
- 컨트롤별 실제 클릭 가능 영역을 측정해 24x24px 미만인 항목을 코드/스타일 검사로 나열
- 고밀도 필름스트립에서 인접 항목을 빠르게 연속 클릭하는 시나리오로 오클릭률 측정

**Bitvue 판정**: Confirmed — `.frame-ref-badge`(레퍼런스 프레임 클릭 배지)가 기본 상태에서 14x14px 원형(`frontend/components/Filmstrip/views/ThumbnailsView.css:365-386`, `cursor: pointer` 포함)이고, `.frame-nav-search-clear` 버튼도 20x20px(`frontend/components/FrameNavigationToolbar.css:251-254`)로 WCAG 권장 24x24px 미만. 둘 다 히트박스를 시각 크기보다 넓히는 padding/스냅 처리가 없음.

### UIX-A11Y-005: 지나치게 낮은 대비

**분류**: 시각적 대비 · **심각도**: High · **탐지**: Visual

**사용자 목표**:
어두운 테마의 전문 도구에서 텍스트, 아이콘, 그래프 축/그리드선을 장시간 피로 없이 읽고 싶다.

**증상**:
- 비활성(disabled) 상태 텍스트가 배경과 거의 구분되지 않는 회색(예: `#3a3a3a` on `#2a2a2a`)
- RD 커브/히스토그램의 축 라벨, 그리드선이 저대비 회색으로 그려져 저조도 환경에서 읽기 어려움

### UIX-A11Y-007: tooltip에만 핵심 정보 존재

**분류**: 정보 접근성 · **심각도**: High · **탐지**: Interaction

**사용자 목표**:
마우스 hover 없이도(키보드 탐색, 터치, 스크린리더로도) QP 값, MV 크기, 프레임 타입 같은 핵심 분석 정보를 확인하고 싶다.

- 터치 디바이스(터치스크린 워크스테이션)에서 hover 자체가 발생하지 않아 정보에 접근할 방법이 없음
- tooltip이 `title` 속성 하나로만 구현되어 스크린리더가 낭독하지 않거나 지연 후에만 낭독

**원인**:
"마우스 hover"를 유일한 상호작용 모델로 가정하고 설계했고, 키보드 포커스/터치/스크린리더 각각에 대응하는 정보 노출 경로를 별도로 구현하지 않았다.

### UIX-A11Y-008: 확대 시 레이아웃 붕괴

**분류**: 반응형/확대 대응 · **심각도**: Medium · **탐지**: Visual

**사용자 목표**:
OS/브라우저 텍스트 확대(125%~200%) 또는 저시력 보조 확대 기능을 사용해도 패널, 툴바, 그래프가 겹치거나 잘리지 않고 정상적으로 보고 싶다.

**증상**:
- 200% 확대 시 툴바 아이콘들이 겹치거나 잘려서 클릭 불가능해짐
- 사이드 패널의 라벨 텍스트가 확대되면서 고정폭 컨테이너를 벗어나 다른 요소와 겹침
- 창 크기를 줄이거나 폰트를 키우면 QP 히트맵 캔버스와 범례가 서로 겹쳐 범례를 읽을 수 없음

**원인**:
레이아웃이 px 고정 크기와 절대 위치(absolute positioning)로 설계되어 텍스트/컨트롤 크기 변화에 따라 재흐름(reflow)되지 않는다.

**구현 냄새**:
- 폭/높이가 `px` 고정값으로 하드코딩되고 `rem`/`%`/flex/grid 기반 유연한 레이아웃이 아님
- 텍스트 컨테이너에 `overflow: hidden` + `white-space: nowrap`만 있고 확대 시 잘림 대비(줄바꿈, 축약, 스크롤)가 없음
- 200% 확대 상태에서 QA를 진행한 기록이 없고 기본 100% 배율에서만 디자인 검증됨

**영향**:
저시력 사용자, 고해상도 디스플레이에서 OS 배율을 높여 쓰는 사용자가 핵심 컨트롤에 접근하지 못하거나 범례/축 라벨을 읽지 못해 데이터를 오독한다.

**권장**:
- 레이아웃을 flex/grid + 상대 단위(rem/%) 기반으로 설계해 텍스트 확대에 따라 자연스럽게 재흐름되도록 구현
- 200%, 400% 브라우저 확대(WCAG 1.4.4/1.4.10 기준) 상태에서 겹침/잘림 없이 접근 가능한지 QA 체크리스트에 포함
- 좁아진 공간에서는 툴바를 오버플로 메뉴로 축약하는 등 명시적인 반응형 전략을 설계

**탐지**:
- 브라우저 확대 100/150/200/400%에서 각 패널을 스크린샷으로 비교해 겹침/잘림 여부 확인
- OS 텍스트 크기 설정을 최대로 올린 상태에서 전체 워크플로(프레임 탐색→히트맵 확인→값 조회)를 끝까지 수행 가능한지 시나리오 테스트

**Bitvue 판정**: Suspected — 레이아웃 자체는 상당 부분 flex/grid + `rem`/`%`이지만, YUV 뷰어 툴바/범례 영역은 `position: absolute` + px 고정폭이 다수 존재(`frontend/components/panels/YuvViewerPanel/YuvViewerPanel.css:73,87,120,249,274,346`)하고 QP 범례 자체가 canvas `fillText`로 그려져(`QPMapRenderer.tsx:44-49`) OS 텍스트 확대의 영향을 전혀 받지 않는 구조. 200%/400% 확대 시 실제로 겹치는지는 브라우저 렌더링 확인 없이는 단정 불가 — 구조적으로 개연성 있는 정도.

### UIX-A11Y-009: screen reader용 label이 없음

**분류**: 스크린리더 지원 · **심각도**: High · **탐지**: Code

**사용자 목표**:
스크린리더로 툴바 아이콘 버튼, 드롭다운, 슬라이더가 각각 무슨 기능인지 파악하고 조작하고 싶다.

**증상**:
- 아이콘만 있는 버튼(재생/일시정지/북마크/비교 등)에 텍스트 라벨이 전혀 없어 스크린리더가 "버튼"이라고만 읽음
- 커스텀 드롭다운/콤보박스가 `<div>` 조합으로 만들어져 `role`, `aria-expanded`, `aria-selected` 등이 없어 선택 가능한 목록임을 스크린리더가 인식하지 못함
- QP 임계값 슬라이더가 현재 값을 시각적으로만 표시하고 `aria-valuenow`가 없어 스크린리더 사용자는 값을 알 수 없음

**원인**:
컴포넌트를 시각적 결과물(아이콘, 커스텀 드롭다운 UI) 중심으로 구현하고, 각 컴포넌트가 어떤 네이티브 HTML 요소/ARIA 역할에 대응해야 하는지 고려하지 않았다. 특히 네이티브 `<select>`, `<input type="range">` 대신 직접 구현한 디자인 시스템 커스텀 컴포넌트에서 반복된다.

**구현 냄새**:
- 아이콘 버튼에 `aria-label`이나 시각적으로 숨겨진(`sr-only`) 텍스트가 없음
- 커스텀 인터랙티브 컴포넌트가 `<div onClick>`으로 구현되고 `role="button"`/`tabindex`/키보드 핸들러가 없음
- 폼 컨트롤에 대응하는 `<label>` 요소나 `aria-labelledby` 연결이 없음

**영향**:
스크린리더 사용자는 툴바가 무엇을 하는지, 지금 어떤 값이 설정되어 있는지 전혀 알 수 없어 도구를 독립적으로 조작할 수 없다 — 법적 컴플라이언스 문제이자 완전한 기능적 배제다.

**권장**:

### UIX-A11Y-010: 단축키 도움말을 찾을 수 없음

**분류**: 발견가능성(discoverability) · **심각도**: Medium · **탐지**: User test

**사용자 목표**:
프레임 스텝, 줌, 오버레이 토글 등에 쓸 수 있는 키보드 단축키 전체 목록을 필요할 때 쉽게 찾아 확인하고 싶다.

**증상**:
- 단축키가 존재하긴 하지만 어디에도 목록으로 정리되어 있지 않아 우연히 발견하거나 소스코드를 뒤져야 함
- `?` 키나 도움말 메뉴를 눌러도 단축키 목록이 뜨지 않음
- 툴바 버튼에 단축키가 tooltip으로도 병기되지 않아, 마우스로 쓰던 기능을 키보드로 대체할 수 있다는 사실 자체를 모름

**원인**:
단축키를 개발 과정에서 파워 유저 편의를 위해 하드코딩했지만, 이를 사용자에게 노출하는 UI(도움말 오버레이, 메뉴 항목, tooltip 병기)는 별도 작업으로 취급되어 우선순위에서 누락되었다.

**구현 냄새**:

- 메뉴/버튼 라벨에 단축키가 병기되지 않음(예: "재생" 옆에 "Space" 표시 없음)
- 온보딩/도움말 문서에 단축키 섹션이 없거나 오래되어 실제 구현과 어긋남

**영향**:
키보드 단축키에 의존해야 생산성이 나오는 전문 도구인데, 발견 가능성이 없으면 대부분의 사용자가 단축키를 영영 모른 채 느린 마우스 조작만 반복하게 된다 — 특히 모터 장애로 마우스 사용이 어려운 사용자에게는 단순 불편이 아니라 접근성 장벽이 된다.

**권장**:
- 모든 단축키를 하나의 중앙 레지스트리(데이터)로 관리하고, 이를 소스로 "단축키 도움말" 오버레이(`?` 키 등 업계 관용 트리거)를 자동 생성
- 메뉴 항목/버튼 tooltip에 해당 단축키를 항상 병기
- 단축키 목록을 기능명으로 검색/필터링 가능한 형태로 제공

**탐지**:
- 신규 사용자 대상으로 "이 도구에 단축키가 있는지, 있다면 어떻게 확인하는지" 질문하는 사용자 테스트
- 코드베이스에서 키 이벤트 리스너 등록 지점 전체를 grep해, 그중 도움말 UI/문서에 실제로 나열된 것이 몇 개인지 대조

**Bitvue 판정**: N/A — 이 안티패턴이 이미 해결되어 있음: 중앙 레지스트리 `KEYBOARD_SHORTCUTS`(`frontend/utils/keyboardShortcuts.ts`)를 소스로 `KeyboardShortcutsDialog.tsx`가 자동 생성되고, `?` 키(`frontend/hooks/useKeyboardNavigation.ts:238`)와 Help 메뉴(`frontend/utils/menu/creators/helpMenu.ts:30-32`) 양쪽에서 업계 관용대로 열림. 버튼 tooltip에도 단축키가 병기됨(예: `PlaybackControls.tsx:26` `"Pause (Space)"`). 권장안이 이미 구현된 상태.

### UIX-A11Y-011: 색각 이상을 고려하지 않은 heatmap/diverging 팔레트

**분류**: 색상 인코딩 · **심각도**: Critical · **탐지**: Domain review

**사용자 목표**:
QP/MV/품질 편차 같은 연속값을 컬러맵으로 표시할 때, 색각 유형과 무관하게 값의 상대적 크기와 방향(양/음)을 정확히 읽고 싶다.

**증상**:
- QP 히트맵이 고전적인 "jet"(파랑-청록-노랑-빨강) 컬러맵을 사용해 지각적으로 균일하지 않은 구간(노랑 근처가 뭉개짐)이 존재
- 두 스트림 비교용 diverging 팔레트(A가 더 좋음=초록, B가 더 좋음=빨강)가 적록색각이상 사용자에게는 거의 같은 회색조로 보임
- 팔레트를 색각이상 시뮬레이터로 검증한 기록이 디자인 산출물 어디에도 없음

**원인**:
컬러맵을 "시각적으로 화려하고 데이터 범위를 다채롭게 보여주는 것"을 기준으로 선택했고, 지각적 균일성(perceptual uniformity)과 색각이상 시뮬레이션 검증을 설계 프로세스에 포함하지 않았다.

**구현 냄새**:
- 컬러맵 정의가 임의의 RGB 정지점(stop) 배열로 하드코딩되고, viridis/cividis 같은 검증된 지각 균일 팔레트 라이브러리를 쓰지 않음
- diverging 팔레트의 두 극단이 hue만 다른 순수 빨강/초록 조합(예: `#FF0000` vs `#00FF00`)
- 팔레트 교체/추가 시 색각이상 시뮬레이션 스크린샷을 리뷰 산출물로 요구하지 않음

**영향**:
색각이상 사용자가 QP/품질 편차 히트맵에서 "더 나쁨"과 "더 좋음"을 반대로 읽거나 아예 구분하지 못해, 인코더 튜닝/비교 판단이 실제로 반대 방향으로 내려질 수 있다 — 이 도구군 전체에서 접근성이 정확성 버그로 직결되는 대표 사례다.

**권장**:
- diverging에는 두 hue가 명도로도 충분히 구분되는 검증된 팔레트(hue 하나로만 극단을 나누지 말고 채도·명도를 이중 인코딩) 사용, sequential에는 viridis/cividis류 지각 균일 팔레트 사용
- 팔레트마다 protanopia/deuteranopia/tritanopia 시뮬레이션 스크린샷을 디자인 리뷰 체크리스트에 포함
- 임계값을 넘는 지점은 색상 외에 윤곽선/해칭 등 형태 신호를 병행해 팔레트 자체의 한계를 보완

**탐지**:
- Coblis/Chrome DevTools 색각이상 시뮬레이션으로 모든 heatmap/diverging 팔레트를 렌더링해 값의 상대적 순서가 유지되는지 확인
- 팔레트의 지각 균일성을 CIE L*a*b* 공간에서 명도(L*) 단조 증가 여부로 정량 검증

**Bitvue 판정**: Confirmed — `QP_COLOR_STOPS`(`frontend/components/panels/OverlayRenderer/utils/colors.ts:14-19`)가 정확히 "jet류" 파랑→청록→노랑→빨강 4-stop RGB 정지점을 임의 하드코딩한 것이며, viridis/cividis 같은 검증된 지각 균일 팔레트가 아님. 색각이상 시뮬레이션 검증 기록도, `docs`/코드 어디에도 없음. diverging(A/B 비교) 전용 별도 팔레트는 코드에서 확인되지 않아 그 부분은 아직 미구현(N/A에 가까움) — 확인된 것은 sequential QP 히트맵 컬러맵 자체의 결함.

### UIX-A11Y-012: 깜빡임/모션에 대한 제어 불가

**분류**: 모션/발작 안전 · **심각도**: Medium · **탐지**: Interaction

**사용자 목표**:
anomaly 강조 깜빡임, 자동 재생 애니메이션, 실시간 갱신 그래프 등을 전정기관 장애나 광과민성 발작 위험 없이, 또는 최소한 끌 수 있는 선택지를 가지고 사용하고 싶다.

**증상**:
- 디코딩 오류/이상치 프레임을 강조하기 위해 해당 썸네일/블록이 빠르게 점멸(blink)함
- 실시간 비트레이트/QP 그래프가 매 프레임 갱신되며 화면 전체가 지속적으로 흔들리듯 리렌더링됨
- OS의 "모션 줄이기(`prefers-reduced-motion`)" 설정을 앱이 전혀 감지하지 않고 항상 동일한 애니메이션을 재생

**원인**:
강조 효과(깜빡임, 흔들림)를 "주의를 끄는 가장 확실한 방법"으로 채택했고, 모션 민감 사용자를 위한 감쇠/차단 경로나 OS 설정 연동을 구현 범위에서 제외했다.

**구현 냄새**:
- CSS `@keyframes` 기반 blink/pulse 애니메이션이 `prefers-reduced-motion: reduce` 미디어 쿼리 분기 없이 하드코딩됨
- 애니메이션 강도/속도를 제어하는 설정 UI가 없음
- 초당 3회를 초과하는 점멸(WCAG 2.3.1 임계값)이 있는지 검증한 기록이 없음

**영향**:
광과민성 발작 위험이 있는 사용자에게는 안전 문제이며, 전정기관 장애(어지럼증 유발) 사용자에게는 장시간 작업이 불가능한 수준의 불편을 초래한다 — 전문 분석 도구는 특성상 장시간 사용이 전제되므로 영향이 누적된다.

**권장**:
- 모든 반복 애니메이션(깜빡임, pulse, 실시간 그래프 흔들림)에 `prefers-reduced-motion` 대응을 구현하고, 앱 자체 설정에도 "모션 줄이기" 토글을 제공
- 강조 효과의 점멸 빈도를 초당 3회 미만으로 제한하거나, 깜빡임 대신 정적 강조(테두리 두께, 아이콘, 배지)로 대체
- 실시간 갱신 그래프는 갱신 주기를 사용자가 조절하거나 일시정지할 수 있게 함

**탐지**:
- 브라우저 개발자 도구의 CSS media feature emulation으로 `prefers-reduced-motion: reduce` 상태에서 앱이 실제로 애니메이션을 줄이는지 확인
- 강조 효과의 초당 점멸 횟수를 프레임 캡처로 측정해 WCAG 2.3.1 임계값(초당 3회) 준수 여부 검증

**Bitvue 판정**: Confirmed — 저장소 전체에서 `prefers-reduced-motion`이 쓰이는 곳은 `frontend/components/panels/DockableLayout.css:387-392` 단 한 곳뿐이며, 그마저도 `scroll-behavior: smooth` 토글용이지 반복 애니메이션 감쇠용이 아님. `referencedPulse`(`ThumbnailsView.css:240`), `pulse-arrow`(`CodingFlowView.css:153`), `subtlePulse`(`App.css:496`), `progress-pulse`(`Loading.css:184`) 등 무한 반복 pulse 애니메이션은 전부 `prefers-reduced-motion` 분기 없이 하드코딩됨. 다만 주기가 1.5~2s(0.5~0.67Hz)로 WCAG 2.3.1의 초당 3회 임계값보다 훨씬 느려 발작 위험 자체는 낮고, 전정기관 불편/모션 감쇠 제어 부재 쪽이 실제 위반 지점.
